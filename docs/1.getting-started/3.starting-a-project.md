# Starting a Project

Vuestrata is a template you own a copy of, not a dependency you resolve. That
normally means upstream improvements never reach you. `@vuestrata/cli` is what
makes them reach you anyway, and this page is the path from a fresh copy to an
app that can still take updates a year later.

Prerequisites and the dependency install are in
[Installation](/docs/getting-started/installation).

## 1. Take your own copy

Use the **Use this template** button on
[the repository](https://github.com/boussadjra/vuestrata) rather than forking —
you want your own history, not a fork tied to ours.

```bash
git clone https://github.com/<you>/<your-app>.git my-app
cd my-app
vp install
```

## 2. Install the CLI

```bash
vp add -D @vuestrata/cli
```

Do this now even if you have no intention of upgrading soon. It costs nothing,
and the alternative is retrofitting it onto a codebase you have already changed —
where it can no longer tell your edits apart from what it shipped.

```bash
vp exec vuestrata doctor
```

Expect **"Everything an upgrade needs is in place"**. The template ships its own
`vuestrata.lock.json`, so there is no `init` step; that command exists for
adopting the CLI in a project that predates it.

## 3. Clear out the demo

The template arrives with nine demo modules, a marketing home page, a component
showcase and an in-app documentation site. They exist to be read, not kept.

```bash
vp exec vuestrata eject --dry-run
```

Read the plan. When you are happy with it:

```bash
vp exec vuestrata eject
```

Deleting those directories is the easy part. The command also unwires the
modules from the registry, withdraws their permissions from the closed
`BuiltinPermission` union **and** from the roles that were granted them, removes
the tests that covered them, and writes a placeholder home route. Doing that by
hand means finding each one from a broken build.

`--keep customers` keeps a module you want as a reference. `--keep-docs` keeps
`docs/`.

```bash
vp check && vpr build && vpr test --run
```

Commit that on its own. It is a large deletion and it is worth having isolated
in your history.

## 4. Build your app

Scaffold domains rather than hand-writing them — not for speed, but because the
registries are easy to forget and forgetting one fails silently. A module
missing from `setup.ts` does not throw; the feature simply never loads.

```bash
vp exec vuestrata add module payments
```

That writes the zod contract, the queries, a seeded mock backend, three pages
and the translations, then registers the module and its permissions. The same
goes for `add page`, `add component`, `add theme` and `add icon-set`. Every one
of them takes `--dry-run`.

See [Recipes](/docs/recipes) for what each generator deliberately leaves to you.

## 5. Customise through the seams

This is the habit that decides whether upgrades keep working for you.

| To change                      | Edit this                                         |
| ------------------------------ | ------------------------------------------------- |
| A colour, radius, shadow, ramp | `src/modules/app/styles/brand.css`                |
| Any interface string           | `src/modules/app/locales/<locale>.overrides.json` |
| Product name, footer links     | `src/modules/app/config/app.overrides.ts`         |
| The logo                       | `src/modules/app/components/Logo.vue`             |

Each of those files is yours from the moment you clone. Nothing upstream ever
writes to them.

To restyle a component from the outside, pass classes:

```vue
<UiButton class="rounded-none px-10">Save</UiButton>
```

The incoming class genuinely replaces the wrapper's own padding rather than
racing it, so you rarely need to open the component at all.

You _may_ edit `semantic.css`, a `Ui*` wrapper, or any other file Vuestrata
owns. It simply means that file becomes yours, upgrades stop updating it, and
every release reports it. A fine trade when you mean it, an expensive surprise
when you do not.

## 6. Take an update

```bash
vp add -D @vuestrata/cli@latest
vp exec vuestrata diff
```

`diff` prints exactly what `upgrade` is about to do and writes nothing. When it
looks right, from a clean working tree:

```bash
vp exec vuestrata upgrade
vp check && vpr test --run
```

Files you never touched are replaced. Files you edited are left alone, with the
new version written to `.vuestrata/incoming/<path>` and the `git diff --no-index`
command printed so you can decide what to take. Modules you created are never
mentioned.

[Upgrading](https://github.com/boussadjra/vuestrata/blob/main/UPGRADING.md) has
the full account of how that decision is made.

## A rough edge

Your project also contains a committed `packages/cli/` directory, because it
lives in the template repository. That copy is frozen at the version you cloned
and never updates, so the `vpr gen:*` scripts in `package.json` will drift.

Use `vp exec vuestrata ...` as shown above — that runs the installed package,
which is the one that moves. Cleaner still, delete `packages/cli/` from your
project: it is the machinery that maintains Vuestrata, not part of your app.
