# Develop Against Your Backend

`vpr dev` starts in demo mode: MSW answers every request inside the browser and
no backend is involved. To work against your own API, run the dev server in
**production mode** — the code path a real deployment takes — and choose how
the browser reaches the API.

|                      | A. Proxy (recommended)        | B. Direct                   | C. Demo                 |
| -------------------- | ----------------------------- | --------------------------- | ----------------------- |
| `VUESTRATA_API_URL`  | `/api`                        | `http://localhost:8000/api` | `/api`                  |
| Requests go to       | the dev server, then your API | your API                    | MSW, inside the browser |
| CORS on your backend | not needed                    | required                    | not needed              |
| Cookies              | first-party                   | cross-origin                | none                    |

## A. Proxy through the dev server

Create `.env.development.local` in the project root:

```bash
VUESTRATA_RUNTIME_MODE=production
VUESTRATA_USE_MOCKS=false
VUESTRATA_AUTH_ADAPTER=jwt             # or oauth
VUESTRATA_API_URL=/api
DEV_API_TARGET=http://localhost:8000
```

Run `vpr dev`. The browser asks the dev server for `/api/...`, and the dev
server forwards each request, path unchanged, to `DEV_API_TARGET`:

```
browser ─▶ http://localhost:3333/api/users ─▶ dev server ─▶ http://localhost:8000/api/users
```

The path is not rewritten, so your backend must serve its API under `/api`
too. If it serves it from the root, use B.

From the browser's side this is the same-origin deployment that `/api` stands
for in production, behind your reverse proxy. The backend needs no CORS
configuration, session and refresh cookies are first-party — `SameSite=Strict`
included — and `VUESTRATA_API_URL=/api` is already the value a same-origin
deployment ships with.

What the proxy does on the way through:

- **Only the API path.** `/api` and `/api/users` are forwarded; `/api-docs` and
  the app's own files are not.
- **Cookies land on the dev server.** Any `Domain` attribute is stripped from
  `Set-Cookie`, so a cookie your backend scopes to its own host is kept rather
  than rejected. `Path` is left alone.
- **Your backend sees its own host.** `Host` is rewritten to the target, and the
  browser-facing host arrives in `X-Forwarded-Host`. A framework that checks
  `Origin` against a trusted list for CSRF (Django's `CSRF_TRUSTED_ORIGINS`,
  Laravel Sanctum's stateful domains) needs the dev server,
  `http://localhost:3333`, on that list.
- **WebSockets** under the path are proxied too.
- **A stopped backend** shows up as a `502` in the browser and an
  `http proxy error` in the terminal.
- **Only the dev server.** A build never reads `DEV_API_TARGET`, and
  `vpr preview` does not proxy.

::alert{type="info"}
`DEV_API_TARGET` is deliberately **not** a `VUESTRATA_` variable. Every
`VUESTRATA_*` value is inlined into the client bundle; this one is read only by
the dev server, so it never reaches `import.meta.env`, a build, or a browser.
::

## B. Call your backend directly

```bash
VUESTRATA_RUNTIME_MODE=production
VUESTRATA_USE_MOCKS=false
VUESTRATA_AUTH_ADAPTER=jwt
VUESTRATA_API_URL=http://localhost:8000/api
```

A build rejects `localhost`, `127.0.0.1`, `0.0.0.0` and `api.example.com` as
placeholder hosts. `vp dev` accepts them, so this works under the dev server
and nowhere else. The page's own CSP `<meta>` does not restrict connections, so
nothing has to be widened for it: under `vp dev` no header carries a policy, and
the calls go through.

Your backend has to answer CORS for the dev origin:

| Header                             | Value                                       |
| ---------------------------------- | ------------------------------------------- |
| `Access-Control-Allow-Origin`      | `http://localhost:3333` — exact, never `*`  |
| `Access-Control-Allow-Credentials` | `true`                                      |
| `Access-Control-Allow-Headers`     | `Authorization, Content-Type, X-CSRF-Token` |
| `Access-Control-Allow-Methods`     | `GET, POST, PUT, PATCH, DELETE`             |

Credentials are not optional: the default `refresh-cookie` session restore and
the `oauth` adapter both send cookies, and a browser refuses a credentialed
response that allows `*`.

Give both servers the same host name: with the API at `http://localhost:8000`,
open the app at `http://localhost:3333`, not `http://127.0.0.1:3333`. A
different port is still the same site, so `SameSite=Lax` cookies keep flowing;
a different host name makes every cookie cross-site.

Prefer A. B is for exercising the CORS setup that a cross-origin deployment
will need.

## C. Stay in demo mode

No configuration: `vpr dev` defaults to demo mode, MSW answers every request
from seeded fixtures, and you sign in with the demo account. Demo mode always
runs MSW and the mock adapter — the schema rejects a real adapter or
`VUESTRATA_USE_MOCKS=false` there — so it never talks to a backend. Switch to A
when you need one.

::alert{type="warning"}
`vpr dev` starts the server with `--host`, so the proxy forwards requests from
anyone on your network to `DEV_API_TARGET`. Point it only at a backend you are
happy to expose on the LAN, or run `vp dev` without `--host`.
::

## Why `.env.development.local`

Vite reads `.env.[mode].local` only in that mode, and `vp dev` runs in
`development`. So this file configures the dev server and nothing else:
`vpr build` runs in `production` mode and `vpr test` in `test`, so neither
reads it. The `.local` suffix keeps it out of git, and it overrides
`.env.local`, so a copy of `.env.example` there does not get in the way.

That scoping is what lets a build keep refusing a local backend URL while you
develop against one. Setting the variables inline also works in a POSIX shell
(`VUESTRATA_API_URL=/api vpr dev`), but Git Bash on Windows rewrites `/api` into
a Windows path before Vite sees it. The file avoids that; so does prefixing the
command with `MSYS_NO_PATHCONV=1`.

## When it does not work

| You see                                                         | Cause                                                                                            |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| `DEV_API_TARGET is set, but VUESTRATA_API_URL=… is absolute`    | The browser calls that origin directly, so there is nothing to proxy. Use a path such as `/api`. |
| `DEV_API_TARGET must be an absolute http(s) URL`                | Include the scheme: `http://localhost:8000`.                                                     |
| `/api` requests get `index.html` or a `404` from the dev server | No proxy is running: `DEV_API_TARGET` is not set where `vp dev` reads it.                        |
| `vpr build` fails with `points at the placeholder host`         | A local backend URL reached a build. Keep it in `.env.development.local`.                        |
| `"C:/Program Files/Git/api" must use http or https`             | Git Bash rewrote an inline `/api`. Put the variables in the file, or set `MSYS_NO_PATHCONV=1`.   |

For every variable and the rules that combine them, see
[Environment](/docs/configuration/environment). For the endpoints your backend
must implement, see [Real Production](/docs/deployment/real-production).
