# Deploying the demo

The demo is a complete application with **no backend**. MSW runs as a service
worker and answers every request from seeded fixtures. It exists to be clicked
through, screenshotted and linked to — not to be trusted with anything.

## Environment variables

`vercel.json` injects the three required variables on the build command, so a
Git-connected project deploys a working demo without dashboard setup:

```
VUESTRATA_RUNTIME_MODE=demo
VUESTRATA_USE_MOCKS=true
VUESTRATA_AUTH_ADAPTER=mock
```

`vpr build` defaults `RUNTIME_MODE` to `production`. Leaving the other two as
demo values in the Vercel dashboard (or in a leftover `.env`) is what produces
`Incompatible environment configuration`. The build command overrides that
mismatch.

Optional branding still belongs in the project settings (Settings → Environment
Variables):

```
VUESTRATA_APP_TITLE=Acme Console
VUESTRATA_THEME=ocean
VUESTRATA_DEMO_AUTH_RETENTION_HOURS=24
```

::alert{type="info"}
Those three are set on the build command, not read from the dashboard, so a
leftover `RUNTIME_MODE=production` in project settings cannot break the demo.
Branding variables above still come from the dashboard.
::

## Project settings

`vercel.json` is committed and already correct. It configures:

- **Build**: demo-mode `vp build` (the built-in, so no `vue-tsc` pass), output
  `dist`
- **SPA fallback**: everything rewrites to `/index.html`, so a hard load of
  `/dashboard/orders/ORD-1042` works. `/api/*` is excluded — without that
  exclusion the fallback would answer API calls with HTML, and MSW's passthrough
  would look like a JSON parse error. `/runtime-config.js` is excluded for the
  same reason: every page loads it as a script before the app, and it must be
  the file, never the page.
- **`/assets/*`**: `max-age=31536000, immutable`. Safe because the filenames are
  content-hashed.
- **`/mockServiceWorker.js`**: `no-cache`. **This one matters.** A cached
  service worker keeps serving the previous deploy's handlers indefinitely, and
  the symptom — a demo showing stale data with no error — is close to
  undebuggable.
- **Security headers**: generated from the same definition as `public/_headers`,
  so the demo and any static host agree. Vercel reads `vercel.json` from the
  repository before the build runs, so the policy is whatever is committed: an
  origin the app must reach goes under `headers.connectSrc` in
  `src/modules/app/config/deploy.config.ts`, followed by `vpr security:headers`.
  See [Security headers](./2.real-production#security-headers).

## Deploying

```bash
vp dlx vercel --prod
```

Or connect the repository and let Vercel build on push. Nothing else is needed:
no database, no API, no secrets.

## Signing in

The demo account is defined once in `src/modules/app/state/demo/account.ts` and
shared by the login page, the MSW handler and the e2e helper. It is shown on the
login screen, so you do not need to document it separately.

Session state lives in IndexedDB, in the database named by `DEMO_DB_NAME` in
`src/modules/app/state/demo-persistence.ts`, and expires after
`VUESTRATA_DEMO_AUTH_RETENTION_HOURS`.

## Verifying a demo deploy

```bash
node scripts/build/verify-bundle.mjs --mode=demo
```

Five assertions: the build exists, an MSW chunk was emitted, the service worker
is published, `index.html` exists, and it loads `runtime-config.js` as a separate
script before the app. The checks on what the page loads run as well: its
scripts are in the build, no on-demand chunk is among them, and the four size
budgets hold ([Your own budgets](../6.configuration/1.environment#your-own-budgets)).
CI runs this on every build.

Then, against the deployed URL, confirm by hand:

1. The service worker registers at the **root** scope. Registered under
   `/assets/` it would never see requests from the app shell.
2. A dashboard request returns JSON. There is no backend, so a 200 with JSON can
   only have come from MSW.
3. A hard reload of a nested route (`/dashboard/customers/CUS-1000`) renders
   rather than 404s.

`e2e/smoke.spec.ts` asserts all three against the built preview.

## Limitations, stated plainly

The demo is a demo. Specifically:

- **Data resets.** Everything is in-memory plus IndexedDB. Writes survive a
  reload; they do not survive a new browser, and they are not shared between
  visitors.
- **No real authentication.** The mock adapter validates credentials against
  seeded records in the browser. Anyone who opens devtools can grant themselves
  any role. This is fine for a demo and catastrophic anywhere else — which is
  exactly why `AUTH_ADAPTER=mock` is rejected outside demo mode.
- **A service worker is required.** Browsers with service workers disabled, and
  some private-browsing modes, will show an application that cannot load data.
- **Not a performance benchmark.** Handlers add artificial latency so loading
  states are visible.

## Preview deployments

Pull-request previews use the same demo configuration. They are the right place
to review UI changes and the wrong place to test backend integration — for that,
use a staging build in `production` mode pointed at a staging API.
