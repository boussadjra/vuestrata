# CI for your project

The workflows in `.github/workflows` are the template's own. They test the CLI
by running it against the template, build against a placeholder API, run the
end-to-end suite in four browsers, publish a release tarball and deploy the
hosted demo. A project needs the part of that which is about an application,
and none of the part that maintains a template.

```bash
vp exec vuestrata add ci
```

That writes `.github/workflows/ci.yml` for a project. `vuestrata eject` writes
the same file in place of the template's, so a project that ejected already has
it.

**It is your file from then on.** `vuestrata upgrade` never rewrites it and
`vuestrata doctor` never compares it: add jobs, remove them, change the
triggers. `add ci` writes nothing when the workflow is already in place, and
refuses to write over any other one. `--force` is how you replace a workflow
with the current version, and `--branch <name>` names a default branch other
than `main`.

## What it runs

On every pull request and every push to the default branch, with a newer push
cancelling the run it makes obsolete, and with `permissions: contents: read`:

| Job      | What it does                                                                                                      |
| -------- | ----------------------------------------------------------------------------------------------------------------- |
| `check`  | `vp build` for the typings, then `vp check`, `vp run lint` and `vue-tsc`                                          |
| `test`   | `vp run test --run --coverage`, and uploads `coverage/`                                                           |
| `build`  | A **production** build, `verify-bundle --mode=production`, and `dist/` uploaded as the `dist-production` artifact |
| `e2e`    | The end-to-end suite in Chromium against a preview of the built app; the report is uploaded when it fails         |
| `docker` | Builds the image, starts it, and opens it in a browser. Written only when the project has a `Dockerfile`          |
| `ci-ok`  | Fails when any of the others did. The one status check to require in branch protection                            |

`build` waits for `check` and `test`, and `e2e` waits for `build`, so a broken
bundle fails before any browser time is spent on it.

The `check` job builds first for one reason: the route and auto-import typings
(`typed-router.d.ts`, `src/auto-imports.d.ts`, `src/components.d.ts`) are
generated, not committed, and `vp check` reads them. On a fresh checkout it
reports hundreds of errors without them. That build is thrown away; the one
that counts is the `build` job's.

There is no deploy job, and nothing in the workflow reads a secret.

## The two variables

The production build takes its API URL and its auth adapter from the
repository's **variables** (Settings → Secrets and variables → Actions →
Variables), not from the workflow file:

| Variable                 | Default                         | What it is                                                       |
| ------------------------ | ------------------------------- | ---------------------------------------------------------------- |
| `VUESTRATA_API_URL`      | `https://api.vuestrata.invalid` | Where the built app sends its requests                           |
| `VUESTRATA_AUTH_ADAPTER` | `jwt`                           | `jwt`, `oauth`, or an adapter you registered in `auth.config.ts` |

Neither has to be set for the first run to pass. The default URL is a host the
build accepts and nothing can ever answer on (`.invalid` is reserved for that),
which is the point: the pipeline is green on day one, and an artifact built
without the variable cannot reach somebody else's server. **Set
`VUESTRATA_API_URL` before you deploy what the `build` job uploads.**

The other two values are fixed in the workflow, because they are what makes the
build a production one: `VUESTRATA_RUNTIME_MODE=production` and
`VUESTRATA_USE_MOCKS=false`. `VUESTRATA_RELEASE` is the commit.

A cross-origin API URL also has to be allowed by the Content-Security-Policy.
For a static host, see
[Where each origin comes from](2.real-production#where-each-origin-comes-from);
the Docker image decides it when a container starts.

Anything else your build reads, add to the `env` of the `Build` step the same
way:

```yaml
env:
  VUESTRATA_APP_TITLE: ${{ vars.VUESTRATA_APP_TITLE || 'Acme Console' }}
```

Use variables, not secrets: every `VUESTRATA_*` value ends up in the bundle,
where anyone can read it.

## The end-to-end job tests a demo build

`E2E_TARGET=preview` makes Playwright build the app and serve `dist/`, so the
suite runs against a real bundle and not the dev server. That build is the
**demo** one: `playwright.config.ts` sets demo mode, the mock backend and the
mock sign-in for it, because the specs need a backend that answers.

So this job proves that the application works against its mock backend, and the
`build` job proves that the production artifact holds none of it. Neither
proves that your backend answers the way the mocks do. To run specs against a
deployed environment, start nothing and point the suite at it:

```yaml
- name: Run E2E against staging
  env:
    E2E_TARGET: external
    E2E_BASE_URL: https://staging.yourcompany.com
  run: vpr test:e2e --project=chromium
```

The job runs Chromium only. `playwright.config.ts` also defines `firefox`,
`webkit` and `mobile-chrome`; add a matrix when you need them.

## The Docker job

Written when the project has a `Dockerfile` and the spec that opens the image,
`e2e/production-artifact.spec.ts`. It builds the image, starts a container,
waits for `/healthz`, and runs that spec against it with `E2E_TARGET=external`.
Nothing is pushed.

It is there because `verify-bundle` reads files on disk and cannot tell you the
app mounts behind nginx. A project that ships no container deletes its
`Dockerfile`, and `add ci` then writes no such job; run `vuestrata add ci
--force` after adding or removing one, or delete the job by hand.

## Adding a deploy job

Where the app ships, and who may trigger that, are your decisions, so the
workflow stops at an artifact. A deploy job belongs after everything else has
passed, on the default branch only, behind a GitHub environment that holds the
secrets and can require an approval:

```yaml
deploy:
  name: Deploy
  runs-on: ubuntu-latest
  needs: [build, e2e]
  if: github.event_name == 'push' && github.ref == 'refs/heads/main'
  environment: production
  steps:
    - uses: actions/download-artifact@v4
      with:
        name: dist-production
        path: dist/
    # Upload dist/ to your host here.
```

Three things to get right:

- **Deploy the artifact `build` verified**, as above, and do not build again in
  the deploy job. A second build is a second artifact, and nothing checked it.
- **One artifact per API URL**, for a static host: the URL is compiled in. To
  ship one build to several environments, use the Docker image, which takes its
  URL when a container starts. See
  [Build once, deploy many](2.real-production#build-once-deploy-many).
- **Give the job only what it needs.** `permissions: contents: read` at the top
  of the workflow applies to it too. A job that pushes an image to GHCR adds
  `packages: write` to itself, not to the workflow.

For a container, the deploy job builds and pushes the image the `docker` job
only built. Add it to the `needs` of `ci-ok` only if a failed deploy should fail
the required check.

[Deploying to production](2.real-production) covers what the app needs from the
host: the headers, the `/api` route, the SPA fallback.

## How it differs from the template's own pipeline

| The template's `ci.yml`                                              | The project workflow                          |
| -------------------------------------------------------------------- | --------------------------------------------- |
| Round-trips the CLI: scaffolds modules, ejects, checks the lockfile  | No such job                                   |
| Maintainer gates: the template lock, the CLI payload, the snapshots  | None of them                                  |
| Builds the demo and the production artifact, and verifies both       | Builds and verifies production                |
| Production build against a fixed placeholder URL                     | API URL and adapter from repository variables |
| End-to-end in four browsers                                          | Chromium                                      |
| Starts the image three ways, and builds it for arm64 under emulation | Starts it once                                |
| `deploy-demo.yml` publishes the demo; `release.yml` a tarball        | No deploy, no release                         |

The commands themselves are the same. A test in the template compares
the two workflows, so a script renamed there cannot leave the project workflow
naming the old one.

## Versions

Node comes from `NODE_VERSION` at the top of the workflow, which `add ci` reads
from `.nvmrc`. `scripts/lint/check-toolchain-pins.mjs`, part of `vp run lint`,
fails when the two disagree, in this workflow and in any other that pins
`NODE_VERSION`. To move to another Node, change `.nvmrc`, `.node-version`, the
workflow and the `Dockerfile` in one commit.

Actions are pinned by major version (`actions/checkout@v4`), as the template's
own workflows are. Pinning each to a commit SHA is stricter, and Dependabot's
`github-actions` ecosystem keeps SHA pins current; do it if your organisation
requires it.

## If you did not eject

A project that keeps the demo also keeps the template's workflows:

- **`ci.yml`** runs in your repository without the maintainer steps, which are
  limited to the template's own. It is still the template's pipeline. `vuestrata
add ci --force` replaces it with the one on this page.
- **`release.yml`** publishes a `vuestrata-<tag>.tar.gz` release whenever a `v*`
  tag is pushed. Delete it unless that is what you want a tag to do.
- **`deploy-demo.yml`** deploys a **demo** build to Vercel. Since 1.1.0 it runs
  only in the template's repository. A copy from an earlier release has no such
  condition and deploys the demo to production as soon as a `VERCEL_TOKEN`
  secret exists: delete the file before you store that secret for your own
  application.
