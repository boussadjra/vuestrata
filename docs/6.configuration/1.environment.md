# Environment

## The one variable that decides everything

```
VUESTRATA_RUNTIME_MODE = demo | production
```

Vuestrata builds **two different artifacts** from one codebase, and this is the
switch:

|                          | `demo`                              | `production`                            |
| ------------------------ | ----------------------------------- | --------------------------------------- |
| MSW                      | bundled, intercepts every request   | **not bundled at all**                  |
| Auth                     | mock adapter, IndexedDB             | `jwt` or `oauth` against a real backend |
| Demo account + seed data | present                             | compiled out                            |
| Service worker           | published                           | deleted from `dist/`                    |
| Sourcemaps               | `hidden` (generated, not published) | none                                    |
| Backend required         | no                                  | yes                                     |

It defaults to `demo` in development and `production` in a build.

The mode is applied by two deliberately different mechanisms:

- **`__VUESTRATA_DEMO__`**, a compile-time constant. `if (__VUESTRATA_DEMO__)`
  branches are dead-code-eliminated, which is what makes a production bundle
  genuinely free of demo code rather than merely not calling it.
- **`appConfig`**, parsed when the app loads: API URL, title, theme, icons and
  the rest. Being a runtime value, it cannot remove code the way the constant
  does. Vite inlines every `VUESTRATA_*` value into the bundle, and for most of
  them that is final. Five can be replaced when the app **starts**, without a
  new build — see [Build time and start time](#build-time-and-start-time).

## Variables

Every key uses the `VUESTRATA_` prefix. That prefix **replaces** Vite's default
`VITE_`, so a `VITE_*` variable is never exposed to client code.

| Variable                              | Default                                        | Required          | Decided        | Notes                                                                                                          |
| ------------------------------------- | ---------------------------------------------- | ----------------- | -------------- | -------------------------------------------------------------------------------------------------------------- |
| `VUESTRATA_RUNTIME_MODE`              | `demo` in dev, `production` in a build         | no                | at build       | `demo` \| `production`                                                                                         |
| `VUESTRATA_APP_TITLE`                 | `Vuestrata`                                    | no                | build or start | Document title                                                                                                 |
| `VUESTRATA_API_URL`                   | `/api`                                         | **in production** | build or start | Absolute origin, or a same-origin path behind a proxy                                                          |
| `VUESTRATA_USE_MOCKS`                 | follows the mode                               | no                | at build       | Must agree with the mode                                                                                       |
| `VUESTRATA_MOCK_ONLY`                 | unset                                          | no                | at build       | Module ids, comma-separated: MSW answers for those and your backend for the rest. Demo mode, real adapter only |
| `VUESTRATA_AUTH_ADAPTER`              | `mock` in demo, `jwt` in production            | no                | at build       | `mock` \| `jwt` \| `oauth`, or an adapter registered in `config/auth.config.ts`                                |
| `VUESTRATA_SESSION_PERSISTENCE`       | `none` in demo, `refresh-cookie` in production | no                | build or start | `none` \| `refresh-cookie` \| `session` \| `local`                                                             |
| `VUESTRATA_ICON_PROVIDER`             | `solar`                                        | no                | at build       | `solar` \| `lucide` \| `phosphor` \| `iconoir` \| `tabler` \| `mingcute` \| `remix` \| `griddy` \| `iconamoon` |
| `VUESTRATA_THEME`                     | `default`                                      | no                | at build       | Initial theme for a fresh session                                                                              |
| `VUESTRATA_DEMO_AUTH_RETENTION_HOURS` | `24`                                           | no                | at build       | 1–720. Ignored in production                                                                                   |
| `VUESTRATA_ERROR_REPORTING_DSN`       | unset                                          | no                | build or start | Public write-only ingest URL                                                                                   |
| `VUESTRATA_RELEASE`                   | unset                                          | no                | build or start | Version attached to error reports; CI sets the git SHA                                                         |

## Build time and start time

A value is **decided at build** when Vite inlines it into the bundle and nothing
can change it afterwards. It is decided at **build or start** when the inlined
value is only a default, and a deployment may replace it when the app starts.
That second kind is what lets one build — one Docker image — be promoted from
staging to production unchanged.

### Which keys, and why only those

Five built-in keys can be set at start:

- `VUESTRATA_API_URL`
- `VUESTRATA_APP_TITLE`
- `VUESTRATA_ERROR_REPORTING_DSN`
- `VUESTRATA_RELEASE`
- `VUESTRATA_SESSION_PERSISTENCE`

plus any variable of your own that you list under `runtime` in
`deploy.config.ts` ([Your own variables](#your-own-variables)).

The other seven are fixed at build, and not for convenience. `RUNTIME_MODE`,
`USE_MOCKS`, `MOCK_ONLY` and `AUTH_ADAPTER` decide what is **in** the bundle and
which mocks start: a production build contains no MSW and no mock adapter, and a
value set at start cannot bring back code that was compiled out. `ICON_PROVIDER`,
`THEME` and `DEMO_AUTH_RETENTION_HOURS` stay with them. Setting any of the seven
at start does nothing but log a warning.

### How a start-time value reaches the app

Every page loads `/runtime-config.js` before the app bundle. The file assigns one
object:

```js
window.__VUESTRATA_RUNTIME__ = { VUESTRATA_API_URL: 'https://api.staging.example.com' }
```

It is a plain script rather than a JSON file the app fetches, because the API
client reads its base URL while its module is evaluated. The value has to be
there before the bundle runs, and a request would finish after it.

Who writes the file depends on where the app runs:

- **The Docker image** writes it when the container starts, from the
  container's environment. See
  [Build once, deploy many](../8.deployment/2.real-production#build-once-deploy-many).
- **A static host** serves the copy in `public/runtime-config.js`, which sets
  nothing. To set a value there, write the file in your deploy step.
- **`vp dev` and `vp preview`** serve that same empty copy, so development
  behaves like a build whose deployment set nothing.

### Precedence, and what counts as "not set"

1. A value in `window.__VUESTRATA_RUNTIME__`, for a key that can be set at start.
2. The value inlined at build time.
3. The default in the table above.

In the file, three things mean "not set", and the next source in the list
applies:

- a key that is absent;
- an empty string;
- a placeholder nothing substituted, such as `"${VUESTRATA_API_URL}"`. A host
  that serves the file as a template and has no value for a key leaves the
  placeholder in place, and it must never be read as a URL.

A key outside the list above is ignored with a warning in the console. So is a
value that is not a string.

::alert{type="warning"}
**A start-time value is validated like a build-time one, but it cannot fail a
build.** A value its key does not accept is dropped, with a warning in the
browser console that names the key, and the next source in the list applies:
the value the app was **built** with, and the default only when the build set
none. So an app built with `VUESTRATA_SESSION_PERSISTENCE=none` and started with
`Session` keeps `none`; it does not fall through to `refresh-cookie`. The app
keeps running either way.

The Docker image does not let most such values get that far. Its entrypoint
refuses to start on a session persistence mode that does not exist, or on an API
URL it cannot turn into an origin or a path.
::

One rule differs between the two. A **build** refuses a placeholder host
(`localhost`, `127.0.0.1`, `0.0.0.0`, `api.example.com`) in `VUESTRATA_API_URL`,
because a build that points there was never configured. A value **set at start**
is honoured on those hosts too: whoever passed it to a running container chose
it, and the container's CSP already allows that origin.

### `VUESTRATA_SESSION_PERSISTENCE`

How a session survives a page reload, and which refresh credential the `jwt`
adapter presents for the rest of it.

Access tokens live in memory and always will — persisting one only widens what
an XSS can steal. That leaves a reload with no credential at all, so the app has
to get a new access token from somewhere, and this variable says where.

| Value            | At boot                                                                               | Mid-session refresh (on a 401, and a minute before expiry) | Trade-off                                                                                               |
| ---------------- | ------------------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `none`           | Nothing. The session ends at the reload.                                              | `{ refreshToken }` from memory.                            | Correct for kiosks and shared terminals. Explicit, not accidental.                                      |
| `refresh-cookie` | `POST /auth/refresh`, cookies attached and no body, then `GET /auth/me` for the user. | The same request: the cookie, no body.                     | **Recommended.** No long-lived credential is readable by JavaScript. Needs the backend described below. |
| `session`        | `POST /auth/refresh` with the refresh token read from `sessionStorage`.               | `{ refreshToken }` from memory, else from storage.         | Survives reload, dies with the tab. An XSS can read it.                                                 |
| `local`          | `POST /auth/refresh` with the refresh token read from `localStorage`.                 | `{ refreshToken }` from memory, else from storage.         | Survives a browser restart. Same exposure, longer window.                                               |

`none`, `session` and `local` are the body-token contract: `POST /auth/login`
returns `refreshToken` in the body and `POST /auth/refresh` takes it back as
`{ refreshToken }`. Requests go out with `credentials: 'omit'`, so no cookie is
involved and no CORS credentials setup is needed.

`/auth/refresh` returns tokens and **may omit `user`** in every mode. When it
does, the app calls `GET /auth/me` with `Authorization: Bearer <the new token>`
before it stores anything, so a resumed session always has a user. A refresh
that succeeds while `/auth/me` fails resumes nothing: the visitor lands signed
out.

#### What `refresh-cookie` needs from the backend

Under `refresh-cookie` the app sends `credentials: 'include'` on **every**
`/auth/*` request — login, register, MFA, magic link, `/auth/me`, refresh and
logout — and on nothing else. A browser neither stores a `Set-Cookie` nor sends
a cookie for a request made without it, so the whole family has to agree. The
rest of the API keeps `credentials: 'omit'` and the bearer token.

The backend must:

1. **Set the refresh token as a cookie on every response that starts a
   session** — `POST /auth/login`, `/auth/register`, `/auth/mfa/verify`,
   `/auth/magic-link/verify`:

   ```http
   Set-Cookie: refresh_token=<opaque>; HttpOnly; Secure; SameSite=Lax; Path=/api/auth; Max-Age=1209600
   ```

   The name is yours; the app never reads it. `Path` must cover both
   `/auth/refresh` and `/auth/logout` as the browser sees them. The body is
   `{ user, token, expiresIn }`. Leave `refreshToken` out of it — that is the
   point of the mode.

2. **Read that cookie on `POST /auth/refresh`**, which arrives with no body and
   no `Authorization` header. Answer `{ token, expiresIn }`, and rotate the
   cookie with a new `Set-Cookie` if you rotate refresh tokens. Answer `401`
   when the cookie is missing, expired or revoked: that is how a signed-out
   visitor's boot looks, and how a session ends. The app does not repeat a
   refresh that was answered `401` or `403`.

3. **Read and clear it on `POST /auth/logout`** (`Max-Age=0`), and revoke the
   token server-side.

4. **Say how long the access token lives**: `expiresIn` in seconds, or a JWT
   `exp` claim. The app refreshes one minute before that. With neither, it
   refreshes only after a request has already been answered `401`.

5. **Allow credentialed CORS on the auth routes, when the API is on another
   origin than the app**:

   ```http
   Access-Control-Allow-Origin: https://app.example.com
   Access-Control-Allow-Credentials: true
   Access-Control-Allow-Headers: Authorization, Content-Type
   Vary: Origin
   ```

   The origin must be the exact one; a browser rejects `*` on a credentialed
   request. The headers must be listed for the same reason: there,
   `Access-Control-Allow-Headers: *` means a header named `*`, and the login's
   preflight is refused. Nothing is needed when the API is served from the app's
   own origin (a reverse proxy mounting it at `/api`).

6. **Choose `SameSite` by where the API lives.** `Lax` or `Strict` works when
   the app and the API share a site — the same origin, or sibling subdomains
   such as `app.example.com` and `api.example.com`. Different sites need
   `SameSite=None; Secure`, which browsers that block third-party cookies will
   refuse to store, and reloads then sign the user out again. Serve the API from
   the app's site instead. With `SameSite=None`, also check the `Origin` header
   on `/auth/refresh` and `/auth/logout`: the cookie is an ambient credential on
   those two routes.

**If your backend sets no cookie**, choose `none`, `session` or `local` rather
than leaving the default in place. Under `refresh-cookie`:

- A reload signs the user out: the boot request has no cookie to present.
- When the login body carries a `refreshToken`, the app still holds it in memory
  (it is never written anywhere) and sends it back as `{ refreshToken }` on a
  mid-session refresh, so the session lasts until the reload. Without one, the
  session ends when the access token does.
- When the API is on another origin and answers
  `Access-Control-Allow-Origin: *`, the browser refuses every `/auth/*`
  response, the login included: a credentialed request needs the exact origin
  and `Access-Control-Allow-Credentials: true`.

Only the **refresh** token is ever written, never the access token. Logout and
`clearAuth()` clear both storage areas regardless of the configured mode, so
changing this setting cannot strand a live token in an existing user's browser.

The `oauth` adapter has no use for it: it uses cookie transport, so the browser
already holds the session and the app resumes from `/auth/me` unconditionally.
The build therefore rejects any value but `none` alongside `oauth` — and since
the production default is `refresh-cookie`, an `oauth` build must set
`VUESTRATA_SESSION_PERSISTENCE=none` explicitly. Demo mode must use `none` too;
it restores from IndexedDB.

::alert{type="warning"}
**Every one of these values reaches the browser and is therefore public** —
inlined into the bundle, or served in `/runtime-config.js`. A DSN is designed
for that — it is a write-only ingest endpoint. A provider _API token_ is a
secret and must never appear in a `VUESTRATA_` variable. If a value must stay
private, it belongs on your backend.
::

## Validation runs twice, on purpose

The schema lives in `src/modules/core/lib/config/env.schema.ts` and is imported
by both `vite.config.ts` (Node, before aliases resolve) and the app. It is
dependency-free for that reason.

**At build time — strict.** An invalid combination fails `vpr build` with a
message naming the offending key. This is the right place to fail: a
misconfiguration caught in CI costs a red build; the same one caught in the
browser costs a white screen.

**In the browser — lenient.** The same rules warn and fall back rather than
throwing. `app.config.ts` used to throw at module-eval time in production, which
turned a single bad variable into a blank page with nothing in the console. This
is also the only validation a value set at start gets from the app, which is why
it has to be the forgiving one.

A container adds a check of its own before either: its entrypoint refuses to
start on a value that holds anything but URL-safe characters (a title may also
hold spaces), and on a session persistence mode that is not one of the four.
That check is about injection first and meaning second, and is described with
[the image](../8.deployment/2.real-production#what-a-container-may-be-started-with).

### The combination rules

These are what a per-key schema cannot express, and each one closes a way to
ship something broken:

- `demo` ⇒ `USE_MOCKS=true` **and** `AUTH_ADAPTER=mock`. A demo with mocks off
  has no backend to talk to; a demo with a real adapter cannot sign anyone in.
- `demo` ⇒ `SESSION_PERSISTENCE=none`. The demo restores its session from
  IndexedDB; outside MSW there is no refresh endpoint to call.
- `MOCK_ONLY` is the one exception to those two, and it comes with its own
  rules. It lists the modules MSW answers for while a real backend answers for
  everything else, so it needs `demo` mode (MSW has to be in the bundle), mocks
  on, and a **real** adapter; it may not name `auth`, because the mock sign-in
  endpoints and a real adapter cannot both own `/auth/*`; and it is refused
  outright in `production` mode, where a build with it set fails. The session
  persistence and the API URL are then held to the production rules below, since
  that half of the app is real. The whole table is in
  [Develop Against Your Backend](/docs/getting-started/develop-against-your-backend#what-is-valid).
- `production` ⇒ `USE_MOCKS=false`. MSW is not in the bundle, so asking for it
  produces a request to a worker that will never register.
- `AUTH_ADAPTER=mock` outside demo mode is a **hard error**. The mock adapter's
  endpoints exist only inside MSW; a "production" build using it authenticates
  against nothing.
- `AUTH_ADAPTER=oauth` ⇒ `SESSION_PERSISTENCE=none`. Cookie transport resumes
  from its session cookie; a bearer strategy beside it would write a refresh
  token to Web Storage for an adapter that never receives one. The rule follows
  the transport, so it holds for an adapter of your own registered as
  `transport: 'cookie'`.
- `AUTH_ADAPTER` must be a built-in name or one registered under `adapters` in
  `src/modules/app/config/auth.config.ts`. Anything else is a **hard error**
  that names that file. It is never replaced by `mock`; in the browser the
  fallback is the mode's default. The build reads the registered names from the
  file's text, without running it; see
  [Write your own auth adapter](../9.recipes/10.write-your-own-auth-adapter#how-the-build-reads-the-adapter-names).
- `production` ⇒ `API_URL` must not be a placeholder. `localhost`,
  `api.example.com` and friends are rejected by a build, because a build that
  silently points at `example.com` deploys successfully and then fails one
  request at a time. `vp dev` accepts them, so you can develop against a backend
  on your own machine, and so does a container
  [started with one](#precedence-and-what-counts-as-not-set).
- `API_URL` must be an absolute `http(s)` URL or a same-origin path with a
  single leading `/`. `//host/path` and `/\host/path` are refused everywhere: a
  browser reads both as another host.

One thing no rule can check: an `http://` API URL only works while the app
itself is served over `http://`. From an `https://` page a browser blocks it as
mixed content, whatever the CSP says, and the build cannot know how the app
will be served.

## Your own variables

A project has configuration of its own: a feature flag, a map key, the URL of a
second service. Declare it in `src/modules/app/config/deploy.config.ts`, a file
Vuestrata writes once and never touches again, and it gets the treatment the
built-in variables get.

```ts
import { z } from 'zod'

import { defineDeployConfig } from '~/lib/config/deploy'

export default defineDeployConfig({
  env: {
    VUESTRATA_FEATURE_BILLING: z.enum(['on', 'off']).default('off'),
    VUESTRATA_SUPABASE_URL: z.url().optional(),
  },
  // The ones a deployment may set at start, like VUESTRATA_API_URL.
  runtime: ['VUESTRATA_SUPABASE_URL'],
})
```

Read them, typed from the schemas, through `appEnv`:

```ts
import { appEnv } from '~/bootstrap/app-env'

appEnv.VUESTRATA_FEATURE_BILLING // 'on' | 'off'
appEnv.VUESTRATA_SUPABASE_URL // string | undefined
```

The rules:

- **A name starts with `VUESTRATA_`**, followed by capitals, digits and
  underscores. No other prefix reaches the browser. A built-in name cannot be
  declared again.
- **Each schema is given the raw string**, or `undefined` when the variable is
  unset or empty. Use `z.coerce` for a number, `.default()` for a fallback.
- **The build is strict.** An invalid value fails `vpr build` and `vpr dev`,
  naming the variable. So does a missing one whose schema requires it.
- **The browser is lenient.** A bad value that arrives at start is dropped with
  a warning, and the value the app was built with applies; when the build set
  none, the schema's default, or `undefined`.
- **A variable under `runtime` may be absent from the build**, even when its
  schema requires it: the build cannot know what a container will be started
  with. Give such a variable a default or make it optional, because nothing
  guarantees that an environment sets it.
- **A test run is not held to any of this.** Vitest starts without the variables
  of a deployment, and `appEnv` holds the defaults.

After changing `runtime`, run `vpr security:headers` and commit the result: the
list of names the container may set is generated from it. `deploy.config.ts`
also holds what your security headers allow; that half is covered in
[Real production](../8.deployment/2.real-production#security-headers). And it
holds the size budgets your bundle is checked against:
[Your own budgets](#your-own-budgets), below.

The file may import `zod` and nothing else by value. The header generator loads
it in Node, where nothing of the app exists.

## The four configurations

### 1. Local development

No configuration at all — `vpr dev` defaults to demo mode.

```bash
vpr dev
```

To develop against your own API instead, see [Develop Against Your Backend](/docs/getting-started/develop-against-your-backend).

### 2. Public demo

```bash
VUESTRATA_RUNTIME_MODE=demo
VUESTRATA_USE_MOCKS=true
VUESTRATA_AUTH_ADAPTER=mock
```

See [Vercel demo deployment](../8.deployment/1.vercel-demo).

### 3. Preview / staging against a real backend

Identical to production, pointed at your staging origin. Deliberately _not_ a
third mode: a staging build that differs from production is a staging build that
proves nothing.

```bash
VUESTRATA_RUNTIME_MODE=production
VUESTRATA_USE_MOCKS=false
VUESTRATA_AUTH_ADAPTER=jwt
VUESTRATA_API_URL=https://staging-api.yourcompany.com
```

With the Docker image it can be the very same build: start the production image
with `-e VUESTRATA_API_URL=https://staging-api.yourcompany.com`. The mode and
the adapter stay as built, which is the point.

A staging environment that is **ahead of its backend** is a different thing: a
demo build with a real adapter and `VUESTRATA_MOCK_ONLY` naming the modules the
backend does not have yet. It contains MSW, so it is not the build you promote.
See [Mock only what the backend has not built yet](/docs/getting-started/develop-against-your-backend#mock-only-what-the-backend-has-not-built-yet).

### 4. Real production

```bash
VUESTRATA_RUNTIME_MODE=production
VUESTRATA_USE_MOCKS=false
VUESTRATA_AUTH_ADAPTER=jwt          # or oauth, with VUESTRATA_SESSION_PERSISTENCE=none
VUESTRATA_API_URL=https://api.yourcompany.com
VUESTRATA_RELEASE=$GIT_SHA
```

See [Real production deployment](../8.deployment/2.real-production).

## Verifying the artifact

Type-checking cannot see what ended up in a bundle, so this is checked
mechanically:

```bash
VUESTRATA_RUNTIME_MODE=production \
VUESTRATA_USE_MOCKS=false \
VUESTRATA_AUTH_ADAPTER=jwt \
VUESTRATA_API_URL=https://api.yourcompany.com \
  vpr build

node scripts/build/verify-bundle.mjs --mode=production
```

It asserts that the build exists and that it has no MSW chunk, no reference to
one, no service worker, no demo IndexedDB store, no demo salt, no demo account
address and no published sourcemaps. Every chunk is searched, the in-app docs
included: they ship in a production build too. For both modes it also checks
that `runtime-config.js` is in the build and that `index.html` loads it as a
separate script before the app, that the scripts `index.html` names are in the
build, that no chunk a page fetches on demand is loaded with the page, and the
four size budgets. Both modes are verified in CI.

### Your own budgets

The budgets are measured on this template: 560 KB gzipped for everything the
page loads before it renders, 400 KB for the largest chunk among those files,
700 KB for the largest stylesheet among them, and 7 MiB of JavaScript in all.
Your modules add to the first, and an app that draws a chart on every page
loads the charting engine with the page on purpose.

Say so in `src/modules/app/config/deploy.config.ts`, under `bundle`. Do not edit
`scripts/build/verify-bundle.mjs`: it is Vuestrata's file, an edited copy is
held back by every upgrade, and you would stop receiving its checks.

```ts
export default defineDeployConfig({
  bundle: {
    // Sizes in KB. Set only the ones that differ.
    initialPayloadGzipKb: 620,
    largestEagerChunkKb: 450,
    largestEagerStylesheetKb: 760,
    totalJsKb: 8192,

    onDemandChunks: {
      // A vendor group of your own that pages fetch with import(): the `name`
      // of its group in vite.config.ts. Loading it with the page then fails.
      add: ['maps-vendor'],
      // A chunk from the default list (ON_DEMAND_CHUNKS in the script) that
      // this app loads with every page by design.
      remove: ['charts-vendor'],
    },
  },
})
```

Every run prints what you changed beside the default, so a raised budget stays
visible in the CI log and in review:

```text
initial payload budget 620.0 KB (default 560.0 KB, from deploy.config.ts)
on-demand chunk charts-vendor is not checked (removed in deploy.config.ts)
```

A value that is not a size above 0, an option that does not exist and a chunk
to remove that the check does not look for all fail the run, naming the key. A
project without the file, or one whose file cannot be loaded, is checked
against the defaults, and the run says so in one line.

The app never reads `bundle`: it is build tooling's, and adds nothing to what
the browser downloads beyond the few numbers you write there.

## App configuration

`appConfig` is the parsed, validated result — import it rather than reading
`import.meta.env` directly, so every consumer sees the same defaults and
coercions. It is also the only one of the two that knows what was set at start:
`import.meta.env.VUESTRATA_API_URL` is whatever the build inlined, whatever the
container was started with.

```ts
import { appConfig } from '@/config/app.config'

appConfig.apiUrl // string, never undefined
appConfig.authAdapter // 'mock' | 'jwt' | 'oauth'
appConfig.runtimeMode // 'demo' | 'production'
```

## MSW mock handlers

In demo builds, [MSW](https://mswjs.io/) intercepts every request. Handlers come
from two places:

- App-level: `src/modules/app/mocks/handlers/` — dashboard, users, billing, audit
- Module-owned: each module's `mockHandlers` factory, which **must** be a
  dynamic `import()` behind `__VUESTRATA_DEMO__`. See
  [Creating a module](../3.modules/2.creating-a-module).

## Docker

Build arguments set what is decided at build, and the defaults for the rest:

```bash
docker build \
  --build-arg VUESTRATA_RUNTIME_MODE=production \
  --build-arg VUESTRATA_AUTH_ADAPTER=jwt \
  -t vuestrata .
```

What differs per environment is given to the container, not to the build:

```bash
docker run -p 8080:8080 \
  -e VUESTRATA_API_URL=https://api.yourcompany.com \
  -e VUESTRATA_RELEASE=$GIT_SHA \
  vuestrata
```

`--build-arg VUESTRATA_API_URL=…` still works, and becomes the value a container
uses when it is started with none, or with an empty one.

With Compose, the container's values go in `docker.env` (copy
`docker.env.example`), never in `.env`: that file is Vite's, for development,
and `docker-compose.yml` does not read the container's environment from it.
[Build once, deploy many](../8.deployment/2.real-production#build-once-deploy-many)
has the full list and a Kubernetes example.

The image strips `*.map` after building, so sourcemaps cannot be served even if
the reverse proxy would have allowed it.
