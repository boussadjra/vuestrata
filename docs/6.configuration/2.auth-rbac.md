# Auth & RBAC

## Authentication

Vuestrata supports multiple auth strategies through the adapter pattern:

```ts
import { useAuth } from '~/modules/auth'

const { login, register, socialLogin, logout, sendMagicLink, verifyMagicLink } = useAuth()
```

What is described below is the contract the app speaks as shipped. A backend
that differs — other paths, other field names, a differently shaped user, an
SDK — is described in `src/modules/app/config/auth.config.ts`, a file that is
yours. See [Configuring it for your backend](#configuring-it-for-your-backend).

### Credential Login

```ts
await login({ email: 'admin@example.com', password: 'password' })
```

### Social Login

```ts
// Google, GitHub or Microsoft as shipped; any id listed under `providers`
// in auth.config.ts otherwise.
await socialLogin('google')
```

### Magic Link

```ts
await sendMagicLink('user@example.com')
// User clicks link in email...
await verifyMagicLink(token)
```

### Auth Adapter Selection

Set via environment variable:

```bash
VUESTRATA_AUTH_ADAPTER=mock   # Development (MSW mocks)
VUESTRATA_AUTH_ADAPTER=jwt    # JWT-based auth
VUESTRATA_AUTH_ADAPTER=oauth  # OAuth 2.0
VUESTRATA_AUTH_ADAPTER=session  # your backend's own session cookie (Sanctum, Django, Rails…)
VUESTRATA_AUTH_ADAPTER=sdk    # an adapter you registered in auth.config.ts
```

`mock` is only valid when `VUESTRATA_RUNTIME_MODE=demo` — its endpoints exist
only inside MSW, so the env schema rejects the combination at build time, and
the adapter itself is not in a production bundle.

A name that is neither built in nor registered **fails the build**, with a
message naming `auth.config.ts`. It is never replaced by `mock`.

### Transport

Every adapter declares how it proves identity. This drives the API client:

| Transport | `Authorization: Bearer` | Cookies sent    | `X-CSRF-Token` |
| --------- | ----------------------- | --------------- | -------------- |
| `bearer`  | yes                     | no (`omit`)     | no             |
| `cookie`  | no                      | yes (`include`) | on mutations   |

The two are mutually exclusive by design. The client previously sent a bearer
header **and** ambient cookies on every request regardless of adapter, which
means a bearer API received credentials it never asked for, and a cookie API
received a header that could bypass its CSRF assumptions.

CSRF only applies to the cookie transport: with bearer tokens there is no
ambient credential for a third-party page to ride on.

One exception to the `bearer` row, and only on `/auth/*`: under
`VUESTRATA_SESSION_PERSISTENCE=refresh-cookie` the `jwt` adapter sends
`credentials: 'include'` on its auth requests, because that is the only way a
browser stores the refresh cookie at login and presents it on refresh and
logout. Every other request stays `omit`. See
[Environment](1.environment#what-refresh-cookie-needs-from-the-backend).

### Adapters

| Adapter   | Transport | Purpose                                                                                                                                                                                               |
| --------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `mock`    | `bearer`  | Demo builds only. MSW-backed; mints an unsigned JWT so the demo exercises the same header path a real bearer backend would.                                                                           |
| `jwt`     | `bearer`  | Credentials + access/refresh tokens. Refreshes with the credential `VUESTRATA_SESSION_PERSISTENCE` selects: an HttpOnly cookie, or a refresh token held by the app.                                   |
| `oauth`   | `cookie`  | Authorization code + PKCE against a backend-for-frontend that completes the exchange server-side and issues an HttpOnly session cookie, so no token reaches JavaScript.                               |
| `session` | `cookie`  | Credentials against a backend that keeps a server session in an HttpOnly cookie and expects a CSRF token: Laravel Sanctum, Django, Rails, Spring Security, ASP.NET cookie auth. No token, no refresh. |

One more kind is yours: an adapter registered under `adapters` in
`auth.config.ts`, with the transport it declares there. That is how an SDK that
keeps its own session goes behind the same contract; see
[Write your own auth adapter](../9.recipes/10.write-your-own-auth-adapter).
Most backends do not need one: `jwt`, `oauth` and `session` are configured, not
replaced.

### Cookie sessions

A backend that signs users in with its own session cookie needs two lines of
configuration and no adapter of yours. For Laravel with Sanctum:

```bash
VUESTRATA_AUTH_ADAPTER=session
VUESTRATA_SESSION_PERSISTENCE=none
```

```ts
// src/modules/app/config/auth.config.ts
export default defineAuthConfig({ endpoints: endpointPresets.sanctum })

// src/modules/app/config/api.overrides.ts
export default defineApiOverrides({ backend: presets.laravel })
```

Signing in fetches a CSRF token, posts the credentials (a `204` is an answer),
then asks who that is. Nothing is held in JavaScript, a reload resumes from the
cookie, and a session that ends sends the visitor to sign in again with the way
back. A route the backend serves beside its API rather than under it is written
`{ path: '/login', base: 'origin' }`. What the cookies and CORS have to look
like, other backends, and what happens when the session ends are in
[Cookie sessions](3.auth-deep-dive#cookie-sessions-the-session-adapter).

### Capabilities

Only `login`, `logout` and `getUser` are required. Everything else is optional
and declared through `capabilities`, so the UI can hide an affordance the
configured adapter cannot honour rather than letting a user discover it at
click time.

| Capability     | `mock` | `jwt` | `oauth` | `session` | Notes                                       |
| -------------- | ------ | ----- | ------- | --------- | ------------------------------------------- |
| `register`     | ✅     | ✅    | ❌      | ✅        | OAuth registration happens at the provider. |
| `social`       | ✅     | ❌    | ✅      | ❌        | Redirect flow; use the `oauth` adapter.     |
| `magicLink`    | ✅     | ✅    | ❌      | ✅        |                                             |
| `mfa`          | ✅     | ✅    | ❌      | ✅        | OAuth MFA is enforced by the provider.      |
| `refresh`      | ✅     | ✅    | ❌      | ❌        | Cookie sessions are renewed server-side.    |
| `codeExchange` | ✅     | ❌    | ✅      | ❌        | The `/auth/callback` step.                  |

The table is what the adapters can do against the full contract. Under
`endpointPresets.sanctum` the `session` adapter offers `register` alone:
Sanctum has no magic-link or MFA route, and the preset switches them off. A project
narrows it from `auth.config.ts`: an endpoint set to `null` takes its
capability with it, and `capabilities: { mfa: false }` disclaims one outright.
Either way the adapter drops the method as well as the flag, and the login and
register pages hide what is gone.

Bind UI to `useAuth().capabilities`, and use `requireCapability()` before
invoking an optional method — it throws an error naming both the adapter and
the missing capability, rather than "not a function".

```ts
const { capabilities, sendMagicLink } = useAuth()
// <UiButton v-if="capabilities.magicLink" @click="…">
```

### Backend endpoints

All paths are relative to `VUESTRATA_API_URL`. These are the defaults
(`endpointPresets.vuestrata`); each path, method and response shape can be
changed, and each endpoint switched off, from `auth.config.ts`.

| Endpoint                  | Method | Used by            | Response                                                                    |
| ------------------------- | ------ | ------------------ | --------------------------------------------------------------------------- |
| `/auth/login`             | POST   | mock, jwt, session | `{ user, token, refreshToken, expiresIn }`; `session`: `204`, or `{ user }` |
| `/auth/register`          | POST   | mock, jwt, session | same as login                                                               |
| `/auth/logout`            | POST   | all                | `204`                                                                       |
| `/auth/me`                | GET    | all                | `User`                                                                      |
| `/auth/refresh`           | POST   | mock, jwt          | `{ token, refreshToken, expiresIn }`                                        |
| `/auth/magic-link`        | POST   | mock, jwt          | `{ message }`                                                               |
| `/auth/magic-link/verify` | POST   | mock, jwt          | same as login                                                               |
| `/auth/mfa/setup`         | POST   | mock, jwt          | `{ secret, qrCodeUrl, backupCodes }`                                        |
| `/auth/mfa/verify`        | POST   | mock, jwt          | same as login                                                               |
| `/auth/mfa/disable`       | POST   | mock, jwt          | `{ message }`                                                               |
| `/auth/authorize`         | GET    | oauth              | `302` to the provider                                                       |
| `/auth/:provider`         | GET    | oauth              | `302` to the provider                                                       |
| `/auth/token`             | POST   | oauth, mock        | same as login                                                               |

A login response may instead return `{ mfaRequired: true, mfaToken }`, which
puts the flow into the MFA challenge state.

`/auth/refresh` carries no `user`. When a reload resumes a session from it, the
app follows with `GET /auth/me`, sending the new token, and stores nothing until
that answers. A backend may include `user` in the refresh response to save the
round trip. Under `refresh-cookie` the request has no body and `refreshToken` is
absent from every response: the credential travels as an HttpOnly cookie.
`expiresIn` is in seconds; the app refreshes a minute before the token runs out,
reading the lifetime from a JWT's own `exp` claim when the token has one and
from `expiresIn` otherwise.

The `oauth` adapter sends the browser to `/auth/authorize` or `/auth/:provider`
with `response_type=code`, `state`, `code_challenge`,
`code_challenge_method=S256` and `redirect_uri` (the app's `/auth/callback`).
On the way back it checks `state` itself and then posts
`{ grant_type: 'authorization_code', code, code_verifier, redirect_uri }` to
`/auth/token`; `state` never reaches the backend. Request bodies for every
endpoint are in [Real production](../8.deployment/2.real-production).

Every `User` these endpoints return is **validated** before the app keeps it:
`id` and `email` are required, `role` and `name` are strings when present, and
`permissions` is an array of strings when present. A numeric `id` becomes a
string, `null` on an optional field reads as absent, and fields the app does
not know are kept. A user with no `name` is shown by their email. A user with
no `role` is treated as `guest` for role checks and holds no permission at
all, which is what the app has always done with one. A user may also carry
`roles`, a list of role names, beside `role` or instead of it; see
[What a user holds](#what-a-user-holds). Anything else — no `id`,
an array for a `role`, `permissions` that is not a list of strings — fails the
request with a `CONTRACT_MISMATCH` error that names the fields, the same way a
domain response that breaks its schema does. A login that returns tokens and no
`user` is followed by `GET /auth/me` with the new token; under bearer transport
a login that returns no `token` is refused the same way, unless it is an MFA
challenge.

### Configuring it for your backend

`src/modules/app/config/auth.config.ts` is where a backend that is not the one
above is described. It ships empty, `vuestrata upgrade` never rewrites it, and
nothing under `src/modules/auth/adapters/` is edited to integrate a backend.

```ts
import { authRefreshBodies, authResponseMappers, defineAuthConfig } from '~/lib/auth'

export default defineAuthConfig({
  // Where each request goes. null: this backend has no such endpoint.
  endpoints: { login: '/v1/session', me: '/users/me', magicLink: null, magicLinkVerify: null },
  // { access_token, refresh_token, expires_in } → the app's names.
  mapAuthResponse: authResponseMappers.snakeCase,
  buildRefreshBody: authRefreshBodies.snakeCase,
  // Your user record → User. The result is validated.
  mapUser: (raw) => {
    const user = raw as { id: number; email: string; full_name: string; role: string }
    return { id: user.id, email: user.email, name: user.full_name, role: user.role }
  },
})
```

| Key                  | What it changes                                                                      |
| -------------------- | ------------------------------------------------------------------------------------ |
| `endpoints`          | Path and method of each request; `null` switches one off, and its capability with it |
| `mapAuthResponse`    | How a login, registration, magic-link, MFA or code-exchange response is read         |
| `mapRefreshResponse` | The same for a refresh. Defaults to `mapAuthResponse`                                |
| `buildRefreshBody`   | The body of a refresh that presents a token. Defaults to `{ refreshToken }`          |
| `mapUser`            | Your user record → `User`, applied wherever a user enters the app                    |
| `capabilities`       | Capabilities the built-in adapters should not claim                                  |
| `providers`          | The social sign-in buttons, and the provider ids `socialLogin` accepts               |
| `adapters`           | Adapters of your own, selected by name with `VUESTRATA_AUTH_ADAPTER`                 |

The refresh goes through the adapter in both directions — the 401 path and the
proactive timer — so a custom body and response shape work mid-session, not only
at login. Every auth request keeps the two things the default ones have,
wherever you point it: it is exempt from the 401 refresh (a 401 from a login is
its answer), and under `refresh-cookie` it is sent with credentials.

The mock adapter ignores all of it. Its backend is the demo's service worker,
which serves the contract above, so a project can describe its real backend and
still run the demo.

[Write your own auth adapter](../9.recipes/10.write-your-own-auth-adapter) works
through two cases in full: a REST backend integrated with `endpoints` and
mappers alone, and an SDK that owns the session.

## RBAC System

### Roles

6 built-in hierarchical roles (highest to lowest). A project adds its own
beside them in `src/modules/app/config/rbac.overrides.ts`, each with the roles
it inherits from, and never by editing `core/lib/rbac/`:
[Add a permission or a role](../9.recipes/7.add-a-permission#add-a-role).

| Role          | Description                      |
| ------------- | -------------------------------- |
| `super_admin` | Full access to everything        |
| `admin`       | Full access except system config |
| `manager`     | Team and content management      |
| `member`      | Standard user access             |
| `viewer`      | Read-only access                 |
| `guest`       | Minimal, unauthenticated access  |

### Permissions

16 built-in granular permissions. Modules can register additional permissions at runtime via the permission registry.

| Permission         | Description           |
| ------------------ | --------------------- |
| `users:read`       | View user list        |
| `users:create`     | Create users          |
| `users:update`     | Edit users            |
| `users:delete`     | Delete users          |
| `roles:read`       | View roles            |
| `roles:assign`     | Assign roles          |
| `billing:read`     | View billing data     |
| `billing:manage`   | Manage subscriptions  |
| `dashboard:read`   | View dashboard        |
| `dashboard:export` | Export dashboard data |
| `settings:read`    | View settings         |
| `settings:update`  | Update settings       |
| `reports:read`     | View reports          |
| `reports:create`   | Create reports        |
| `reports:export`   | Export reports        |
| `audit:read`       | View audit logs       |

### Permission Registry

Modules register domain-specific permissions at initialization. The registry is seeded with the 16 built-in permissions and extended by modules:

```ts
import { registerPermissions, getRegisteredPermissions, isRegisteredPermission } from '~/lib/rbac'

// Register module permissions (called automatically during module init)
registerPermissions('catalog', ['read', 'create', 'update', 'delete'])

// Check registered permissions
isRegisteredPermission('catalog:read') // true
getRegisteredPermissions() // Set with all built-in + dynamic permissions
```

Registration is idempotent — registering the same permission twice is a no-op. HMR-safe.

### Role Inheritance

Roles use delta-based inheritance. Each role defines only the permissions it adds beyond its parent:

```
guest       → dashboard:read
viewer      → + reports:read
member      → + users:read, settings:read
manager     → + users:create, users:update, roles:read, billing:read, dashboard:export,
                reports:create, reports:export
admin       → + roles:assign, billing:manage, settings:update, audit:read
super_admin → + users:delete
```

`getRolePermissions(role)` resolves the full inherited set automatically. A
role of the project's own has no delta: it holds what the roles it `inherits`
from hold, plus its `grants`.

`getRoleDefinitions()` lists every role, built-in and the project's, for a
picker or a legend (`getAssignableRoles()` for the ones a picker offers).
`ROLE_DEFINITIONS` holds the built-in six only.

### What a user holds

One rule decides it, `resolveSubjectPermissions(user)` in
`core/lib/rbac/identity.ts`:

| `/auth/me` returns              | The user holds                                              |
| ------------------------------- | ----------------------------------------------------------- |
| `permissions: [...]`            | Exactly that list. The role adds nothing to it.             |
| `permissions: []`               | Nothing.                                                    |
| a `role` and no `permissions`   | What the role grants, through the hierarchy and its grants. |
| `roles: [...]`, no permissions  | The union of what each of those roles grants.               |
| an unknown role, no permissions | Nothing.                                                    |
| nobody signed in                | Nothing.                                                    |

A user may hold several roles: `roles`, a list of role names, beside `role` or
instead of it. `role` stays the primary one, for display and for code written
for one role; when only `roles` came it is the first of them that no other
inherits from. A role name the app does not declare (a new role at the identity
provider, a typo) is dropped, never treated as a role, and logged once in
development. An explicit `permissions` list still wins over any number of
roles, and loses what the project listed under `withdrawn`.

The route guard, `useRbac()`, the sidebar and the auth store's
`userPermissions` all resolve through it, so a link the UI shows is a route the
guard opens. A backend can therefore describe a user by role alone and leave
the permission table to the frontend, or send the explicit list and own it.

### Using RBAC in Components

```ts
import { useRbac } from '~/composables/useRbac'

const { can, canAny, canAll, canNamespace, isAtLeast } = useRbac()

// Check a single permission
if (can('users:create')) {
  /* ... */
}

// Check any of multiple permissions
if (canAny(['reports:read', 'dashboard:read'])) {
  /* ... */
}

// Check all permissions
if (canAll(['users:read', 'users:update'])) {
  /* ... */
}

// Check role hierarchy: true when ANY role the user holds is a manager,
// or inherits from it
if (isAtLeast('manager')) {
  /* ... */
}
```

`useRbac()` also returns `roles` (every role the user holds that the app
declares) and `hasRole(role)` (whether the user was given exactly that role).

#### Roles from an identity provider

A backend that passes on its identity provider's claims (Keycloak's
`realm_access.roles`, Auth0's `permissions`, Entra's `roles` and `groups`) maps
them to the app's roles in `auth.config.ts`, with the identity mappers in
`~/lib/rbac/identity-mappers`:
[Roles from an identity provider](../9.recipes/7.add-a-permission#roles-from-an-identity-provider).
They drop every name the app does not declare. What they return decides what
the interface shows; the backend must enforce each role and permission itself.

#### Dependency Injection

`useRbac` supports three-tier user source resolution:

1. **Explicit parameter** — pass an `RbacUserSource` directly (best for testing):

```ts
import { ref } from 'vue'
import { useRbac } from '~/composables/useRbac'

const { can } = useRbac({
  role: ref('admin'),
  permissions: ref(['users:read', 'dashboard:read']),
})
```

2. **provide/inject** — provide `RBAC_USER_SOURCE_KEY` from a parent component
3. **Auth store fallback** — reads from `useAuthStore()` (default behavior),
   resolving the signed-in user through `resolveSubjectPermissions`

#### Namespace Checks

Gate entire UI sections by domain:

```ts
const { canNamespace } = useRbac()

if (canNamespace('billing')) {
  /* user has any billing:* permission */
}
```

#### Resource-Scoped Predicates

Register ownership-aware permission checks:

```ts
import { registerPredicate } from '~/lib/rbac'

// Register a predicate for a permission
registerPredicate('users:update', (ctx) => ctx.ownerId === ctx.currentUserId)

// Use in components with context
const { can } = useRbac()
if (can('users:update', { ownerId: profile.userId, currentUserId: auth.user.id })) {
  /* ... */
}
```

When no predicate is registered or no context is provided, the check falls back to the standard role-based behavior.

#### Authorization Event Hooks

Subscribe to authorization decisions for audit logging and analytics:

```ts
import { onAuthorizationCheck } from '~/lib/rbac'

const unsubscribe = onAuthorizationCheck(({ permission, granted, userRole, source, context }) => {
  if (!granted) analytics.track('access_denied', { permission, userRole })
})

// Later: unsubscribe when done
unsubscribe()
```

Hooks are synchronous, failure-isolated (a throwing hook does not affect others), and support multiple subscribers.

### Route Guards

Routes can require auth, roles, and permissions via `meta`:

```yaml
# In a <route lang="yaml"> block (file-based routing)
meta:
  requiresAuth: true
  requiredRole: manager
  requiredPermission: users:read
```

Or programmatically:

```ts
{
  path: '/admin/users',
  meta: {
    requiresAuth: true,
    requiredRole: 'admin',
    requiredPermission: 'users:read',
  },
}
```

#### Multi-Permission Guards

Routes support multiple permissions with AND/OR semantics:

```ts
{
  path: '/admin/billing',
  meta: {
    requiresAuth: true,
    requiredPermissions: ['billing:read', 'billing:manage'],
    permissionMode: 'all', // 'all' (default) | 'any'
  },
}
```

When both `requiredPermission` (singular) and `requiredPermissions` (array) are set, the array takes precedence.

#### Resource-Scoped Route Guards

Routes support context-aware permission predicates via `permissionContext`:

```ts
{
  path: '/users/:id/edit',
  meta: {
    requiresAuth: true,
    requiredPermission: 'users:update',
    permissionContext: (to) => ({ ownerId: to.params.id }),
  },
}
```

When no context is configured the check proceeds without one. When the resolver
**throws**, the guard fails closed and redirects to `/403` — it does not fall
back to the base role check. A resolver that throws cannot be trusted to supply
the data a predicate needs, and proceeding on the role check alone is exactly
the escalation the context exists to prevent.

The guard logic lives in `src/modules/app/plugins/route-guard.ts` as a pure
`resolveRouteAccess()` function so it can be tested without booting a router;
`router.ts` only translates its decision into a navigation.

**Role and permission checks apply to anonymous visitors too.** They used to be
nested inside an `isAuthenticated` branch, so a route declaring
`requiredPermission` without `requiresAuth: true` was open to anyone not signed
in — it failed _open_ for precisely the visitors it was meant to stop. An
anonymous visitor now evaluates as `guest` (empty permission set) and is sent to
`/403`. Declaring `requiresAuth: true` is still preferred, because it produces a
friendlier login redirect that preserves the destination.

### Sidebar Gating

Sidebar navigation items are shown/hidden based on permissions:

```vue
<template>
  <nav>
    <a v-for="item in filteredItems" v-show="can(item.permission)" :href="item.to">
      {{ item.label }}
    </a>
  </nav>
</template>
```

## CSRF Protection

### Overview

Vuestrata includes built-in CSRF (Cross-Site Request Forgery) protection for all state-changing API requests. The frontend reads a CSRF token from a `<meta>` tag and attaches it as a header on every mutating request.

The meta tag is the default, and it needs a backend that renders `index.html`. A backend that hands the token over in a cookie instead — Laravel Sanctum, Django, Spring Security — is described in `src/modules/app/config/api.overrides.ts` with a CSRF strategy: which cookie to read, which header to send it in, and where to fetch a first token. See [Connect Your Backend API](/docs/recipes/connect-your-backend-api).

### How It Works

1. The backend renders a `<meta name="csrf-token">` tag in `index.html` with a per-session token.
2. The API client (`src/modules/core/lib/api/client.ts`) reads this token and attaches it as the `X-CSRF-Token` header on all `POST`, `PUT`, `PATCH`, and `DELETE` requests.
3. The backend validates the token on every mutating endpoint.

### Frontend Configuration

The API client automatically includes the CSRF token — no manual setup is required:

```ts
// src/modules/core/lib/api/client.ts (already configured)
const csrfToken = document.querySelector('meta[name="csrf-token"]')?.getAttribute('content')

// All mutating requests include X-CSRF-Token automatically
```

### Backend Requirements

Your backend must:

1. **Generate a per-session CSRF token** and embed it in the HTML response:

   ```html
   <meta name="csrf-token" content="<server-generated-token>" />
   ```

2. **Validate the `X-CSRF-Token` header** on all `POST`, `PUT`, `PATCH`, and `DELETE` endpoints. Reject requests where the header is missing or does not match the session token with `403 Forbidden`.

3. **Rotate the token** on login and session changes to prevent fixation attacks.

### OAuth state & PKCE

`login()` and `socialLogin()` on the `oauth` adapter generate a cryptographic
`state`, a PKCE code verifier, and its S256 challenge. State and verifier are
written to `sessionStorage` (scoped to one tab's one attempt) alongside a
timestamp, and validated on callback.

Three checks run before the code is exchanged, in `exchangeCode()`:

1. **State match.** A mismatch throws and deliberately _preserves_ the stored
   state, so a back-button replay of the same callback URL can still succeed.
2. **Age.** State older than 10 minutes (`OAUTH_STATE_TTL_MS`) is rejected and
   cleared — expiry is unrecoverable, so the next attempt starts clean.
3. **Verifier present.** Missing verifier throws without clearing.

State is consumed only on success, so a transient backend failure does not
strand the user with no way to retry.

There is **no** `nonce`. OpenID Connect ID-token validation is not implemented;
the flow relies on `state` plus PKCE. Add a nonce if you introduce ID-token
verification.

### Development Mode

The `mock` adapter uses the `bearer` transport, so the CSRF header is not sent
at all and no meta tag is required — MSW-based mocking works without setup.

## Demo Mode

`VUESTRATA_AUTH_ADAPTER=mock` requires `VUESTRATA_RUNTIME_MODE=demo`; the env
schema rejects any other combination at build time. No backend is required.

### Demo code is compiled out of production builds

Everything in this section — the seeded super-admin, the IndexedDB layer, the
credential hint on the login page, the MSW handlers — exists **only** in a demo
build. It is all reachable through a single dynamic-import boundary
(`src/modules/app/state/demo`) guarded by the build-time `__VUESTRATA_DEMO__`
constant, so rolldown removes the whole subtree from a production bundle.

`scripts/build/verify-bundle.mjs --mode=production` asserts this on every CI
run: it fails if the demo IndexedDB store name, the integrity salt, the demo
address, or any MSW chunk appears in the output. That includes this page,
which a production build ships as well, so the sections below name each of
those values by the constant that holds it rather than quoting it.

If you add demo-only code, reach it through that barrel behind that guard.
Importing `~/state/demo-store` statically from application code puts the demo
super-admin — holding every registered permission — back into production.

> **Previously:** `installRuntimeBackends()` called `seedDemoSuperAdmin()`
> unconditionally, with no dev check and no adapter check. Every boot in every
> environment, including a real production deployment, wrote that user into the
> browser's IndexedDB.

### Default Demo Account

A demo build's login page shows the account's email and password under the
form. They are not repeated here: this page ships in production builds too,
where the credentials must not appear.

The account (`DEMO_ACCOUNT`, role `super_admin`) is defined once in
`src/modules/app/state/demo/account.ts` and imported by the login-page hint, the
MSW login handler, the seed routine, and the e2e helpers, so they cannot drift
apart.

The account is seeded on first boot of a demo build and holds every permission
the app knows about: the role hierarchy's set unioned with whatever modules
contributed to the RBAC registry, read live rather than hardcoded.

Its grants are **reconciled on every boot**, not just written once. The stored
permission array is a snapshot in IndexedDB that outlives the code that wrote
it, and it is copied again into the session envelope at login. Seeding only into
an empty store meant a permission added afterwards never reached a returning
visitor — the nav entry stayed filtered out and the page kept answering `/403`
until they cleared site data. The seed now tops up the demo account, and any
signed-in demo session, whenever the app knows about a permission the stored
copy is missing. Accounts registered through the demo's own sign-up flow are
left alone.

### Persistence

Demo sessions survive page reloads via IndexedDB (the database named by
`DEMO_DB_NAME` in `src/modules/app/state/demo-persistence.ts`). Each record is
wrapped in an envelope carrying an `integrityHash`.

That hash is a **salted SHA-256 digest, not an HMAC**, and the salt is a public
constant compiled into the client bundle. It detects accidental corruption and
version skew in demo data; it provides no tamper resistance and is not a
security boundary — anything in a client bundle is readable, so the salt cannot
be secret. `e2e/helpers/auth.ts` reproduces it deliberately to seed test state.

> It previously read from `VITE_VUESTRATA_DEMO_SALT`. Because `envPrefix` is
> `VUESTRATA_`, that variable was never exposed to client code, so the fallback
> constant was always the value in use. The variable has been removed rather
> than fixed, since a client-visible salt is not a secret either way.

Cross-tab synchronisation is handled through a `BroadcastChannel`. When any tab logs in, out, or updates session data, the other tabs reload their session automatically.

### Session Retention

Demo sessions expire after `VUESTRATA_DEMO_AUTH_RETENTION_HOURS` hours (default: 24, range: 1–720). Expired envelopes are rejected on read and cleared on the next boot.

### Social Login & Magic Link

All social providers (Google, GitHub, Microsoft) and the magic-link flow are fully mocked. Social login issues a `demo-oauth-code-<provider>` code that the MSW `/auth/token` handler exchanges for tokens, exactly as a real OAuth code-exchange would.

### User Management in Demo Mode

Demo users can be created, have their roles reassigned, and have per-user permission overrides applied — all persisted to IndexedDB and reflected immediately across tabs.
