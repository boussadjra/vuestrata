# Semantic Tokens

Vuestrata has two layers of colour:

1. **Numeric ramps** — `--color-primary-50…950`, and the same for `secondary`,
   `accent`, `danger`, `surface`, `success`, `warning`, `info`. Each theme
   defines its own. This is where a theme's _character_ lives.
2. **Semantic tokens** — `--color-background`, `--color-foreground`,
   `--color-border`, `--color-ring`, and so on. These are **aliases onto the
   ramps** and never introduce a colour of their own. This is where a colour's
   _meaning_ lives.

Components use layer 2. That is the whole rule.

Defined in `src/modules/app/styles/semantic.css`, imported after every theme so
it can alias whichever ramp the active theme installed.

## Why

Before this layer existed, a component wrote out both halves of every colour
decision by hand:

```html
<!-- Don't -->
<p class="text-surface-500 dark:text-surface-400">…</p>
<div class="bg-green-50 dark:bg-green-950/30 border-green-200 dark:border-green-800">…</div>
```

Three problems, all of which were live in this codebase:

- **Dark mode was per-component.** Eight of the ten themes that existed then had no dark surface
  flip at all — dark mode only "worked" because each component wrote its own
  `dark:` twin. Miss one and that component alone is broken, on that theme alone.
- **Raw palette families ignore the theme.** `bg-green-50` renders identically
  on every theme. 332 utilities were doing this, almost all of them status
  colour — the one thing the token system had no answer for.
- **Contrast was decided ad hoc.** `surface-400` and `surface-500` were both used
  for "muted text"; only one of them clears WCAG AA on a light background.

Now:

```html
<!-- Do -->
<p class="text-muted-foreground">…</p>
<div class="bg-success-subtle border-success-200 dark:border-success-800">…</div>
```

No `dark:` variant for the surface or the foreground: `semantic.css` re-points
those tokens in a single `:root.dark` block that covers every theme at once.

## The tokens

### Surfaces

| Token                | Light               | Dark          | Use for                       |
| -------------------- | ------------------- | ------------- | ----------------------------- |
| `--color-background` | `surface-50`        | `surface-950` | The page.                     |
| `--color-card`       | lifted `surface-50` | `surface-900` | Panels resting on the page.   |
| `--color-elevated`   | lifted `surface-50` | `surface-800` | Popovers, dropdowns, dialogs. |
| `--color-muted`      | `surface-100`       | `surface-800` | Inset/secondary blocks.       |

Keeping `card` and `elevated` distinct is what lets a dialog read as _above_ a
card without each component inventing its own `bg-white dark:bg-surface-900`.
Both light values are `oklch(from var(--color-surface-50) …)` — a lift along
the active ramp, not a literal `#ffffff`. Terminal's mid-grey `surface-50`
becomes a lighter charcoal card; default's already-light 50 clips to
near-white.

### Foregrounds

| Token                       | Light         | Dark          | Notes                                                |
| --------------------------- | ------------- | ------------- | ---------------------------------------------------- |
| `--color-foreground`        | `surface-900` | `surface-50`  | Body text. ~16:1 on its background.                  |
| `--color-muted-foreground`  | `surface-600` | `surface-400` | Secondary text. Clears AA on **every** surface.      |
| `--color-subtle-foreground` | `surface-400` | `surface-500` | Decorative only. **Not** for text that must be read. |

A foreground token must clear AA against **every** surface it is paired with,
not just the page background. `surface-500` reached 4.61:1 on `background` but
only 4.34:1 on the slightly darker `muted` — the same class passing in a card
and failing inside an inset block. `surface-600` clears both.

Several components were reaching for `surface-400` directly, which is the
**decorative** step and does not clear AA at body size on any light surface.

`--color-subtle-foreground` currently has **no consumers**, and that is the
correct state rather than an oversight. Its only use was the calendar's
adjacent-month day numbers, which measured 2.55:1 — a day number is text that
must be read, so it belongs on `muted-foreground`. Reach for this token only
for genuine decoration: a watermark, a separator glyph, a decorative counter
whose value is also available as real text somewhere else.

### Lines and focus

| Token                   | Use                                               |
| ----------------------- | ------------------------------------------------- |
| `--color-border`        | Default dividers and outlines.                    |
| `--color-border-strong` | Emphasis, hover.                                  |
| `--color-input`         | Form control borders.                             |
| `--color-ring`          | The focus indicator. One value for the whole app. |

`--color-ring` is `primary-600` in light and `primary-400` in dark. A single
value cannot serve both: the previous rule mixed the ring toward _white_ in both
modes, so on a near-black surface it drifted toward the background it was
supposed to stand out from.

The global rule lives in `app.css`:

```css
*:focus-visible {
  outline: 2px solid var(--color-ring);
  outline-offset: 2px;
}
```

Do not write `focus-visible:outline-none` without an equivalent replacement.

### Status

`destructive`, `success`, `warning`, `info` — each with a `-subtle` background
that already handles its own dark-mode treatment.

`--color-warning-foreground` is dark in **both** modes: amber is light enough
that white text on it fails contrast regardless of colour mode.

#### Status text on a surface

| Token             | Light         | Dark          | Use                                  |
| ----------------- | ------------- | ------------- | ------------------------------------ |
| `--color-success` | `success-800` | `success-300` | Success text on `card`/`background`. |
| `--color-warning` | `warning-800` | `warning-300` | Warning text on `card`/`background`. |
| `--color-info`    | `info-800`    | `info-300`    | Info text on `card`/`background`.    |

Use `text-success` / `text-warning` / `text-info` — **not** a ramp step with a
hand-written dark twin. `text-success-700 dark:text-success-300` looks
equivalent and is not: a fixed step cannot know what surface a theme puts behind
it. Terminal's _light_ card is `#e1e1e5` rather than white, where `success-700`
measures 4.21:1 and `warning-700` 3.85:1 — both below AA, and both shipped on
the dashboard until the theme matrix caught them. The `800` steps clear 4.5:1
there (5.89 and 5.44) and still have room on white.

::alert{type="warning"}
`--color-destructive` is **not** part of this set, and `text-destructive` is not
the counterpart to `text-success`. It is tuned as a _fill_ — it pairs with
`--color-destructive-foreground` on buttons — and sits at `danger-600`, which is
3.70:1 on Terminal's light card. For destructive **text** on a surface use
`text-danger-700 dark:text-danger-300` (4.96:1). See `UiTrendDelta.vue`, whose
two branches are asymmetric for exactly this reason.
::

### Sidebar

`--color-sidebar`, `-foreground`, `-accent`, `-accent-foreground`, `-border`.
Separate from `card` so a theme can give navigation its own weight without
dragging every panel with it.

### Charts

`--color-chart-1` through `--color-chart-8`, read at runtime by
`useThemeColors()` (canvas cannot use CSS classes). The slots are declared on
`:root` in `semantic.css` as well as inside `@theme`: Tailwind v4 does not
emit unused `@theme` keys, so a JS-only read of `--color-chart-3` was empty
in light mode and every series past 2 fell back to the default palette.

The slots alternate hue family **and** lightness, so adjacent series differ on
two channels. The previous palette had five entries pulled straight off the
brand ramps, two pairs of which were a single ramp step apart — series 2/4 and
3/5 were effectively the same colour, and colour was the only thing telling them
apart.

Colour must never be the sole carrier of meaning (WCAG 1.4.1). Pair series with
direct labels, distinct dash patterns, or the `BaseChart` data table.

### Filled controls

`--color-primary-solid` / `--color-primary-foreground` is the pair for filled
controls that carry text (primary buttons, selected chips). The default is
`primary-600` with a lifted `surface-50` label. That pair clears AA on the
default teal ramp and fails on Sunset orange-600 and Forest/Terminal
emerald-600; those themes re-point `--color-primary-solid` to `primary-700`
(Terminal dark keeps a vivid `primary-600` with `surface-950` ink).

`UiPanel` and `UiStatCard` set `data-ui="card"` so theme card chrome (Harbour
glass, Blueprint registration marks, Brutalist offset shadows) reaches the
dashboard. `UiStatCard` also sets `data-shape="tabbed"` and clips the card to a
single folder path; hover lift stays on the `.card` class (`UiCard`) so a
static panel does not look clickable.

## The lint rule

`scripts/lint/plugins/no-raw-palette.plugin.mjs` blocks raw Tailwind palette
utilities (`bg-red-50`, `text-slate-600`, …) in `src/`.

It runs as a **ratchet**: it carries a baseline of the violations that already
existed, so untouched files keep working while new code cannot add to the count.
Lower a file's entry when you migrate it; delete the entry at zero. The rule
also fails when a count drops _below_ its baseline without the baseline being
updated — otherwise the number silently drifts back up on the next edit.

Escape hatch, for genuine brand colours that must not follow the theme:

```ts
// lint-allow-raw-palette
bg: 'hover:bg-red-50 dark:hover:bg-red-950/20', // Google brand tint
```

## Adding a theme

Define the ramps; the semantic layer does the rest.

```css
:root.theme-mine {
  --color-primary-50: …;
  /* … through 950, for primary / secondary / accent / danger / surface */
}
```

You do **not** need a `.dark` block for surfaces — the shared `:root.dark` in
`semantic.css` handles the flip. Override an individual semantic token only when
your theme's character genuinely demands it:

```css
:root.theme-mine {
  --color-card: var(--color-surface-100); /* flatter cards */
}
```

Then verify contrast — see the "Adding a theme" checklist in
[Accessibility Testing](../7.testing/2.accessibility.md).

## Motion

`styles/motion.css` neutralizes animation under `prefers-reduced-motion: reduce`
globally: every transition and animation utility, `<Transition>` components,
smooth scrolling, and view transitions.

Durations collapse to `0.01ms` rather than `none` so `transitionend` /
`animationend` listeners still fire — code that waits for one (the boot loader
does) would hang forever on `animation: none`. Purely decorative infinite
animations are stopped outright.

You should not need per-component reduced-motion handling. If you add motion
that the global rule cannot reach — a JS-driven animation, an inline style —
guard it yourself with `useMediaQuery('(prefers-reduced-motion: reduce)')`.
Charts go through `BaseChart`, which already does this for ECharts (canvas
tweening is not CSS, so the global rule never sees it).
