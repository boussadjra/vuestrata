# Adapter Systems

Vuestrata keeps one fixed UI component implementation and uses the **adapter pattern** where runtime flexibility still adds value: icons, validation engines, auth strategies, and the conventions of the API behind them.

## UI Wrapper Layer

The public `Ui*` components remain the stable import surface for the app, but they now target the repo's Reka UI implementation directly.

```
<UiButton>  →  UiButton.vue
```

### Usage

The wrapper surface stays consistent for app code:

```vue
<template>
  <UiButton variant="primary" size="lg">Click me</UiButton>
  <UiDialog v-model:open="dialogOpen">
    <template #title>Confirm</template>
    <p>Are you sure?</p>
  </UiDialog>
</template>
```

### Shared Field Behaviour

Components that embed shared logic (Formwerk wiring for form fields) delegate it to a composable rather than an intermediate component:

```
UiTextField  →  UiTextField.vue                    (public wrapper: template + styling)
    ↓
         composables/forms/useUiTextField.ts   (Formwerk bindings, labels, errors)
```

There is no `components/ui/base/` folder. Shared behaviour lives in `src/modules/app/composables/forms/`, and a `Ui*` wrapper is the only component in the chain. See [Ui Wrapper Architecture](/docs/components/provider-architecture).

## Icon Adapter

Icons use semantic names mapped to CSS classes per icon set:

```vue
<AppIcon name="bolt" size="lg" />
```

| `lucide`   | Lucide Icons   | Shared semantic map |

### Custom Icon Maps

```ts
import { registerIconMap, createCustomIconMap } from '~/config/icon-provider'

const myIcons = createCustomIconMap({
  bolt: 'my-icon-lightning',
  user: 'my-icon-person',
  // ... extend from an existing map
})

registerIconMap('custom', myIcons)
```

## Validation Utilities

Validation standardizes on Zod:

```ts
const { validate, validateField } = await createValidator('zod')
```

The shared `ValidationAdapter` interface remains so framework-agnostic code can validate through one contract:

```ts
interface ValidationAdapter {
  validate<T = unknown>(schema: unknown, data: unknown): ValidationResult<T>
  // `true` when the field is valid, otherwise its first error message
  validateField(schema: unknown, field: string, value: unknown): string | true
}
```

Both methods are synchronous. Only `createValidator()` is async, because it
loads the adapter on first use.

## API Client

`apiFetch` (`src/modules/core/lib/api/client.ts`) is the one HTTP client every
module uses. What it does is fixed; what it does _for your backend_ is
configuration, read on every request from a runtime slot:

```
src/modules/app/config/api.overrides.ts      yours: describes your backend
        ↓  resolveApiIntegration()            src/modules/app/bootstrap/seams.ts
ApiIntegration slot                           src/modules/core/lib/runtime.ts
        ↓  currentApiIntegration()
apiFetch                                      src/modules/core/lib/api/client.ts
```

`core/lib` never imports the overrides file. The bootstrap resolves it and
installs the result, and the client falls back to `DEFAULT_API_INTEGRATION` when
nothing is installed, which is why `core/lib` and its tests need no setup.

### The request lifecycle

```
apiFetch(request)
  │
  ├─ 0. is it for the API?       the URL's origin is the origin of VUESTRATA_API_URL,
  │                              or the call said `trusted: true`
  │
  ├─ 1. Authorization            from the session, unless the caller set one      ┐
  ├─ 2. credentials              'include' under the cookie transport, else 'omit' │ API
  ├─ 3. CSRF header              cookie transport only, from the CSRF strategy     │ requests
  ├─ 4. built-in headers         Accept: application/json (every request);         │ only
  │                              X-Request-Id and traceparent when tracing is on   │
  ├─ 5. request hooks            Accept-Language, then the project's headers/hooks ┘
  ├─ 6. the caller's onRequest
  │
  ├─ fetch
  │
  ├─ 7. classifiers              on every API response, first answer wins
  │      unauthenticated  →  refresh the session once, replay once
  │      csrf             →  renew the token (prime it if possible), replay once
  │      forbidden        →  no refresh, no replay
  │      unexpected       →  a 2xx fails as UNEXPECTED_RESPONSE; no replay
  ├─ 8. expectJson               only for a call that set it: a 2xx whose body is
  │                              not JSON fails as UNEXPECTED_RESPONSE
  └─ 9. error mappers            on a 4xx or 5xx: body → AppError
```

Steps 1 to 5 run inside the request's deadline: a hook, or a CSRF prime step,
that never settles fails the request as `TIMEOUT` instead of holding it open.

Steps 1 to 4 belong to the client. A request hook can add headers and change the
ones that are its business, but an `Authorization` or CSRF header the client
applied is put back if a hook removed or replaced it.

Three boundaries hold whatever the overrides file says:

- **The session stays on the API's origin.** A request to any other origin
  carries no `Authorization`, no CSRF token, no cookies, none of the project's
  headers or hooks, and is never refreshed, replayed or classified. A call, or
  a client made with `apiFetch.create()`, opts in with `trusted: true`.
- **A request is sent again only when the first attempt was refused.** A
  classifier answers `unauthenticated` or `csrf` on evidence (a status, a code,
  a redirect to the sign-in page), because a replayed `POST` that had been
  applied is applied twice.
- **A success is a success.** With no `expectJson` on the call, a `2xx` resolves
  with whatever ofetch parsed, exactly as bare ofetch would: a delete answered
  with `OK` as plain text has still deleted the record. `ignoreResponseError`
  is honoured the same way: the response comes back unclassified.

### The four extension points

| Option     | Type                                              | Where the shipped ones live                 |
| ---------- | ------------------------------------------------- | ------------------------------------------- |
| `request`  | `ApiRequestHook` (and `headers`, a table of them) | —                                           |
| `classify` | `ApiResponseClassifier`                           | `src/modules/core/lib/api/classifiers.ts`   |
| `errors`   | `ApiErrorMapper`                                  | `src/modules/core/lib/api/error-mappers.ts` |
| `csrf`     | `CsrfStrategy`                                    | `src/modules/core/lib/api/csrf.ts`          |

`src/modules/core/lib/api/presets/` bundles them per framework: `vuestrata`,
`laravel`, `django`, `spring`, `aspnet`, `nest`. The types, `defineApiOverrides`
and `resolveApiIntegration` are in `src/modules/core/lib/api/integration.ts`, and
the correlation ids in `src/modules/core/lib/api/tracing.ts`.

The one built-in header `core/lib` cannot produce is `Accept-Language`: the
active locale lives in vue-i18n, which `core/lib` may not import. The bootstrap
contributes it as the first request hook.

### What a failure looks like

Every failure that leaves the client is an `AppError`:

| Field                   | Meaning                                                                     |
| ----------------------- | --------------------------------------------------------------------------- |
| `kind`                  | `network`, `timeout`, `aborted`, `http`, `contract` or `unknown`            |
| `status`, `code`        | The HTTP status (0 when there was no response) and a machine-readable code  |
| `retryable`             | Whether sending the same request again could succeed                        |
| `details`, `formErrors` | Messages per field, keyed by the backend's own path, and for no field       |
| `messageKey`            | An i18n key for the user-facing text: `errors.network`, `errors.status_404` |
| `serverMessage`         | The backend's own message for a `4xx`, when it sent one                     |
| `requestId`             | The id the backend logged, or the one the client sent                       |

`describeError(error, t)` in `src/modules/core/lib/errors/index.ts` picks the
line to show, and `useErrorMessage()` binds it to vue-i18n. The message of a
`5xx` is never the backend's: it names internals, so the user reads the
translation of the status instead. Its `details` and `formErrors` are dropped
too, and its `code` is kept only when it is an identifier: a stack trace in a
500's body reads to an error mapper exactly like field errors, and a form must
not print it.

The full walkthrough, with a table of presets and worked examples for a tenant
header, Laravel Sanctum and ASP.NET problem details, is
[Connect Your Backend API](/docs/recipes/connect-your-backend-api).

## Collections

`createCollectionApi` (`src/modules/core/lib/api/collection-queries.ts`) is the
one data layer every domain module uses: a list, a record, three writes, with
the response validated by the module's zod schema. It never names a backend.
What goes on the wire is decided by one of two things it is given.

```
createCollectionApi({ resource, schema, keys, dialect?, path?, updateMethod? })
        │
        ├─ dialect ── the call's own
        │             else ApiIntegration.collection   (api.overrides.ts, or its backend preset)
        │             else dialects.vuestrata          (the contract before dialects existed)
        │
        │   filters ─ toListQuery ─▶ apiFetch ─▶ parseList / unwrapRecord ─▶ key case ─▶ zod ─▶ T
        │
createCollectionApi({ source: { list, get, create?, update?, remove? }, schema, keys })
        │
        └─ source ─── five functions over an SDK ──────────────────────────▶ zod ─▶ T
```

### Dialects

A `CollectionDialect` (`src/modules/core/lib/api/dialects.ts`) is a backend's
list conventions as data plus a few pure functions: the parameter names, the
number of the first page, the sort and array syntax, where the rows and totals
are in the answer, where the record is, the case of the keys, PATCH or PUT, and
the paths. It is framework-agnostic and has no Vue in it; the factory is the
only file in `core/lib` that imports TanStack Query.

Shipped: `vuestrata`, `laravel`, `laravelCursor`, `drf`, `drfLimitOffset`,
`drfCursor`, `spring`, `nestPaginate`. Each is a plain object declared on its
own, so a build that names none of them carries none of them.

The dialect is resolved **on every call**, not when the collection is made: a
module's `createCollectionApi` runs when the module is imported, before
`boot()` has read `api.overrides.ts`.

The order of a response is fixed, and it is what makes errors readable:
the dialect finds the rows (`parseList`) or the record (`unwrapRecord`), keys
are renamed to the app's case if the dialect says so, and only then does zod
validate. A `CONTRACT_MISMATCH` therefore names `data.3.contactName`, the path
a developer and a form both know, whatever the backend called it. Key renaming
reads the schema for what to leave alone (`z.record()` dictionaries,
`z.unknown()` fields), and never touches `AppError.details`. It is lossy for
digits and acronyms (`address_line_1`, `userID`), so in development the
collection checks the schema's fields against the rule and warns with the
`names` entry to add.

Three rules hold for every dialect, and are enforced in the factory rather
than left to each one:

- **An id is data.** Wherever a path is built from one (a record, a parent in
  `within()`, an action's or a read's `path` function) the id is
  percent-encoded as a single segment, and `''`, `.` and `..` are refused with
  an `AppError` (`INVALID_ID`) before any request. `resolveCollectionDialect`
  wraps every dialect's `paths.detail`, a project's own included, so a template
  is handed the encoded id and cannot get it wrong.
- **The cache key never throws.** A filter the dialect cannot write (an object
  with no serializer, or one named like the dialect's own parameter) is raised
  by the request, inside the query function: the list reaches its error state
  with a message instead of the component failing in `setup`. The key comes
  from `listKey`, which builds the same parameters without throwing or
  logging.
- **A dialect's parameter wins over a filter of the same name**, and the
  filter is reported, not silently overwritten.

### Sources

A `source` replaces REST with functions, for Supabase, Firebase or a GraphQL
client. Everything above the wire is the same code path: query keys, the
placeholder page, validation, invalidation after a write, and errors, which are
normalized to `AppError` whatever the SDK throws (an SDK error's `code` is
kept, and its status, or the one its code stands for, so a "not found" from
Firebase is a 404 to `isNotFoundError`). A source without `create`,
`update` or `remove` yields a collection without `useCreate`, `useUpdate` or
`useRemove`, in its type as well as at runtime.

### What a collection gives a module

| Composable                            | For                                                                        |
| ------------------------------------- | -------------------------------------------------------------------------- |
| `useList(filters)`                    | A numbered page: `{ items, meta }`. What `useServerTable({ query })` takes |
| `useInfiniteList(filters)`            | The same list a page at a time, by cursor or by page number: "load more"   |
| `useDetail(id)`                       | One record; waits for the id                                               |
| `useCreate`, `useUpdate`, `useRemove` | The writes; each invalidates the collection when it settles                |
| `action({ path, input, output })`     | A validated call that is not one of the five (`POST /orders/{id}/cancel`)  |
| `read({ name, path, output })`        | A validated read that is not one of the five (`GET /orders/{id}/summary`)  |
| `within(parent)`                      | All of the above under a parent, for a nested resource                     |

`createApiAction` and `createApiRead` are `action` and `read` for a call that
belongs to no collection.

The wire contract of each dialect is in
[Real Production](/docs/deployment/real-production#domain-endpoints); worked
examples for Laravel, Spring, an SDK, cursors, nested resources and a dialect
of your own are in
[Connect Your Backend API](/docs/recipes/connect-your-backend-api#collections).
