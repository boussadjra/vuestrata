# Adapter Systems

Vuestrata keeps one fixed UI component implementation and uses the **adapter pattern** where runtime flexibility still adds value: icons, validation engines, auth strategies, and the conventions of the API behind them.

## UI Wrapper Layer

The public `Ui*` components remain the stable import surface for the app, but they now target the repo's Reka UI implementation directly.

```
<UiButton>  →  UiButton.vue
```

### Usage

The wrapper surface stays consistent for app code:

```vue
<template>
  <UiButton variant="primary" size="lg">Click me</UiButton>
  <UiDialog v-model:open="dialogOpen">
    <template #title>Confirm</template>
    <p>Are you sure?</p>
  </UiDialog>
</template>
```

### Shared Field Behaviour

Components that embed shared logic (Formwerk wiring for form fields) delegate it to a composable rather than an intermediate component:

```
UiTextField  →  UiTextField.vue                    (public wrapper: template + styling)
    ↓
         composables/forms/useUiTextField.ts   (Formwerk bindings, labels, errors)
```

There is no `components/ui/base/` folder. Shared behaviour lives in `src/modules/app/composables/forms/`, and a `Ui*` wrapper is the only component in the chain. See [Ui Wrapper Architecture](/docs/components/provider-architecture).

## Icon Adapter

Icons use semantic names mapped to CSS classes per icon set:

```vue
<AppIcon name="bolt" size="lg" />
```

### Icon Sets

| Provider   | Library        | Mapping Style       |
| ---------- | -------------- | ------------------- |
| `solar`    | Solar Icons    | Shared semantic map |
| `lucide`   | Lucide Icons   | Shared semantic map |
| `phosphor` | Phosphor Icons | Shared semantic map |

### Custom Icon Maps

```ts
import { registerIconMap, createCustomIconMap } from '~/config/icon-provider'

const myIcons = createCustomIconMap({
  bolt: 'my-icon-lightning',
  user: 'my-icon-person',
  // ... extend from an existing map
})

registerIconMap('custom', myIcons)
```

## Validation Utilities

Validation standardizes on Zod:

```ts
const { validate, validateField } = await createValidator('zod')
```

The shared `ValidationAdapter` interface remains so framework-agnostic code can validate through one contract:

```ts
interface ValidationAdapter {
  validate<T = unknown>(schema: unknown, data: unknown): ValidationResult<T>
  // `true` when the field is valid, otherwise its first error message
  validateField(schema: unknown, field: string, value: unknown): string | true
}
```

Both methods are synchronous. Only `createValidator()` is async, because it
loads the adapter on first use.

## Auth Adapter

Auth supports multiple strategies via the adapter pattern:

```ts
const {
  login,
  register,
  socialLogin,
  logout,
  fetchUser,
  sendMagicLink,
  verifyMagicLink,
  setupMfa,
  verifyMfaCode,
  disableMfa,
} = useAuth()
```

### Strategies

| Adapter | Env Value                      | Flow                        |
| ------- | ------------------------------ | --------------------------- |
| Mock    | `VUESTRATA_AUTH_ADAPTER=mock`  | MSW-backed development auth |
| JWT     | `VUESTRATA_AUTH_ADAPTER=jwt`   | JSON Web Token auth         |
| OAuth   | `VUESTRATA_AUTH_ADAPTER=oauth` | OAuth 2.0 / social login    |

## API Client

`apiFetch` (`src/modules/core/lib/api/client.ts`) is the one HTTP client every
module uses. What it does is fixed; what it does _for your backend_ is
configuration, read on every request from a runtime slot:

```
src/modules/app/config/api.overrides.ts      yours: describes your backend
        ↓  resolveApiIntegration()            src/modules/app/bootstrap/seams.ts
ApiIntegration slot                           src/modules/core/lib/runtime.ts
        ↓  currentApiIntegration()
apiFetch                                      src/modules/core/lib/api/client.ts
```

`core/lib` never imports the overrides file. The bootstrap resolves it and
installs the result, and the client falls back to `DEFAULT_API_INTEGRATION` when
nothing is installed, which is why `core/lib` and its tests need no setup.

### The request lifecycle

```
apiFetch(request)
  │
  ├─ 1. Authorization            from the session, unless the caller set one
  ├─ 2. credentials              'include' under the cookie transport, else 'omit'
  ├─ 3. CSRF header              cookie transport only, from the CSRF strategy
  ├─ 4. built-in headers         Accept: application/json; X-Request-Id and
  │                              traceparent when tracing is on
  ├─ 5. request hooks            Accept-Language, then the project's headers and hooks
  ├─ 6. the caller's onRequest
  │
  ├─ fetch
  │
  ├─ 7. classifiers              on every response, first answer wins
  │      unauthenticated  →  refresh the session once, replay once
  │      csrf             →  renew the token (prime it if possible), replay once
  │      forbidden        →  no refresh, no replay
  ├─ 8. non-JSON success         for a request that asked for JSON: UNEXPECTED_RESPONSE
  └─ 9. error mappers            on a 4xx or 5xx: body → AppError
```

Steps 1 to 4 belong to the client. A request hook can add headers and change the
ones that are its business, but an `Authorization` or CSRF header the client
applied is put back if a hook removed or replaced it.

### The four extension points

| Option     | Type                                              | Where the shipped ones live                 |
| ---------- | ------------------------------------------------- | ------------------------------------------- |
| `request`  | `ApiRequestHook` (and `headers`, a table of them) | —                                           |
| `classify` | `ApiResponseClassifier`                           | `src/modules/core/lib/api/classifiers.ts`   |
| `errors`   | `ApiErrorMapper`                                  | `src/modules/core/lib/api/error-mappers.ts` |
| `csrf`     | `CsrfStrategy`                                    | `src/modules/core/lib/api/csrf.ts`          |

`src/modules/core/lib/api/presets/` bundles them per framework: `vuestrata`,
`laravel`, `django`, `spring`, `aspnet`, `nest`. The types, `defineApiOverrides`
and `resolveApiIntegration` are in `src/modules/core/lib/api/integration.ts`, and
the correlation ids in `src/modules/core/lib/api/tracing.ts`.

The one built-in header `core/lib` cannot produce is `Accept-Language`: the
active locale lives in vue-i18n, which `core/lib` may not import. The bootstrap
contributes it as the first request hook.

### What a failure looks like

Every failure that leaves the client is an `AppError`:

| Field                   | Meaning                                                                     |
| ----------------------- | --------------------------------------------------------------------------- |
| `kind`                  | `network`, `timeout`, `aborted`, `http`, `contract` or `unknown`            |
| `status`, `code`        | The HTTP status (0 when there was no response) and a machine-readable code  |
| `retryable`             | Whether sending the same request again could succeed                        |
| `details`, `formErrors` | Messages per field, keyed by the backend's own path, and for no field       |
| `messageKey`            | An i18n key for the user-facing text: `errors.network`, `errors.status_404` |
| `serverMessage`         | The backend's own message for a `4xx`, when it sent one                     |
| `requestId`             | The id the backend logged, or the one the client sent                       |

`describeError(error, t)` in `src/modules/core/lib/errors/index.ts` picks the
line to show, and `useErrorMessage()` binds it to vue-i18n. The message of a
`5xx` is never the backend's: it names internals, so the user reads the
translation of the status instead.

The full walkthrough, with a table of presets and worked examples for a tenant
header, Laravel Sanctum and ASP.NET problem details, is
[Connect Your Backend API](/docs/recipes/connect-your-backend-api).
