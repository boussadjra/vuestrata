# Architecture Overview

Vuestrata follows a layered architecture with strict inward dependency flow.

## Layers

- `src/modules/core/lib/`: framework-agnostic foundation (API client, errors, logging, query key helpers, event bus, RBAC, validation)
- `src/modules/app/config/`: runtime configuration and provider resolution
- `src/modules/app/bootstrap/`: the boot sequence (`boot()`), maintained by Vuestrata; `src/main.ts` and `src/App.vue` are thin shells over it
- `src/modules/app/stores/`: app-level Pinia client state
- `src/modules/app/composables/`: reusable reactive logic and server-state composables
- `src/modules/app/components/`: UI building blocks and provider wrappers
- `src/modules/app/pages/` and `src/modules/app/layouts/`: route entry points and application shells
- `src/modules/<name>/`: feature modules (`auth`, `analytics`, `billing`, `users`, `showcase`, `settings`) registered at startup

## Route Pages Are Inbound Adapters

Pages under `src/modules/*/pages/` are the boundary between Vue Router and the
application. They normalize route input, handle route-level concerns
(redirects, metadata, breadcrumbs, not-found, route access) and compose a
feature screen. Reusable feature or business logic lives in the feature module,
not in the page, and must not depend on route components or raw router state.

```text
Vue Router → route page → feature screen → components / composables → queries / API
```

See [Route Pages](4.route-pages.md) for the full rule, the smell checklist, and
good/bad examples.

## Server vs Client State

Ownership rule:

- Server state belongs to TanStack Query composables.
- Client-only preferences belong to Pinia stores.
- Cross-module notifications use the typed event bus in `src/modules/core/lib/events.ts`.

Current examples:

- `billing`: TanStack Query (`useBilling`)
- `users`: TanStack Query (`useUsers`)
- `settings`: Pinia + persisted app storage (`useSettingsStore`)

## State Ownership Policy

Module-scope mutable state in `src/**` is forbidden and enforced by the
`module-scope-state` custom lint rule
([scripts/lint/plugins/module-scope-state.plugin.mjs](../../scripts/lint/plugins/module-scope-state.plugin.mjs)).
The rule fails the build when it sees top-level `let`, `new Map/Set/WeakMap/WeakSet`
(non SCREAMING_SNAKE_CASE), or unwrapped reactivity calls (`ref`, `reactive`,
`computed`, `watch`, `watchEffect`, `useStorage`, `useAppStorage`, `shallowRef`,
`shallowReactive`).

Use the right primitive for the job:

| Need                                                                      | Primitive                             | Where                                        |
| ------------------------------------------------------------------------- | ------------------------------------- | -------------------------------------------- |
| Singleton shared simple state (registries, caches, theme/icon maps)       | `createGlobalState(...)` from VueUse  | `src/modules/app/state/*`                    |
| Complex client orchestration (multi-action stores, devtools, persistence) | `defineStore(...)` (Pinia)            | `src/modules/app/stores/*` and module stores |
| Server state                                                              | TanStack Query composables            | feature `composables/`                       |
| Cross-module pub/sub                                                      | typed event bus                       | `src/modules/core/lib/events.ts`             |
| Per-call state                                                            | local `const` / refs inside `setup()` | components/composables                       |

Allowlisted exceptions (still no business logic):

- `src/modules/core/lib/events.ts` (the bus itself)
- `src/modules/core/lib/runtime.ts` (typed injection slots)

One-off escapes must be justified inline with `// lint-allow-module-scope-state`.

## Runtime Backend Injection (`core/lib`)

`src/modules/core/lib/` stays framework-agnostic. Anything that needs Vue,
Pinia, or app-layer wiring is defined as an interface in
[`src/modules/core/lib/runtime.ts`](../../src/modules/core/lib/runtime.ts) and
installed at bootstrap. Today the slots are:

- `ApiAuthBackend` — provider, refresh state, CSRF token (used by
  `core/lib/api/auth-interceptor.ts` and `core/lib/api/client.ts`).
- `RbacBackend` — permission registry + computed predicates (used by
  `core/lib/rbac/*`).
- `ValidationCacheBackend<T>` — adapter cache (used by
  `core/lib/validation/index.ts`).

App-layer code constructs concrete implementations in
[`src/modules/app/state/runtime-backends.ts`](../../src/modules/app/state/runtime-backends.ts):

- `ApiAuthBackend` is a Pinia store (`useApiRuntimeStore`) — it has multiple
  refs and lifecycle.
- `RbacBackend` and `ValidationCacheBackend` are `createGlobalState` containers —
  simple shared maps/sets.

`installRuntimeBackends()` runs from `boot()` (see [Bootstrap](#bootstrap)) immediately after
`app.use(pinia)` and before any consumer touches the slots. Tests get a
clean state per case via
[`test/utils/reset-runtime-state.ts`](../../test/utils/reset-runtime-state.ts),
which is invoked in `test/setup.ts` `beforeEach`.

When you add a new cross-cutting service that `core/lib` needs, follow the
same pattern: add the interface + accessor to `runtime.ts`, build the
concrete backend in `app/state/runtime-backends.ts`, install it in
`installRuntimeBackends()`, and reset it in `resetRuntimeBackends()`.

## Bootstrap

`src/main.ts` is a shell the project owns: it imports the root component and the stylesheet and
calls `boot(App)`. `src/App.vue` is the same kind of shell, and renders `<AppRoot />`. Everything
that used to live in those two files is maintained by Vuestrata, so a fix to the boot order reaches
existing projects through `vuestrata upgrade`:

| File                                            | Role                                                                                                                     |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `src/modules/app/bootstrap/index.ts`            | `boot(App, options?)`: the whole sequence, in order. A step that throws goes to `renderBootFailure()`.                   |
| `src/modules/app/bootstrap/auth-wiring.ts`      | Hands the auth store to the API client, schedules the proactive refresh, and restores the session.                       |
| `src/modules/app/bootstrap/query-client.ts`     | The Vue Query options and the retry policy.                                                                              |
| `src/modules/app/bootstrap/seams.ts`            | `installSeams()`: where the project's seeded configuration is read into `core/lib`. Empty for now.                       |
| `src/modules/app/bootstrap/boot-error.ts`       | `renderBootFailure()`: the static screen a failed boot shows. See [When something fails](#when-something-fails).         |
| `src/modules/app/bootstrap/demo.ts`, `mocks.ts` | Demo-only steps. Only ever called behind `if (__VUESTRATA_DEMO__)`, which is what keeps them out of a production bundle. |
| `src/modules/app/components/layout/AppRoot.vue` | The root component: theme and locale sync, the error boundary, and the route outlet.                                     |

To add something of your own, pass `beforeMount` rather than copying steps into `main.ts`:

```ts
void boot(App, { beforeMount: (app) => app.use(MyPlugin) })
```

`boot()` also takes `queryOptions` (spread `vueQueryOptions` from `bootstrap/query-client` to change one
setting and keep the retry policy). Its `deps` option replaces any dependency and exists for tests:
`test/unit/app/bootstrap.test.ts` uses it to assert the order without booting an app.

## Modules

Modules are assembled in `src/modules/setup.ts` and initialized by `boot()`.

Current built-in modules:

- `auth`
- `analytics`
- `billing`
- `users`
- `showcase`
- `settings`

Each module contributes:

- `config` metadata
- `navItems`
- locale messages (`i18n`)
- optional routes/composables/stores exported through its barrel file

## Query Keys

`src/modules/core/lib/query-keys.ts` provides:

- shared keys (`billingKeys`, `usersKeys`, etc.)
- `defineQueryKeys(moduleId)` for module-local key factories

Convention: `[module, resource, ...params]`.

## Initialization Flow

1. Install global error handlers
2. Create the Vue app and register the Vue error handler
3. Register Pinia
4. Install runtime backends
5. Wire the auth interceptor
6. Register TanStack Query
7. Install i18n
8. Restore the persisted session
9. Setup modules (routes, navigation, translations)
10. Install the router
11. Start MSW (when enabled)
12. Wait for the first navigation and mount the app

## When something fails

Each kind of failure has one place that shows it and one `source` it is reported under.
`reportError()` does nothing until a reporter is installed (see
[Going to production](../8.deployment/2.real-production.md)).

| What failed                                                                                                 | What the visitor sees                                                           | Shown by                                                                                    | Reported as                                 |
| ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------- |
| A step of `boot()`, a required module's install, or the first route                                         | A static screen instead of the spinner: a heading, Reload, and the error's name | [`bootstrap/boot-error.ts`](../../src/modules/app/bootstrap/boot-error.ts)                  | `bootstrap`                                 |
| A route component's `setup()` (async ones too), an async component's loader, or a render that keeps failing | The error state instead of the page: Retry, Reload page, Go home                | [`AppErrorBoundary.vue`](../../src/modules/app/components/layout/AppErrorBoundary.vue)      | `vue:boundary`                              |
| A navigation: the next route's chunk could not be fetched, or a guard threw                                 | One automatic reload for a missing chunk, then the same error state             | [`plugins/stale-chunk.ts`](../../src/modules/app/plugins/stale-chunk.ts), then the boundary | `vue:router`                                |
| A watcher, a lifecycle hook, an event handler, a render error that clears on the next update                | Nothing. The page stays as it is                                                | `app.config.errorHandler`, set in `bootstrap/index.ts`                                      | `vue:render`                                |
| An API request                                                                                              | Whatever the feature that made the request renders for its error                | The feature (see [Route pages](./4.route-pages.md#errors-loading-authorization))            | Not reported, unless it escapes as below    |
| Anything nobody caught                                                                                      | Nothing                                                                         | `installErrorHandlers()` in `core/lib/errors`                                               | `window:error`, `window:unhandledrejection` |

**Boot failure.** `renderBootFailure()` runs when there is no app to render into, so it writes plain
DOM into `#app` and removes the `#app-loader` spinner. It cannot use Vue, i18n or the stylesheet: its
strings for `en`, `fr` and `ar` live in the file, and it picks the language from the persisted locale,
then from the browser. The detail it shows is the error's name and first message line with URLs and
query strings removed, never a stack. Once the app has mounted it is no longer used: a step that fails
after mount is logged and reported, and the running app is left alone.

**The error boundary** wraps the route outlet in `AppRoot.vue`. Vue describes where an error came from
with a readable string in development and a `https://vuejs.org/error-reference/#runtime-N` URL in
production; [`parseVueErrorInfo()`](../../src/modules/core/lib/errors/vue-error-info.ts) reads both, and
`test/unit/lib/vue-error-info.test.ts` pins its table to the installed Vue. Only errors that leave the
page unable to render are trapped. A render error is given two chances per component, because a template
that reads data before it has arrived fails once or twice and then renders. Retry mounts the page again
from scratch, and any navigation clears the error state. A request the app cancelled itself and a page
the visitor has already left are ignored.

**A chunk that will not load** usually means a deploy happened while the tab was open, so the first
failure reloads the page, once per 30 seconds. While that reload is on its way no error screen is shown.
If the chunk fails again, an in-app navigation reaches the error boundary and a first route reaches the
boot-failure screen. Retry on that error state is a page load rather than `router.push()`: Chromium
remembers a dynamic import that failed for as long as the document lives.

**API errors** are normalised to `AppError` by `normalizeError()`, whose `kind` says what failed
(`network`, `timeout`, `aborted`, `http`, `contract`, `unknown`). The feature that made the request shows
them. They reach a reporter only when nothing handles them: a rejection nobody caught, or a throw inside
a route component's `setup()`, which the boundary traps. An `aborted` request is never reported.

## Design Intent

- Keep `src/modules/core/lib/` reusable and free of Vue-layer imports.
- Keep module APIs explicit through barrel exports.
- Keep docs aligned with runtime behavior in the same change.
