# Write Your Own Auth Adapter

Everything about how your backend authenticates goes in one file,
`src/modules/app/config/auth.config.ts`. It is yours: `vuestrata upgrade` writes
it once and never touches it again. Nothing under `src/modules/auth/adapters/`
needs editing, and editing it would stop that folder receiving updates.

Left as it ships, `defineAuthConfig({})`, the app speaks the contract in
[Auth & RBAC](../6.configuration/2.auth-rbac#backend-endpoints).

Everything the file is written with comes from `~/lib/auth`: `defineAuthConfig`,
the endpoint presets, the response mappers, `parseUser` and the adapter types.
That folder is Vuestrata's, so what a release adds to it reaches your project.

## First: do you need an adapter at all?

Usually not. An adapter is a strategy — bearer tokens, a cookie session, an SDK.
A backend that uses a strategy Vuestrata already ships, under different names,
is configuration.

| Your backend                                                             | What to write                                                                  |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| REST, bearer tokens, its own paths, field names or user shape            | `endpoints` and mappers — [first example](#a-rest-backend-with-its-own-shapes) |
| The same, minus a feature (no sign-up, no magic links, no MFA)           | `endpoints: { … : null }` or `capabilities`                                    |
| Different social providers                                               | `providers` — [below](#social-providers)                                       |
| An SDK that signs in, stores the session and rotates the token by itself | An adapter of your own — [second example](#an-sdk-that-owns-the-session)       |
| A protocol none of the built-in adapters speaks                          | An adapter of your own                                                         |

## A REST backend with its own shapes

The backend keeps sessions at `/v1/session`, the current user at `/users/me`,
names its tokens in snake_case, answers a login with tokens and no user, and
has no sign-up, magic links or MFA:

```http
POST /v1/session            → { "access_token": "…", "refresh_token": "…", "expires_in": 900, "token_type": "Bearer" }
POST /v1/session/refresh    ← { "refresh_token": "…" }      → the same shape
DELETE /v1/session          → 204
GET /users/me               → { "id": 7, "email": "…", "full_name": "…", "role_name": "manager" }
```

```ts
// src/modules/app/config/auth.config.ts
import { authRefreshBodies, authResponseMappers, defineAuthConfig } from '~/lib/auth'

interface ApiUser {
  id: number
  email: string
  full_name: string
  role_name: string
}

export default defineAuthConfig({
  endpoints: {
    login: '/v1/session',
    logout: { path: '/v1/session', method: 'DELETE' },
    refresh: '/v1/session/refresh',
    me: '/users/me',
    register: null,
    magicLink: null,
    magicLinkVerify: null,
    mfaSetup: null,
    mfaVerify: null,
    mfaDisable: null,
  },
  mapAuthResponse: authResponseMappers.snakeCase,
  buildRefreshBody: authRefreshBodies.snakeCase,
  mapUser: (raw) => {
    const user = raw as ApiUser
    return { id: user.id, email: user.email, name: user.full_name, role: user.role_name }
  },
})
```

```bash
VUESTRATA_AUTH_ADAPTER=jwt
VUESTRATA_SESSION_PERSISTENCE=session   # this backend hands the refresh token to JavaScript
```

That is the whole integration. The built-in `jwt` adapter now signs in at
`/v1/session`, asks `/users/me` who that is, refreshes at `/v1/session/refresh`
with `{ refresh_token }` when a request comes back 401, replays the request, and
resumes after a reload. `test/integration/auth/snake-case-backend.test.ts` runs
exactly this configuration against a mock server with no `/auth/*` route at all.

### `endpoints`

Paths are relative to `VUESTRATA_API_URL`; an absolute `https://…` URL is used as
it is. An endpoint you do not mention keeps its default. The names:

| Name                                  | Default                                  | Method                 |
| ------------------------------------- | ---------------------------------------- | ---------------------- |
| `login`                               | `/auth/login`                            | POST                   |
| `register`                            | `/auth/register`                         | POST                   |
| `logout`                              | `/auth/logout`                           | POST                   |
| `me`                                  | `/auth/me`                               | GET                    |
| `refresh`                             | `/auth/refresh`                          | POST                   |
| `magicLink`, `magicLinkVerify`        | `/auth/magic-link`, `…/verify`           | POST                   |
| `mfaSetup`, `mfaVerify`, `mfaDisable` | `/auth/mfa/setup`, `/verify`, `/disable` | POST                   |
| `authorize`, `providerAuthorize`      | `/auth/authorize`, `/auth/:provider`     | a redirect, not a call |
| `token`                               | `/auth/token`                            | POST                   |

A string keeps the endpoint's method; `{ path, method }` changes it.

**`null` (or `false`) switches an endpoint off, and its capability with it.** The
adapter then reports `capabilities.register === false` and has no `register`
method, and the UI hides what it cannot do: the login page drops its link to
registration, the magic-link toggle goes, and so on. `logout: null` is for a
backend with stateless tokens: signing out becomes the client forgetting the
session. `login` and `me` cannot be switched off.

A backend that has the endpoint but not the feature says so with
`capabilities: { magicLink: false }`. It can only switch a capability off.

### `mapAuthResponse` and `mapRefreshResponse`

A mapper turns the body your backend sent into the app's names:

```ts
{ user?, token?, refreshToken?, expiresIn?, mfaRequired?, mfaToken? }
```

Three ship in `authResponseMappers`:

| Mapper       | Reads                                                                                                       |
| ------------ | ----------------------------------------------------------------------------------------------------------- |
| `vuestrata`  | `{ user, token, refreshToken?, expiresIn? }` — the default                                                  |
| `snakeCase`  | `{ access_token, refresh_token?, expires_in?, user?, mfa_required?, mfa_token? }`                           |
| `oauthToken` | An OAuth 2.0 token response: `access_token`, `token_type` (must be Bearer), `expires_in?`, `refresh_token?` |

Write your own for anything else. It is a function of the raw body:

```ts
mapAuthResponse: (raw) => {
  const body = raw as { data: { jwt: string; ttl: number } }
  return { token: body.data.jwt, expiresIn: body.data.ttl }
}
```

`user` is your backend's user record as it came; `mapUser` runs on it
afterwards, so a response mapper never has to shape it. When there is no `user`
in a login response, the app asks the `me` endpoint, presenting the token it was
just given.

`mapRefreshResponse` defaults to `mapAuthResponse`. `buildRefreshBody(token)`
builds the body of a refresh that presents a token; `authRefreshBodies` has the
three that pair with the mappers (`oauthToken` is form-encoded). Under
`VUESTRATA_SESSION_PERSISTENCE=refresh-cookie` the refresh has no body: the
credential is a cookie.

### `mapUser`, and what happens to a user that does not fit

`mapUser(raw)` returns the app's `User`. Its result is **validated** wherever a
user enters the app — login, registration, `me`, a resumed session, an OAuth
code exchange — and so is the body itself when you have no `mapUser`:

- `id` and `email` are required. `role` and `name`, if present, are strings;
  `permissions`, if present, is an array of strings.
- A numeric `id` becomes a string, and `null` on an optional field reads as
  absent. Fields the schema does not know are kept, so a `User` you widened
  with `tenantId` arrives whole.
- **A user with no `name` is shown by their email.**
- **A user with no `role` signs in, as `guest` and with no permissions.** The
  role is left absent rather than filled in: the auth store and `useRbac` read
  that as `guest` for role checks, and a user without a role holds no
  permission at all, not even what your `guest` role grants. That is what the
  app did before it validated identity, so a backend that never sent a role
  keeps working; map one in `mapUser` to give such users more.
- Anything else fails the request with a `CONTRACT_MISMATCH` error
  (`kind: 'contract'`), naming the fields in `details`: no `id`, no `email`, a
  `role` that is an array or a number, `permissions` that is not a list of
  strings. The sign-in fails; it does not produce a session nobody can be told
  apart by, or one whose role had to be guessed.

The log line carries field paths, never the payload.

Under bearer transport a login also has to carry a token. One that maps to a
user and no `token` is a `CONTRACT_MISMATCH` too (an MFA challenge excepted):
the store would otherwise hold a user that every request presents as nobody.

## An SDK that owns the session

A hosted auth service's client library is a different kind of thing. It signs
in, stores the session in storage of its own, rotates the access token on its
own timer, and tells you afterwards, including about a sign-out in another tab.
That needs an adapter, and three members of the contract are what it uses:

| Member                    | What it is for                                                                         |
| ------------------------- | -------------------------------------------------------------------------------------- |
| `subscribe(listener)`     | The SDK's announcements. The bootstrap subscribes once and applies them to the store.  |
| `persistence: 'external'` | The SDK stores the session. The app holds the access token in memory and nothing else. |
| `refreshSession()`        | Called on a 401, so the request is replayed with a token the SDK just issued.          |

No SDK ships with the template, so the skeleton below is written against an
imaginary client, `your-auth-sdk`, that resembles these libraries. Yours will
differ in the details — what `signInWithPassword` returns, what the events are
called — and those calls are the part to rewrite. The same adapter runs in the
test suite against a fake client with this shape:
`test/integration/auth/fake-sdk.ts` and `sdk-adapter.test.ts`.

```ts
// ~/auth/sdk-adapter.ts: a module of yours (`~` is the app module)
import { parseUser, type AuthAdapterFactory, type ResumedSession } from '~/lib/auth'
import type { AuthResponse } from '~/types'

import { createClient, type SdkSession } from 'your-auth-sdk'

// One client for the app. The factory below is called more than once (the boot
// wiring, the session restore and `useAuth()` each build an adapter), so
// anything there must be exactly one of lives out here.
const sdk = createClient(/* your project URL and public key */)

function toSession(session: SdkSession): ResumedSession & { token: string } {
  return {
    // The SDK's user is not the app's. Map it, and hold the result to the same
    // contract a REST backend's user is held to.
    user: parseUser({
      id: session.user.id,
      email: session.user.email,
      name: session.user.user_metadata.full_name,
      role: session.user.app_metadata.role,
    }),
    token: session.access_token,
    expiresIn: session.expires_in,
  }
}

const createSdkAdapter: AuthAdapterFactory = () => ({
  name: 'sdk',
  transport: 'bearer',
  persistence: 'external',
  capabilities: {
    register: false,
    social: false,
    magicLink: false,
    mfa: false,
    refresh: false, // the SDK rotates the token; the app is never handed one to rotate
    codeExchange: false,
  },

  async login(credentials) {
    return toSession(await sdk.auth.signInWithPassword(credentials)) as AuthResponse
  },

  async logout() {
    await sdk.auth.signOut()
  },

  async getUser() {
    const session = await sdk.auth.getSession()
    return session ? toSession(session).user : null
  },

  // A reload: the SDK still has the session it stored.
  async resumeSession() {
    const session = await sdk.auth.getSession()
    return session ? toSession(session) : null
  },

  // A 401 from your API: ask the SDK for a fresh token.
  async refreshSession() {
    const session = await sdk.auth.refreshSession()
    return session ? toSession(session) : null
  },

  subscribe(listener) {
    // The order the SDK made its changes in: one counter for all of them,
    // read as each event arrives and before anything asynchronous.
    let events = 0

    return sdk.auth.onAuthStateChange((event, session) => {
      const sequence = ++events

      if (event === 'SIGNED_OUT') {
        listener({ session: null, sequence })
        return
      }
      if (!session) return

      let announced: ReturnType<typeof toSession>
      try {
        announced = toSession(session)
      } catch {
        // The SDK's user stopped fitting `User`. `parseUser` has logged which
        // fields; an exception here would land in the SDK's own event emitter.
        return
      }
      listener({ session: announced, sequence })
    })
  },
})

export default createSdkAdapter
```

If your adapter does anything asynchronous between the SDK's event and the call
to `listener` (fetching the user's profile from your own API is the usual one),
the result can arrive after a later event, and announcing it then would undo
that event: a token rotation that finishes after the sign-out signs the user
back in. Take the counter before the `await` and compare it after:

```ts
return sdk.auth.onAuthStateChange(async (event, session) => {
  const sequence = ++events
  // …the SIGNED_OUT branch, as above…
  const profile = await fetchProfile(session.user.id)
  if (sequence !== events) return // something happened meanwhile: this is stale
  listener({ session: toSession(session, profile), sequence })
})
```

Register it, by the name `VUESTRATA_AUTH_ADAPTER` will select it with, and
declare that name:

```ts
// src/modules/app/config/auth.config.ts
import { defineAuthConfig } from '~/lib/auth'

declare module '~/lib/auth' {
  interface RegisteredAuthAdapterNames {
    sdk: true
  }
}

export default defineAuthConfig({
  adapters: {
    sdk: { transport: 'bearer', load: () => import('~/auth/sdk-adapter') },
  },
})
```

```bash
VUESTRATA_AUTH_ADAPTER=sdk
```

`adapters` is what makes the adapter work. The declaration is what makes its
name part of the type: `appConfig.authProvider` and `AuthAdapterName` are
`'mock' | 'jwt' | 'oauth' | 'session'` until a project adds to
`RegisteredAuthAdapterNames`, so that a project which registers nothing sees no
type change at all. The keys are what matter; write `true` for the value. The
build warns when the two lists differ, in either direction, with the lines to
add.

One more line, only in a project created before this seam: its own
`src/modules/app/types/index.ts` declares
`authProvider: 'jwt' | 'oauth' | 'mock'`, and that file is the project's. The
1.1.0 migration makes it `authProvider: AuthAdapterName` (imported from
`~/lib/config/env.schema`), which is what the template ships; a file it did not
recognise gets a note with that line to write, and needs it for the build to
pass.

What each part buys:

- **`load: () => import(…)`** makes the adapter, and the SDK it imports, a
  separate chunk. `boot()` fetches it before it wires auth, and only in a
  deployment that selects it. A deployment on `jwt` never downloads it.
- **`subscribe`** is how a sign-in the SDK completed, a token it rotated and a
  sign-out elsewhere reach the auth store. `{ session }` signs in or updates the
  token; `{ session: null }` ends the session and sends a visitor on a protected
  page to the login page, keeping the way back. Add `reason: 'expired'` when
  your SDK can tell a revoked session from a sign-out, and the login page says
  so. [What it owes the app](#what-subscribe-owes-the-app) is below.
- **`persistence: 'external'`** is a promise the app holds you to. Whatever
  `refreshToken` your adapter returns is removed before the app sees it, so
  nothing is written to Web Storage under any `VUESTRATA_SESSION_PERSISTENCE`.
  The SDK's own storage is the only copy of the session.
- **`parseUser`** fails the sign-in when the SDK's user stops fitting `User`,
  as it would for a REST backend. The registry applies it to whatever your
  adapter returns in any case — every session, and `getUser()` — so an adapter
  that forwards its SDK's user unchecked is still held to the contract.

An adapter that is cheap to load can be registered with its factory instead of
a loader: `sdk: { transport: 'bearer', create: createSdkAdapter }`. It is then
in the main bundle for every deployment.

### What `subscribe` owes the app

An announcement is not written to the store as it comes. It can be late, and it
can be for somebody else, and either one written blindly is a security bug: a
user signed back in after they signed out, or one user shown another's cached
data. So there is a contract, in both directions.

**Your adapter:**

1. **Reports changes in the SDK's order**, and numbers them: `sequence`, a
   counter that never goes down, taken when the SDK's event arrives and before
   any `await`. One counter for every change, sign-outs included.
2. **Drops what a later event overtook.** If it awaits anything before calling
   the listener, it compares the counter afterwards and stays silent when it
   has moved on (the snippet above).
3. **Ends the SDK's session in `logout()`.** The app clears its own state when
   the user signs out. An SDK that was never told keeps rotating a token for
   somebody who has left.
4. **Never throws into the SDK's emitter.** Catch around the mapping.

**The bootstrap, in return:**

| When                                                               | It                                                                                                                                              |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| A change has a `sequence` lower than one already received          | drops it. A session established later is never replaced by one announced earlier                                                                |
| The session announced belongs to a different user than the store's | ends the current session first — one `auth.logout`, so the query cache is dropped and a refresh in flight is discarded — then sets the new user |
| A session is announced after the app ended one itself, in this tab | ignores it, until the app signs somebody in, or you report `{ session: null }` with a `sequence`                                                |
| You report `{ session: null }`                                     | clears the store. That is the SDK's own word, so a session announced after it is a new sign-in and is honoured                                  |
| The user does not fit `User`                                       | ignores the change, and logs one contract error (field paths only)                                                                              |
| A session has no `token`, under bearer transport                   | ignores it                                                                                                                                      |

The third row is the one to understand. After `useAuth().logout()`, or an
expiry, an announced session cannot be told from a late announcement of the one
that just ended, so it is not honoured. With `sequence`, your report of the
sign-out settles it: whatever you announce after that is, by your own order, a
new sign-in — somebody signing in in another tab, say — and the user is signed
in here too. **Without `sequence` the bootstrap cannot enforce any order**: it
takes changes as delivered, and after a sign-out in this tab only the app's own
sign-in is trusted again. `sequence` is optional, and every adapter should
supply it.

### The contract

`login`, `logout` and `getUser` are required. Everything else is optional, and
each optional method is paired with a capability the UI reads:

| Capability     | Methods                               |
| -------------- | ------------------------------------- |
| `register`     | `register`                            |
| `social`       | `socialLogin`                         |
| `magicLink`    | `sendMagicLink`, `verifyMagicLink`    |
| `mfa`          | `setupMfa`, `verifyMfa`, `disableMfa` |
| `refresh`      | `refreshToken`                        |
| `codeExchange` | `exchangeCode`                        |

`resumeSession`, `refreshSession`, `canRefreshSession`, `subscribe` and
`persistence` have no capability: nothing in the UI depends on them, and the
bootstrap checks for each before using it. `transport` is `'bearer'` (the app
sends `Authorization: Bearer`) or `'cookie'` (the browser sends a session
cookie, and mutations carry a CSRF header).

## How the build reads the adapter names

`VUESTRATA_AUTH_ADAPTER` is validated when the app is built, before anything is
bundled, and the build cannot run `auth.config.ts` to find out what you
registered: the file imports your adapter, which imports an SDK that expects a
browser. So it **reads the file as text**, and takes the names under `adapters`
and each entry's `transport` from the syntax.

That is why `adapters`, and each adapter in it, has to be written where it can
be seen:

```ts
// Read correctly
export default defineAuthConfig({
  adapters: {
    sdk: { transport: 'bearer', load: () => import('~/auth/sdk-adapter') },
    'company-sso': { transport: 'cookie', create: createSsoAdapter },
    legacy: (options) => createLegacyAdapter(options), // an inline function is a bearer adapter
  },
})

// Each of these fails the build, with a message that says why
adapters: { ...sharedAdapters }               // a spread
adapters: { [ADAPTER_NAME]: { create } }      // a computed name
adapters: myAdapters                          // a variable
['adapters']: { … }                           // `adapters` under a computed key
adapters: { sso: ssoRegistration }            // an adapter that is not written inline
adapters: { sso: { ...shared, create } }      // a spread, or a computed key, inside an adapter
adapters: { sso: { transport: TRANSPORT, create } }   // a transport that is not a literal
export default merge(base, { adapters: { … } })       // anything but defineAuthConfig(<one object>)
```

The rule is strict on purpose. Whatever the build cannot read for certain, it
refuses: reading `['adapters']: { … }` as "no adapters" would reject your
adapter's name and tell you to register what you did register, and reading an
adapter held in a variable as a bearer one would let a cookie-transport adapter
through under a bearer persistence mode.

A name is lowercase letters, digits and dashes, and cannot be `mock`, `jwt`,
`oauth` or `session`.

The transport matters because one rule depends on it: a **cookie**-transport
adapter owns its own persistence, so the build requires
`VUESTRATA_SESSION_PERSISTENCE=none` with it, exactly as it does for `oauth`.
When the adapter is built, its `transport` is checked against what you wrote
**and** against what the build read; a difference stops the boot.

The same pass reads the names you declared in `RegisteredAuthAdapterNames`, and
the build warns about an adapter that is registered and not declared, or the
reverse. That is a warning: the adapter works either way, and only its type is
wrong. Keep the declaration in `auth.config.ts`, beside the adapters, which is
the one place the build looks.

## Social providers

The buttons on the login page are a list, not markup:

```ts
export default defineAuthConfig({
  providers: [
    { id: 'gitlab', label: 'GitLab', icon: 'i-logos-gitlab' },
    { id: 'github', labelKey: 'auth_provider_github', icon: 'i-logos-github-icon' },
  ],
})
```

`id` is what `socialLogin(id)` receives and what replaces `:provider` in the
`providerAuthorize` path. `labelKey` is an i18n key (put yours in
`<locale>.overrides.json`); `label` is plain text for a single-language app. The
list replaces the default three, and is also the allowlist: an id that is not in
it is refused. The buttons render only for an adapter whose
`capabilities.social` is true.

The login page is your file. A project created before this seam has the three
buttons written into its `login.vue`; to render the list instead, take the
`socialProviders` computed from the current template, which reads
`useAuth().providers`.

## When something is wrong

| What you see                                                                       | Why                                                                                          |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Build: `unknown auth adapter "x" … register it under adapters in … auth.config.ts` | `VUESTRATA_AUTH_ADAPTER` names an adapter that is not registered                             |
| Build: `auth.config.ts: adapters uses a spread …`                                  | The build could not read the names; see [above](#how-the-build-reads-the-adapter-names)      |
| Build: `adapter "x" is not written inline, so its transport cannot be read`        | Write it as `x: { transport: 'bearer', create: … }` in `adapters` itself                     |
| Build warning: `registers the adapter "x" without declaring its name`              | Add `x: true` to `RegisteredAuthAdapterNames` in `auth.config.ts`; the warning has the lines |
| Build: `SESSION_PERSISTENCE="…" has no meaning with AUTH_ADAPTER="x"`              | A cookie-transport adapter; set it to `none`                                                 |
| Boot-failure screen: `Could not load the "x" auth adapter …`                       | The adapter's chunk failed to load, or its module has no default-exported factory            |
| Boot-failure screen: `registers "x" as a bearer-transport adapter, but …`          | The adapter's `transport` is not the one written in `auth.config.ts`                         |
| Boot-failure screen: `"x" … is a function that returns a promise`                  | `x: () => import(…)` is a factory returning a promise; write `x: { load: () => import(…) }`  |
| The user is not signed in when the SDK announces a session                         | A sign-out in this tab came first; see [the contract](#what-subscribe-owes-the-app)          |
| Sign-in fails with `CONTRACT_MISMATCH`                                             | The user payload does not fit `User`; `details` names the fields. Fix `mapUser`              |
| `vuestrata doctor`: `auth.config.ts exists, but … seams.ts does not install it`    | You edited `bootstrap/seams.ts` before this seam existed; the warning has the lines to add   |

An unknown adapter name is never answered with the demo adapter. It used to be,
which sent a mistyped production deployment to endpoints that exist only inside
the demo's service worker.

## Verify

```bash
vp check && vpr test --run
vpr build       # the strict env parse runs here: an unregistered adapter name fails it
vuestrata doctor
```

Then sign in, let the access token expire (or revoke it server-side) and
navigate: the request should be refreshed and replayed without a visit to the
login page. Reload: the session should still be there.

In the demo (`VUESTRATA_RUNTIME_MODE=demo`) none of this applies. The mock
adapter always speaks the documented contract, whatever `auth.config.ts` says
about your real backend, so configuring one does not break the other.
