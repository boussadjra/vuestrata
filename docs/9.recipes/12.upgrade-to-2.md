# Upgrade to 2.0

Vuestrata 2.0 replaces TanStack Table with vueye-table and adds QueryWeave for
list URLs. TanStack Query continues to fetch and cache server data. This is a
breaking table API change; application columns and custom cells need review.

The published dependencies are pinned to `@vueye-table/core`,
`@vueye-table/vue`, and `@vueye-table/headless` **3.0.0-beta.3**, and
`@queryweave/core`, `@queryweave/vue`, and `@queryweave/vue-router`
**0.1.0-beta.5**.

## 1. Review the upgrade before applying it

Start from a committed project and run the CLI's upgrade preview. Inspect the
planned files, dependency changes, and migration instructions before applying
the release.

The three shared table helpers are now managed as a unit: `useDataTable`,
`useServerTable`, and `table-columns`. Recognized pristine infrastructure can
move together. Modified, moved, deleted, or ejected protected table files block
the upgrade, as does an unresolved application entrypoint. This prevents new
renderers from running against the old table engine.

A blocked apply writes missing review copies under `.vuestrata/incoming/`
without changing application files, dependencies, the lockfile, or the recorded
template version. Existing incoming edits are preserved. Merge the protected
files and entrypoint deliberately, then rerun the upgrade. Keep application
rendering in columns and slots instead of editing the shared engine.

Pristine shipped examples can migrate automatically. Customized examples are
preserved for manual review. Review every application-owned table, including
files outside the original module paths.

## 2. Convert columns and cells

The public entrypoints remain `UiDataTable`, `UiDataGrid`, `useDataTable`,
`useServerTable`, and `createColumns`. Their table value is now a native Vueye
binding. Remove imports from `@tanstack/vue-table` and `@tanstack/table-core`.
`createColumnHelper` and the old raw table/row exports are gone.

| 1.x                                    | 2.0                                                            |
| -------------------------------------- | -------------------------------------------------------------- |
| `accessorKey: 'name'`                  | `id: 'name'`, or `id` with `accessor(row)`                     |
| `enableSorting`                        | `sortable`                                                     |
| `meta.width: '12rem'`                  | `width: 192` in pixels                                         |
| `meta.align`                           | `align`                                                        |
| `cell({ row })` reading `row.original` | `render({ row, value, column, rowKey })` reading raw `row`     |
| `display(..., { cell: row => ... })`   | `display(..., { cell: ({ row }) => ... })`                     |
| Rich content in `format`               | Plain string in `format`; VNodes in `render` or display `cell` |

Use `createColumns` for the common treatments:

```ts
const col = createColumns<Product>()
const columns = [
  col.text('name', { label: 'Product', width: 240 }),
  col.text('sku', {
    label: 'SKU',
    render: ({ value }) => h('code', String(value)),
  }),
  col.display('actions', {
    label: 'Actions',
    cell: ({ row }) => h(UiButton, { onClick: () => edit(row) }, () => 'Edit'),
  }),
]
```

Plain text serves searching, copying, and CSV export. A display column can
supply `text(row)` when it needs a meaningful text representation.

## 3. Convert options, state, and slots

```ts
const { table, state, selectedRows } = useDataTable({
  data: products,
  columns,
  rowKey: 'id',
  initialState: { pagination: { page: 1, pageSize: 10 } },
  selectionMode: 'multiple',
})

table.value.goToPage(2)
table.value.search('keyboard')
```

| 1.x                                                      | 2.0                                                               |
| -------------------------------------------------------- | ----------------------------------------------------------------- |
| Table object in scripts                                  | `table.value` shallow ref; templates still use `:table="table"`   |
| `pageIndex: 0`                                           | `page: 1`                                                         |
| Top-level `pageSize` on `useDataTable`                   | `initialState.pagination.pageSize`                                |
| `getRowId`                                               | `rowKey` field or callback                                        |
| `enablePagination: false`                                | `paginate: false`                                                 |
| `manualPagination` / `manualSorting` / `manualFiltering` | `manual: true`                                                    |
| `getSubRows`                                             | `getChildren`                                                     |
| `getRowCanExpand(row.original)`                          | `getRowCanExpand(rawRow)`                                         |
| Mutable state refs                                       | Read-only `state`; named binding operations or controlled `state` |
| `getRowModel().rows`                                     | `rows`                                                            |
| `getFilteredRowModel().rows`                             | `processedRows`                                                   |
| `getState().pagination`                                  | `state.pagination`                                                |
| `setPageIndex(n)`                                        | `goToPage(n + 1)`                                                 |
| `setGlobalFilter(text)`                                  | `search(text)`                                                    |
| `resetRowSelection()`                                    | `clearSelection()`                                                |

The `expanded-row` slot receives raw `row`, stable `rowKey`, and native
`tableRow`. Replace `row.original.name` with `row.name`. Use native binding
operations for sorting, filtering, visibility, selection, and expansion.
Grouping and resizing were unused by Vuestrata and are no longer exposed by
its wrappers.

## 4. Move shareable state to the route boundary

Install the QueryWeave router adapter once through the application's existing
bootstrap `beforeMount` hook. Keep the teardown returned by that installation
attached to the application lifetime, as shown in the current `src/main.ts`.

Define a domain-owned model with `defineListQueryModel` from
`~/lib/table-query`. Bind it in the route page with `useListRouteState`, then
pass the binding to the feature screen. The screen calls
`useServerTable({ columns, query, queryState, rowKey: 'id' })`. The current
customers, orders, and users modules are complete examples.

This keeps URLs and navigation in the page, requests in the domain query, and
table interaction in the screen. Search replaces history after 300 ms;
pagination pushes history. Filter, sort, search, and page-size changes reset
to page 1 atomically. Invalid URL values recover to model defaults and their
decoding issues remain available on the route binding.

Keep selection, expanded rows, hidden columns, and menus local. A refused
navigation must keep the controls aligned with the committed URL.

## 5. Verify the project

Run `vp check`, local tests, a production build, and the bundle verifier.
Check a saved list URL, reload, Back/Forward, a refused navigation, search,
sorting, filters, page size, and selection across pages. Exercise custom cells,
CSV export, tree/detail expansion, and flat virtualization in every theme your
project ships. Switch English, French, and Arabic while a table is open and
check Arabic RTL on a narrow screen.

The [data-table reference](/docs/components/data-tables) describes the current
contract. `UPGRADING.md` at the repository root records release-level migration
details and the CLI's protected-file rules.
