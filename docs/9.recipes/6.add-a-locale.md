# Add a Locale

There is no generator for this — adding a language is mostly _translating_, and
a tool that produced 1,100 placeholder strings would create the illusion of a
finished translation. The mechanical parts are small and listed here.

## 1. Declare it

`src/modules/app/plugins/appearance.ts` owns the locale list — and, deliberately,
the metadata and RTL set beside it, so adding a language is one file:

```ts
export const SUPPORTED_LOCALES = ['en', 'fr', 'ar', 'de'] as const

export const LOCALE_METADATA: Record<SupportedLocale, { label: string; flag: string }> = {
  // …
  de: { label: 'Deutsch', flag: '🇩🇪' },
}

const RTL_LOCALES = new Set<SupportedLocale>(['ar']) // add here if RTL
```

`plugins/i18n.ts` takes the locale list from there. It still has to load the
new catalog, which is step 2.

## 2. Add the catalog files

One per locale folder — the shell plus every module:

```
src/modules/app/locales/<locale>.json
src/modules/app/locales/<locale>.overrides.json
src/modules/<each module>/i18n/<locale>.json
```

The Vite i18n plugin already globs `src/modules/app/locales/**` and
`src/modules/**/i18n/**`, so no config change is needed.

The shell has two files per locale, and they have different owners:

| File                                 | Whose                                                                                                        |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `en.json`, `fr.json`, `ar.json`      | Vuestrata's. `vuestrata upgrade` replaces them, so a key you add there costs the file its updates.           |
| `<locale>.overrides.json`            | Yours, in every locale. Merged on top of the catalog: it rewords a shipped string or adds a key of your own. |
| `<locale>.json` for a locale you add | Yours. Vuestrata ships no catalog for it, so no upgrade writes to it.                                        |

Load both shell files in `src/modules/app/plugins/i18n.ts`, the way the three
shipped locales are:

```ts
import de from '../locales/de.json'
import deOverrides from '../locales/de.overrides.json'
// …
messages: {
  // …
  de: withOverrides(de, deOverrides),
},
```

Import and expose the new file in each module's `index.ts`:

```ts
import paymentsI18nDe from './i18n/de.json'
// …
i18n: { en: …, fr: …, ar: …, de: paymentsI18nDe },
```

## 3. Translate every key

`i18n-parity` fails if any locale in a folder is missing a key another one has.
That is the point: vue-i18n falls back to `en` silently, so a gap looks like a
working build until a native speaker opens the page.

Fastest honest path: copy `en.json` to `<locale>.json` and `en.overrides.json`
to `<locale>.overrides.json`, translate in place, keep the keys. The second file
holds the strings your project added, and keeping the same split in every
locale means a release that adds strings to `en.json` shows up as exactly the
keys your `<locale>.json` is missing.

```bash
node scripts/lint/run-custom-rules.mjs   # tells you exactly which keys are missing
```

From then on, a key your project needs in the shell goes into
`<locale>.overrides.json` for every locale, never into `en.json`, `fr.json` or
`ar.json`. The rule counts a locale's catalog and its overrides as one, so it
passes as long as each locale has the key in either file.

## RTL

If the language is right-to-left, adding it to `RTL_LOCALES` is enough for the
plumbing — `applyAppearance` sets `html.dir`, and `AppRoot.vue` feeds the same
direction into Reka's `ConfigProvider`. Portalled UI (dropdowns, selects,
dialogs) does **not** inherit `html[dir]` on its own: Reka defaults those
trees to LTR, which is why the account menu used to keep icons on the left
in Arabic. Directional CSS (`ms-*`/`me-*` rather than `ml-*`/`mr-*`) still
matters for everything that is not a Reka portal.

Arabic is covered by `e2e/rtl-and-keyboard.spec.ts`. Add your locale to that spec.

## Verify

```bash
node scripts/lint/run-custom-rules.mjs   # i18n-parity
vp check && vpr test --run
vpr dev                                   # switch language in Settings
```

## In-app docs stay English

The documentation tree is not translated. `/docs` hides the header locale
switcher and locks `html[lang=en] dir=ltr` through `resolveActiveLocale()` in
`src/modules/app/plugins/appearance.ts`. The stored preference is left alone,
so leaving the docs restores French or Arabic.
