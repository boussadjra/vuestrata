# Connect Your Backend API

Every backend has habits. Laravel answers a stale token with `419`. Django REST
Framework answers an anonymous request with `403`. ASP.NET sends validation
errors as `application/problem+json`. A multi-tenant API wants a header on every
request.

The API client in `src/modules/core/lib/api/` is Vuestrata's, and editing it
stops it receiving updates. Everything a backend can do differently is described
in one file that is yours:

```
src/modules/app/config/api.overrides.ts
```

It ships empty. `boot()` reads it once, through `installSeams()` in
`src/modules/app/bootstrap/seams.ts`, and the client consults the result on every
request.

## What the client does with the file empty

| Concern             | Default                                                                                              |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| `Accept`            | `application/json`, unless the call sets `Accept` or a `responseType` other than `json`              |
| `Accept-Language`   | The active locale (`en`, `fr`, `ar`), unless the call sets it                                        |
| Not signed in       | A `401` on anything but an `/auth/` URL: refresh the session once, replay the request once           |
| CSRF                | Cookie transport only: `<meta name="csrf-token">` sent as `X-CSRF-Token`                             |
| Error body          | `{ message, code, details, requestId }`                                                              |
| A `2xx` body        | Whatever it is, handed to the caller as ofetch parses it. See [Expecting JSON](#expecting-json)      |
| Redirects           | Followed, as `fetch` does                                                                            |
| Timeout             | 15 seconds, hooks included                                                                           |
| Correlation headers | None                                                                                                 |
| Another origin      | No session, no CSRF token, no cookies. See [Requests to another origin](#requests-to-another-origin) |

Neither default header costs a CORS preflight: both are on the browser's
safelist.

The two headers are the only thing an empty file changes about a request to
your API. A `2xx` is a success whatever its body: a backend that answers a
delete with `OK` as `text/plain` has deleted the record, and the client says so.

## The options

```ts
import { defineApiOverrides } from '~/lib/api/integration'

export default defineApiOverrides({
  backend, // a preset to start from
  headers, // headers every request carries
  request, // hooks that run before each request
  classify, // how your backend says "not signed in" or "stale CSRF token"
  errors, // how your backend formats an error body
  csrf, // where the CSRF token is read from, and the header it returns in
  timeoutMs, // how long a request may take
  tracing, // X-Request-Id and traceparent
  redirect, // 'follow' (the default) or 'error'
})
```

`collection` is reserved for pagination and sorting dialects. It is accepted and
ignored in this release.

## Presets

A preset is one framework's conventions as a bundle. Import it from
`~/lib/api/presets`.

| Preset              | Reads as "not signed in"                                                                      | Reads as "stale CSRF token" | CSRF token                                                               | Error body                                                       |
| ------------------- | --------------------------------------------------------------------------------------------- | --------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| `presets.vuestrata` | `401`                                                                                         | —                           | `<meta name="csrf-token">` → `X-CSRF-Token`                              | `{ message, code, details, requestId }`                          |
| `presets.laravel`   | `401`, a redirect to `/login`                                                                 | `419`                       | `XSRF-TOKEN` cookie → `X-XSRF-TOKEN`, primed from `/sanctum/csrf-cookie` | `{ message, errors: { field: [...] } }`                          |
| `presets.django`    | `401`, a `403` that says so (see [Django](#django-rest-framework)), a redirect to a login URL | `403` "CSRF Failed: …"      | `csrftoken` cookie → `X-CSRFToken`                                       | `{ detail }`, `{ field: [...] }`, `non_field_errors`             |
| `presets.spring`    | `401`, a redirect to `/login`                                                                 | —                           | `XSRF-TOKEN` cookie → `X-XSRF-TOKEN`                                     | RFC 9457 `ProblemDetail`, else Boot's `{ timestamp, status, … }` |
| `presets.aspnet`    | `401`, a redirect to `/Account/Login`                                                         | —                           | the default                                                              | `ProblemDetails`, `ValidationProblemDetails`                     |
| `presets.nest`      | `401`                                                                                         | —                           | the default                                                              | `{ statusCode, message, error }`                                 |

Each preset's file under `src/modules/core/lib/api/presets/` says what it covers
and what it leaves to you.

"A redirect to `/login`" means exactly that: `fetch` followed a redirect, and
the page it ended on is the sign-in page. The request was refused before it did
anything, so the client refreshes the session and sends it again, whatever its
method. A redirect that ended on any other HTML page is **not** read as an
expired session; it fails with `UNEXPECTED_RESPONSE` and nothing is sent again.
[Writing a classifier](#a-classifier) says why.

### How a preset and your own options combine

A preset is a starting point. Everything you write beside `backend` still applies:

| Options                                    | Order                                                                          | Who wins                                |
| ------------------------------------------ | ------------------------------------------------------------------------------ | --------------------------------------- |
| `headers`, `request`                       | preset `headers`, your `headers`, preset `request` hooks, your `request` hooks | The later one: yours                    |
| `classify`, `errors`                       | yours, the preset's, the built-ins                                             | The first to answer: yours              |
| `csrf`, `timeoutMs`, `tracing`, `redirect` | —                                                                              | Yours replaces the preset's whole value |

To change one field of a preset's CSRF strategy, spread it:

```ts
import { csrfPresets } from '~/lib/api/csrf'
import { presets } from '~/lib/api/presets'

export default defineApiOverrides({
  backend: presets.laravel,
  csrf: { ...csrfPresets.laravel, prime: '/api/csrf-cookie' },
})
```

## Example 1: a tenant header from a store

A header whose value changes while the app runs is a function. It is called for
every request, so it sees the tenant selected now:

```ts
import { useTenantStore } from '@/stores/tenant'
import { defineApiOverrides } from '~/lib/api/integration'

export default defineApiOverrides({
  headers: {
    'X-Tenant': () => useTenantStore().currentTenantId,
  },
})
```

`useTenantStore` is a Pinia store you write; the function runs long after Pinia
is installed, so calling it here is safe. A function that returns `null`,
`undefined` or an empty string sends no header, which is what you want before a
tenant is chosen.

The table supplies defaults. A call that passes the header itself keeps its own
value, so a screen acting for another tenant can say so:

```ts
apiGet('/orders', { headers: { 'X-Tenant': otherTenantId } })
```

When a header table is not enough — the value is fetched, or depends on the
request — use a hook. It may be async:

```ts
export default defineApiOverrides({
  request: async ({ method, setHeader }) => {
    if (method === 'GET') return
    setHeader('X-Gateway-Key', await gatewayKey())
  },
})
```

A hook receives `url` (resolved, without its query string), `method`, the
`headers` so far, `setHeader(name, value)`, where `null` removes a header, and
`hasCallerHeader(name)`, which says whether the call set that header itself.

Five rules apply to every hook, and to the `headers` table, which is one:

- **It runs for requests to your API only.** A call to another origin gets none
  of them. See [Requests to another origin](#requests-to-another-origin).
- **It runs after authentication.** The session's `Authorization` header, the
  CSRF header and `Accept` are already set, and a hook can read them, the bearer
  token included. That is by design: a hook that signs a request has to see what
  it signs. A hook is your code, with the access the rest of your app has; do
  not hand `headers` to code that is not.
- **It cannot remove the session's credentials.** An `Authorization` or CSRF
  header the client applied is put back if a hook changed or deleted it. A hook
  may add `Authorization` to a request that has none.
- **A hook that throws fails the request**, with `AppError` code
  `REQUEST_HOOK_FAILED`, and nothing is sent.
- **Its time counts.** A hook is inside the request's deadline (`timeoutMs`, or
  the call's `timeout`): one that waits on a service that never answers fails
  the request as `TIMEOUT`, and a caller that aborts is released at once.

A new header on a cross-origin API has to be allowed by it. Add the name to the
backend's `Access-Control-Allow-Headers`, or the browser blocks the request at
the preflight.

## Requests to another origin

`apiFetch` accepts any URL, but the session belongs to one origin: the origin of
`VUESTRATA_API_URL` (the page's own origin when that is a path such as `/api`).
Only a request to it carries:

- the `Authorization` header and, under the cookie transport, cookies
  (`credentials: 'include'`) and the CSRF token
- the `headers` table, every `request` hook, and with them `Accept-Language`
- `X-Request-Id` and `traceparent`

and only its responses are run through your classifiers, or met with a token
refresh. A request anywhere else is sent with `Accept` and what the call itself
put on it, and with `credentials: 'omit'` unless the call says otherwise:

```ts
// Carries nothing of the session. A 401 from there does not sign anyone out.
await apiFetch('https://hooks.partner.example/notify', { method: 'POST', body })
```

For a second API of your own that accepts the same credentials, say so, on the
call or once for a client:

```ts
await apiFetch('https://files.acme.example/upload', { method: 'POST', body, trusted: true })

export const filesApi = apiFetch.create({ baseURL: 'https://files.acme.example', trusted: true })
```

`trusted: true` sends the user's token, and your gateway key, to that origin.
Use it for hosts you run, never for a third party.

### Redirects

Whether the session survives a redirect is the browser's decision, not the
client's. When an API response redirects to **another origin**, the browser:

- drops the `Authorization` header
- sends the cookies of the new origin, not your API's
- **keeps every other header**: the CSRF token and whatever your `headers` and
  hooks added, provided the new origin's CORS preflight allows those names

`fetch` cannot follow same-origin redirects and refuse the rest. An API that
never redirects its clients, which is most JSON APIs, should say so, and then a
header from the table cannot follow one anywhere:

```ts
export default defineApiOverrides({
  headers: { 'X-Tenant': () => useTenantStore().currentTenantId },
  redirect: 'error',
})
```

A redirect then fails the request as a network error. `redirect: 'error'`
cannot be combined with the `loginRedirect()` classifier (part of the Laravel,
Django, Spring and ASP.NET presets), which needs the redirect followed to see
where it ended; with those, keep the default and keep secrets out of the header
table. A call can still set its own `redirect`. The client logs a warning
whenever an API request was redirected to another origin.

## Expecting JSON

A `2xx` resolves with whatever the body is. That is right for a write whose
body nobody reads, and wrong for a read: when a static host answers a misrouted
API URL with its fallback `index.html`, the "data" is a page, and it fails three
layers down as a validation error nobody can interpret.

A call that goes on to read the body as data says so:

```ts
const report = await apiGet<Report>('/reports/42', { expectJson: true })
```

A success whose body is not JSON then fails with `AppError` code
`UNEXPECTED_RESPONSE` (`kind: 'contract'`, `messageKey: 'errors.unexpected_response'`).
An empty body always passes, and so does a body that parsed as JSON whatever its
`Content-Type` says. The collection layer (`createCollectionApi`) sets it on its
list, detail and read-back requests, and not on its writes. A client that should
always expect JSON is `apiFetch.create({ expectJson: true })`.

## Example 2: Laravel with Sanctum

```ts
import { defineApiOverrides } from '~/lib/api/integration'
import { presets } from '~/lib/api/presets'

export default defineApiOverrides({ backend: presets.laravel })
```

What that changes:

1. **The first write fetches a token.** A `POST` with no `XSRF-TOKEN` cookie
   first sends `GET /sanctum/csrf-cookie`, with cookies. The path is resolved
   against the API's _origin_, not under its `/api` prefix, which is where
   Laravel serves it.
2. **The token goes back decoded.** Laravel percent-encodes the cookie; the
   client decodes it into `X-XSRF-TOKEN`.
3. **A `419` is repaired, once.** The client fetches a new token and replays the
   request. If the replay is refused too, the request fails with
   `messageKey: 'errors.csrf'` and is not sent a third time.
4. **A redirect to `/login` is an expired session**, not a page of HTML handed
   to a schema. The client already sends `Accept: application/json`, so Laravel
   normally answers `401` instead; this covers calls that set their own `Accept`.
   A redirect to any other page is reported as `UNEXPECTED_RESPONSE`, and the
   request is not sent again.
5. **A `422` reaches you as fields.** `error.details` is
   `{ email: ['…'], 'items.0.quantity': ['…'] }`, keyed exactly as Laravel
   sent it.

Two things are outside this file:

- **The CSRF part applies under the cookie transport**, which the auth adapter
  chooses. With a bearer-token adapter (`jwt`, or Sanctum API tokens) no CSRF
  header is sent and only the error mapping and the classifiers apply. See
  [Auth & RBAC](/docs/configuration/auth-rbac).
- **Laravel has to accept the cookie.** `SANCTUM_STATEFUL_DOMAINS` must list the
  app's origin, and `config/cors.php` needs `supports_credentials` on. In
  development the dev-server proxy keeps both on one origin; see
  [Develop Against Your Backend](/docs/getting-started/develop-against-your-backend).

Requests share the prime: three writes that find no token together wait on one
`GET /sanctum/csrf-cookie`. If priming leaves no cookie JavaScript can read (it
is `HttpOnly`, or set for another domain), the client does not try again for ten
seconds, rather than adding a prime request to every write.

Spring works the same way with `presets.spring`.

### Django REST Framework

```ts
export default defineApiOverrides({ backend: presets.django })
```

Django has no prime endpoint: the `csrftoken` cookie appears once any view
decorated with `ensure_csrf_cookie` has answered. If yours is an API endpoint,
name it:

```ts
csrf: { ...csrfPresets.django, prime: '/api/csrf/' },
```

**How the preset recognises an expired session.** Under `SessionAuthentication`
DRF answers an anonymous request with `403`, the status it also uses for a
signed-in user who lacks a permission, and by default the only difference is a
sentence: `{"detail": "Authentication credentials were not provided."}`. DRF
translates that sentence, and the client sends `Accept-Language`, so a French
user's expired session arrives in French. The preset reads, in this order:

| Signal                                                                       | Covers                                                                       |
| ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| A `401`                                                                      | Every language. Needs the change below                                       |
| `code` (or `errors[].code`) of `not_authenticated` / `authentication_failed` | Every language. Needs a custom exception handler, or drf-standardized-errors |
| DRF's own sentence in English, French or Arabic                              | Those three languages, on a stock DRF                                        |

The sentence is the weakest of the three: a backend that answers in a fourth
language, or rewords the message, is read as "not allowed" and the user stays on
a page that cannot load instead of being sent to sign in. If your backend
localizes, make it say `401`. DRF does so as soon as the first authentication
class provides a `WWW-Authenticate` header:

```python
class SessionAuthentication401(SessionAuthentication):
    def authenticate_header(self, request):
        return 'Session'
```

A `WWW-Authenticate` header on a `403` is deliberately not treated as a signal:
DRF never sends one, and an OAuth resource server sends one with a `403` that
means the opposite (`insufficient_scope`). To add a language instead, extend the
list:

```ts
import { anonymousForbidden, DRF_ANONYMOUS_MESSAGES } from '~/lib/api/classifiers'

classify: [anonymousForbidden({ messages: [...DRF_ANONYMOUS_MESSAGES, 'Anmeldedaten fehlen.'] })],
```

## Example 3: ASP.NET Core problem details

```ts
import { errorMappers } from '~/lib/api/error-mappers'
import { defineApiOverrides } from '~/lib/api/integration'

export default defineApiOverrides({
  errors: [errorMappers.problemJson],
  tracing: { requestId: true },
})
```

A `ValidationProblemDetails` response:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": { "Email": ["The Email field is required."], "Address.City": ["Too short."] },
  "traceId": "00-84c1fd4063c38d9f3900d06e56542d48-85d1d4-00"
}
```

becomes an `AppError` with:

| Field       | Value                                                                         |
| ----------- | ----------------------------------------------------------------------------- |
| `status`    | `400`                                                                         |
| `message`   | `One or more validation errors occurred.`                                     |
| `details`   | `{ Email: ['The Email field is required.'], 'Address.City': ['Too short.'] }` |
| `requestId` | the `traceId`                                                                 |
| `code`      | the `type` URI                                                                |

`details` keeps the server's spelling, `Email` and not `email`. Nothing is
renamed at this layer.

`presets.aspnet` is this mapper plus the redirect-to-login classifier, which
cookie authentication needs and JWT bearer authentication does not.

`tracing: { requestId: true }` sends a fresh `X-Request-Id` with every request
and reports it as `error.requestId` when the response names none. It is off by
default because the header is not CORS-safelisted: a cross-origin API must list
it in `Access-Control-Allow-Headers`, and every `GET` gains a preflight.

The id the backend logged is the better one, and the client prefers it: the
`X-Request-Id` **response** header, read with tracing on or off. On a
cross-origin API the browser hides response headers from JavaScript unless the
backend exposes them, so add `Access-Control-Expose-Headers: X-Request-Id`
there, or `error.requestId` is only ever the id the client sent.

`tracing: true` also sends a W3C `traceparent`, with a new trace id per request
and the `sampled` flag set. A backend whose tracer honours the caller's flag
(OpenTelemetry's parent-based sampler, the usual default) then records every
request the app makes. To leave that decision to the backend, keep the ids and
clear the flag:

```ts
tracing: { requestId: true, traceparent: true, sampled: false },
```

## Writing your own

### A classifier

A classifier sees every response from your API, successful or not, and returns
`'unauthenticated'`, `'csrf'`, `'forbidden'`, `'unexpected'` or `null`. The
first to answer wins. A call made with `ignoreResponseError` is not classified:
it asked for the response as it is.

```ts
import { loginRedirect, statusMeans } from '~/lib/api/classifiers'

export default defineApiOverrides({
  classify: [
    // A status your backend uses for an expired session.
    statusMeans(440, 'unauthenticated'),
    // A sign-in page the default pattern does not know.
    loginRedirect({ loginPath: /^\/sso\/start/ }),
    // A 401 that means "not allowed": never refresh the session for it.
    ({ status, body }) =>
      status === 401 && (body as { code?: string })?.code === 'insufficient_scope'
        ? 'forbidden'
        : null,
  ],
})
```

| Verdict           | What the client does                                                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------------- |
| `unauthenticated` | Refreshes the session and replays once. If that fails, the session is expired and the error has `status: 401` |
| `csrf`            | Reads a new token, priming it if the strategy can, and replays once                                           |
| `forbidden`       | Nothing: no refresh, no replay. The error's `messageKey` is `errors.status_403`                               |
| `unexpected`      | Fails a `2xx` with `UNEXPECTED_RESPONSE`: no refresh, no replay                                               |

**`unauthenticated` and `csrf` send the request again.** For a `POST` that is
only safe when the first attempt was refused before it did anything. Return them
on evidence of a refusal — a status, an error code, a redirect to the sign-in
page — and never on a guess from what the response looks like. A backend that
applies a `POST` and then redirects to a confirmation page looks, to `fetch`,
exactly like one that redirected an expired session to a page: classify that as
`unauthenticated` and the order is placed twice.

That is why `loginRedirect` answers `unauthenticated` only when the redirect
ended on the sign-in path (`loginPath`, by default `/login`, `/signin`,
`/Account/Login`, `/accounts/login/` and their variants). A redirect that ended
on any other HTML page, for a request that sent the client's own
`Accept: application/json`, is `unexpected`: a `POST` that was applied and
answered with a page, or a `GET` a static host answered with its fallback
`index.html`. Neither is an expired session, so nothing is refreshed, nothing is
replayed and nobody is signed out. `loginRedirect({ html: false })` leaves such
a response alone instead.

An HTML page served directly at an API URL, with no redirect, is not
`loginRedirect`'s to judge; [`expectJson`](#expecting-json) is what fails it. A
redirect to another origin, such as an identity provider, is visible only when
that origin allows yours through CORS. Otherwise the browser blocks the
response and it arrives as a network error no classifier sees.

### An error mapper

A mapper sees a failed response and returns what it recognised, or `null` to
hand the body to the next mapper. The Vuestrata mapper always runs last.

```ts
import type { ApiErrorMapper } from '~/lib/api/integration'

const acmeErrors: ApiErrorMapper = ({ body }) => {
  const error = (body as { error?: { text?: string; id?: string } } | null)?.error
  if (!error) return null
  return { message: error.text, requestId: error.id }
}

export default defineApiOverrides({ errors: [acmeErrors] })
```

A mapper may return `message`, `code`, `details`, `formErrors` (messages that
belong to no field) and `requestId`. Whatever it returns, nothing a `5xx` said
reaches a user or a form: its message, form errors and `details` are dropped,
and its `code` is kept only when it is an identifier such as `DB_POOL`, not a
URL or a sentence. A 500 is not a validation failure, and a body like
`{ "trace": [...] }` reads to a mapper exactly like field errors.

The shipped mappers are `errorMappers.problemJson`, `.laravel`, `.drf`, `.nest`
and `.springBoot`. `drf` reads any object whose values are lists, so list it
last when you list several.

An error body is input from the network. The shipped mappers keep a field named
`constructor` or `__proto__` as an ordinary key, drop anything in a message list
that is not a string, stop following a nested error tree after 16 levels, and
cut a message longer than 2,000 characters. A message is never interpreted: one
that contains markup stays that text, so render it as text (interpolation, as
`useErrorMessage()` is used below), never with `v-html`.
Write your own mapper the same way: read `details` with `Object.entries()` or
`Object.hasOwn()`, not `details[name]` on a name the server chose, and return
`null` rather than throwing. A mapper that throws is skipped, and the next one
reads less.

### A CSRF strategy

```ts
csrf: {
  source: 'cookie', // 'meta', 'cookie' or 'none'
  name: 'XSRF-TOKEN', // the cookie's name, or the meta tag's
  header: 'X-XSRF-TOKEN',
  prime: '/csrf', // optional: a URL to GET, or an async function
  decode: decodeURIComponent, // optional
}
```

`csrfPresets` in `~/lib/api/csrf` has `laravel`, `django`, `spring`, `rails` and
`none`. The token refresh request uses the same strategy as every other request.

A `prime` function is given `{ baseURL }` and must settle: it is inside the
deadline of the request waiting on it, and given up on after ten seconds in any
case, after which the request goes ahead without a token.

## Showing the error

Render a failure with `useErrorMessage()`, never with `error.message`:

```vue
<script setup lang="ts">
const { errorMessage } = useErrorMessage()
</script>

<template>
  <UiAlert v-if="saveError" variant="error">{{ errorMessage(saveError) }}</UiAlert>
</template>
```

It shows, in order: what the backend said about a request it refused (a `4xx`
message from the mapper), the translation of the error's `messageKey`, and the
English `message` only as a last resort.

A form needs none of this by hand. `UiForm` with an `action` catches the failed
save, puts each field message under its field and gives the rest, already
localized, as `formErrors`; `src/modules/customers/pages/form.vue` is the
reference and [Submit a form to your API](/docs/recipes/submit-a-form-to-your-api)
the recipe.

The keys are in the shell catalogs: `errors.network`, `errors.timeout`,
`errors.session_expired`, `errors.csrf`, `errors.unexpected_response`,
`errors.status_404` and the rest. To reword one, add the key to
`src/modules/app/locales/<locale>.overrides.json`; the catalog itself is
Vuestrata's.

A backend that localizes its own messages receives the active locale in
`Accept-Language`, so the first case is in the user's language too.

## What this file does not do

- **Pagination, sorting and filter parameters.** The collection contract is
  still Vuestrata's own. `collection` is reserved for it.
- **Authentication.** Which adapter signs the user in, and whether it uses
  cookies or a bearer token, is chosen with `VUESTRATA_AUTH_ADAPTER`.
- **Field names.** `details` is keyed by the backend's path. Mapping
  `contact_name` onto a `contactName` field is the form's job.

## Verify

```bash
vp check
vpr test --run
vpr build
```

`vuestrata doctor` warns if `api.overrides.ts` exists and
`src/modules/app/bootstrap/seams.ts` does not install it, which happens when a
project edited that file before the seam existed.

To test a convention of your own, drive the real client against `msw`.
`test/integration/api/request-lifecycle.test.ts` has a worked case for each
feature on this page: install your overrides with
`installApiIntegration(resolveApiIntegration(overrides))`, send a request, and
assert what the handler received. `request-boundaries.test.ts` beside it covers
other origins, redirects and deadlines, and `response-matrix.test.ts` holds the
client to bare ofetch for every kind of success.
