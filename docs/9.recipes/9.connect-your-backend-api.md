# Connect Your Backend API

Every backend has habits. Laravel answers a stale token with `419`. Django REST
Framework answers an anonymous request with `403`. ASP.NET sends validation
errors as `application/problem+json`. A multi-tenant API wants a header on every
request.

The API client in `src/modules/core/lib/api/` is Vuestrata's, and editing it
stops it receiving updates. Everything a backend can do differently is described
in one file that is yours:

```
src/modules/app/config/api.overrides.ts
```

It ships empty. `boot()` reads it once, through `installSeams()` in
`src/modules/app/bootstrap/seams.ts`, and the client consults the result on every
request.

## What the client does with the file empty

| Concern             | Default                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------ |
| `Accept`            | `application/json`, unless the call sets `Accept` or a `responseType` other than `json`    |
| `Accept-Language`   | The active locale (`en`, `fr`, `ar`), unless the call sets it                              |
| Not signed in       | A `401` on anything but an `/auth/` URL: refresh the session once, replay the request once |
| CSRF                | Cookie transport only: `<meta name="csrf-token">` sent as `X-CSRF-Token`                   |
| Error body          | `{ message, code, details, requestId }`                                                    |
| Non-JSON success    | Rejected as `AppError` `UNEXPECTED_RESPONSE` when the request asked for JSON               |
| Timeout             | 15 seconds                                                                                 |
| Correlation headers | None                                                                                       |

Neither default header costs a CORS preflight: both are on the browser's
safelist.

## The options

```ts
import { defineApiOverrides } from '~/lib/api/integration'

export default defineApiOverrides({
  backend, // a preset to start from
  headers, // headers every request carries
  request, // hooks that run before each request
  classify, // how your backend says "not signed in" or "stale CSRF token"
  errors, // how your backend formats an error body
  csrf, // where the CSRF token is read from, and the header it returns in
  timeoutMs, // how long a request may take
  tracing, // X-Request-Id and traceparent
})
```

`collection` is reserved for pagination and sorting dialects. It is accepted and
ignored in this release.

## Presets

A preset is one framework's conventions as a bundle. Import it from
`~/lib/api/presets`.

| Preset              | Reads as "not signed in"                                                  | Reads as "stale CSRF token" | CSRF token                                                               | Error body                                                       |
| ------------------- | ------------------------------------------------------------------------- | --------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| `presets.vuestrata` | `401`                                                                     | —                           | `<meta name="csrf-token">` → `X-CSRF-Token`                              | `{ message, code, details, requestId }`                          |
| `presets.laravel`   | `401`, a redirect to `/login`                                             | `419`                       | `XSRF-TOKEN` cookie → `X-XSRF-TOKEN`, primed from `/sanctum/csrf-cookie` | `{ message, errors: { field: [...] } }`                          |
| `presets.django`    | `401`, a `403` "credentials were not provided", a redirect to a login URL | `403` "CSRF Failed: …"      | `csrftoken` cookie → `X-CSRFToken`                                       | `{ detail }`, `{ field: [...] }`, `non_field_errors`             |
| `presets.spring`    | `401`, a redirect to `/login`                                             | —                           | `XSRF-TOKEN` cookie → `X-XSRF-TOKEN`                                     | RFC 9457 `ProblemDetail`, else Boot's `{ timestamp, status, … }` |
| `presets.aspnet`    | `401`, a redirect to `/Account/Login`                                     | —                           | the default                                                              | `ProblemDetails`, `ValidationProblemDetails`                     |
| `presets.nest`      | `401`                                                                     | —                           | the default                                                              | `{ statusCode, message, error }`                                 |

Each preset's file under `src/modules/core/lib/api/presets/` says what it covers
and what it leaves to you.

### How a preset and your own options combine

A preset is a starting point. Everything you write beside `backend` still applies:

| Options                        | Order                                                                          | Who wins                                |
| ------------------------------ | ------------------------------------------------------------------------------ | --------------------------------------- |
| `headers`, `request`           | preset `headers`, your `headers`, preset `request` hooks, your `request` hooks | The later one: yours                    |
| `classify`, `errors`           | yours, the preset's, the built-ins                                             | The first to answer: yours              |
| `csrf`, `timeoutMs`, `tracing` | —                                                                              | Yours replaces the preset's whole value |

To change one field of a preset's CSRF strategy, spread it:

```ts
import { csrfPresets } from '~/lib/api/csrf'
import { presets } from '~/lib/api/presets'

export default defineApiOverrides({
  backend: presets.laravel,
  csrf: { ...csrfPresets.laravel, prime: '/api/csrf-cookie' },
})
```

## Example 1: a tenant header from a store

A header whose value changes while the app runs is a function. It is called for
every request, so it sees the tenant selected now:

```ts
import { useTenantStore } from '@/stores/tenant'
import { defineApiOverrides } from '~/lib/api/integration'

export default defineApiOverrides({
  headers: {
    'X-Tenant': () => useTenantStore().currentTenantId,
  },
})
```

`useTenantStore` is a Pinia store you write; the function runs long after Pinia
is installed, so calling it here is safe. A function that returns `null`,
`undefined` or an empty string sends no header, which is what you want before a
tenant is chosen.

The table supplies defaults. A call that passes the header itself keeps its own
value, so a screen acting for another tenant can say so:

```ts
apiGet('/orders', { headers: { 'X-Tenant': otherTenantId } })
```

When a header table is not enough — the value is fetched, or depends on the
request — use a hook. It may be async:

```ts
export default defineApiOverrides({
  request: async ({ url, setHeader }) => {
    if (!url.startsWith('https://api.acme.example/')) return
    setHeader('X-Gateway-Key', await gatewayKey())
  },
})
```

A hook receives `url` (resolved, without its query string), `method`, the
`headers` so far, `setHeader(name, value)`, where `null` removes a header, and
`hasCallerHeader(name)`, which says whether the call set that header itself.

Three rules apply to every hook:

- **It runs after authentication.** The session's `Authorization` header, the
  CSRF header and `Accept` are already set, and a hook can read them.
- **It cannot remove the session's credentials.** An `Authorization` or CSRF
  header the client applied is put back if a hook changed or deleted it. A hook
  may add `Authorization` to a request that has none.
- **A hook that throws fails the request**, with `AppError` code
  `REQUEST_HOOK_FAILED`, and nothing is sent.

`apiFetch` also accepts absolute URLs. Check `url` before attaching a secret, as
the hook above does: a gateway key belongs only on requests to that gateway.

A new header on a cross-origin API has to be allowed by it. Add the name to the
backend's `Access-Control-Allow-Headers`, or the browser blocks the request at
the preflight.

## Example 2: Laravel with Sanctum

```ts
import { defineApiOverrides } from '~/lib/api/integration'
import { presets } from '~/lib/api/presets'

export default defineApiOverrides({ backend: presets.laravel })
```

What that changes:

1. **The first write fetches a token.** A `POST` with no `XSRF-TOKEN` cookie
   first sends `GET /sanctum/csrf-cookie`, with cookies. The path is resolved
   against the API's _origin_, not under its `/api` prefix, which is where
   Laravel serves it.
2. **The token goes back decoded.** Laravel percent-encodes the cookie; the
   client decodes it into `X-XSRF-TOKEN`.
3. **A `419` is repaired, once.** The client fetches a new token and replays the
   request. If the replay is refused too, the request fails with
   `messageKey: 'errors.csrf'` and is not sent a third time.
4. **A redirect to `/login` is an expired session**, not a page of HTML handed
   to a schema. The client already sends `Accept: application/json`, so Laravel
   normally answers `401` instead; this covers calls that set their own `Accept`.
5. **A `422` reaches you as fields.** `error.details` is
   `{ email: ['…'], 'items.0.quantity': ['…'] }`, keyed exactly as Laravel
   sent it.

Two things are outside this file:

- **The CSRF part applies under the cookie transport**, which the auth adapter
  chooses. With a bearer-token adapter (`jwt`, or Sanctum API tokens) no CSRF
  header is sent and only the error mapping and the classifiers apply. See
  [Auth & RBAC](/docs/configuration/auth-rbac).
- **Laravel has to accept the cookie.** `SANCTUM_STATEFUL_DOMAINS` must list the
  app's origin, and `config/cors.php` needs `supports_credentials` on. In
  development the dev-server proxy keeps both on one origin; see
  [Develop Against Your Backend](/docs/getting-started/develop-against-your-backend).

Django and Spring work the same way with `presets.django` and `presets.spring`.
Django has no prime endpoint: the `csrftoken` cookie appears once any view
decorated with `ensure_csrf_cookie` has answered. If yours is an API endpoint,
name it:

```ts
csrf: { ...csrfPresets.django, prime: '/api/csrf/' },
```

## Example 3: ASP.NET Core problem details

```ts
import { errorMappers } from '~/lib/api/error-mappers'
import { defineApiOverrides } from '~/lib/api/integration'

export default defineApiOverrides({
  errors: [errorMappers.problemJson],
  tracing: { requestId: true },
})
```

A `ValidationProblemDetails` response:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "errors": { "Email": ["The Email field is required."], "Address.City": ["Too short."] },
  "traceId": "00-84c1fd4063c38d9f3900d06e56542d48-85d1d4-00"
}
```

becomes an `AppError` with:

| Field       | Value                                                                         |
| ----------- | ----------------------------------------------------------------------------- |
| `status`    | `400`                                                                         |
| `message`   | `One or more validation errors occurred.`                                     |
| `details`   | `{ Email: ['The Email field is required.'], 'Address.City': ['Too short.'] }` |
| `requestId` | the `traceId`                                                                 |
| `code`      | the `type` URI                                                                |

`details` keeps the server's spelling, `Email` and not `email`. Nothing is
renamed at this layer.

`presets.aspnet` is this mapper plus the redirect-to-login classifier, which
cookie authentication needs and JWT bearer authentication does not.

`tracing: { requestId: true }` sends a fresh `X-Request-Id` with every request
and reports it as `error.requestId` when the response names none. It is off by
default because the header is not CORS-safelisted: a cross-origin API must list
it in `Access-Control-Allow-Headers`, and every `GET` gains a preflight.
`tracing: true` also sends a W3C `traceparent`.

## Writing your own

### A classifier

A classifier sees every response, successful or not, and returns
`'unauthenticated'`, `'csrf'`, `'forbidden'` or `null`. The first to answer wins.

```ts
import { loginRedirect, statusMeans } from '~/lib/api/classifiers'

export default defineApiOverrides({
  classify: [
    // A status your backend uses for an expired session.
    statusMeans(440, 'unauthenticated'),
    // A sign-in page the default pattern does not know.
    loginRedirect({ loginPath: /^\/sso\/start/ }),
    // A 401 that means "not allowed": never refresh the session for it.
    ({ status, body }) =>
      status === 401 && (body as { code?: string })?.code === 'insufficient_scope'
        ? 'forbidden'
        : null,
  ],
})
```

| Verdict           | What the client does                                                                                          |
| ----------------- | ------------------------------------------------------------------------------------------------------------- |
| `unauthenticated` | Refreshes the session and replays once. If that fails, the session is expired and the error has `status: 401` |
| `csrf`            | Reads a new token, priming it if the strategy can, and replays once                                           |
| `forbidden`       | Nothing: no refresh, no replay. The error's `messageKey` is `errors.status_403`                               |

`loginRedirect` only reads a response `fetch` reached through a redirect. An
HTML page served directly at an API URL is a misrouted request — a static host's
fallback answering `/api` — and is reported as `UNEXPECTED_RESPONSE` rather than
signing the user out. It cannot see a redirect to another origin, such as an
identity provider: the browser blocks that response, and it arrives as a network
error.

### An error mapper

A mapper sees a failed response and returns what it recognised, or `null` to
hand the body to the next mapper. The Vuestrata mapper always runs last.

```ts
import type { ApiErrorMapper } from '~/lib/api/integration'

const acmeErrors: ApiErrorMapper = ({ body }) => {
  const error = (body as { error?: { text?: string; id?: string } } | null)?.error
  if (!error) return null
  return { message: error.text, requestId: error.id }
}

export default defineApiOverrides({ errors: [acmeErrors] })
```

A mapper may return `message`, `code`, `details`, `formErrors` (messages that
belong to no field) and `requestId`. Whatever it returns, the message and form
errors of a `5xx` never reach a user.

The shipped mappers are `errorMappers.problemJson`, `.laravel`, `.drf`, `.nest`
and `.springBoot`. `drf` reads any object whose values are lists, so list it
last when you list several.

### A CSRF strategy

```ts
csrf: {
  source: 'cookie', // 'meta', 'cookie' or 'none'
  name: 'XSRF-TOKEN', // the cookie's name, or the meta tag's
  header: 'X-XSRF-TOKEN',
  prime: '/csrf', // optional: a URL to GET, or an async function
  decode: decodeURIComponent, // optional
}
```

`csrfPresets` in `~/lib/api/csrf` has `laravel`, `django`, `spring`, `rails` and
`none`. The token refresh request uses the same strategy as every other request.

## Showing the error

Render a failure with `useErrorMessage()`, never with `error.message`:

```vue
<script setup lang="ts">
const { errorMessage } = useErrorMessage()
</script>

<template>
  <UiAlert v-if="saveError" variant="error">{{ errorMessage(saveError) }}</UiAlert>
</template>
```

It shows, in order: what the backend said about a request it refused (a `4xx`
message from the mapper), the translation of the error's `messageKey`, and the
English `message` only as a last resort. `src/modules/customers/pages/form.vue`
is the reference.

The keys are in the shell catalogs: `errors.network`, `errors.timeout`,
`errors.session_expired`, `errors.csrf`, `errors.unexpected_response`,
`errors.status_404` and the rest. To reword one, add the key to
`src/modules/app/locales/<locale>.overrides.json`; the catalog itself is
Vuestrata's.

A backend that localizes its own messages receives the active locale in
`Accept-Language`, so the first case is in the user's language too.

## What this file does not do

- **Pagination, sorting and filter parameters.** The collection contract is
  still Vuestrata's own. `collection` is reserved for it.
- **Authentication.** Which adapter signs the user in, and whether it uses
  cookies or a bearer token, is chosen with `VUESTRATA_AUTH_ADAPTER`.
- **Field names.** `details` is keyed by the backend's path. Mapping
  `contact_name` onto a `contactName` field is the form's job.

## Verify

```bash
vp check
vpr test --run
vpr build
```

`vuestrata doctor` warns if `api.overrides.ts` exists and
`src/modules/app/bootstrap/seams.ts` does not install it, which happens when a
project edited that file before the seam existed.

To test a convention of your own, drive the real client against `msw`.
`test/integration/api/request-lifecycle.test.ts` has a worked case for each
feature on this page: install your overrides with
`installApiIntegration(resolveApiIntegration(overrides))`, send a request, and
assert what the handler received.
