# Add a Module

```bash
vpr gen:module payments
```

Preview first with `--dry-run`; nothing is written until you drop the flag.

```bash
vpr gen:module payments --dry-run
```

## Options

| Flag                  | Purpose                                                                             |
| --------------------- | ----------------------------------------------------------------------------------- |
| `--entity <singular>` | Override the guessed singular. `people` → `person`, not `people`.                   |
| `--nav-group <id>`    | Sidebar section. One of the ids in `src/modules/nav-groups.ts`. Defaults to `work`. |
| `--icon <name>`       | Nav icon. Must be an `IconName`. Defaults to `widget`.                              |
| `--dry-run`           | Print the plan; write nothing.                                                      |
| `--json`              | Machine-readable plan, for tooling.                                                 |
| `--force`             | Overwrite existing files.                                                           |

## What it writes

```
src/modules/payments/
├── index.ts                    ModuleDefinition + public API barrel
├── types.ts                    zod schema, filters, draft schema
├── query-keys.ts               defineQueryKeys('payments')
├── query-model.ts              supported URL state, sorting and status choices
├── presentation.ts             status → badge variant
├── components/PaymentsScreen.vue list workflow and table columns
├── composables/
│   ├── usePayments.ts          createCollectionApi → 5 hooks
│   └── usePaymentForm.ts       initial values + the save the form awaits
├── mocks/
│   ├── fixtures.ts             seeded, deterministic
│   └── payments.handlers.ts    createCollectionMock
├── i18n/{en,fr,ar}.json
└── pages/{index,detail,form}.vue
```

And edits two files you would otherwise have to remember, both yours:

- `src/modules/setup.ts` — the import **and** the `appModules` entry
- `src/modules/app/config/rbac.overrides.ts` — `payments:read` /
  `payments:manage` declared in its `app:permissions` region, so the module's
  routes type-check

It never edits a file Vuestrata owns. `src/modules/core/lib/rbac/` stays as the
release shipped it, so `vuestrata upgrade` keeps updating it, and
`vuestrata doctor` reports no drift after a generator has run.

Then it runs `vpr fmt` over everything it touched.

The public barrel exposes domain types, schemas, status choices and query keys.
Query hooks stay internal so the module registry does not load collection
queries before a feature screen is opened.

## What it deliberately does not do

**It does not invent your domain.** `types.ts` gets a placeholder shape —
`name`, `status`, `createdAt`, `notes`. Replace it. Everything else in the
module derives from that schema: the mock builds responses through it, the query
validates responses against it, the form validates and submits the draft built
from it. A generator that guessed a `Payment` had a `currency` and a `refundedAt` would
produce code that looks finished and is wrong.

**It does not grant the new permissions to anyone.** The permissions are
_declared_, so the module compiles and the routes can reference them — but no
role holds them, so the pages are inaccessible until you add them to the
`grants` in `src/modules/app/config/rbac.overrides.ts` (see
[Add a permission](/docs/recipes/add-a-permission)). Silently handing
`super_admin` a new capability is not a generator's decision to make.

**It does not translate.** `fr.json` and `ar.json` ship with the English
strings. That keeps the `i18n-parity` lint rule meaningful — if they shipped
empty, the very first `vp check` after generating would fail, and people would
learn to ignore that rule.

## Verify

```bash
vp check && vpr test --run
```

Both pass on a freshly generated module with no edits, in a project that has ejected
the demo. In the template repository itself `public-surface.test.ts` snapshots
the module list and fails when one is added; that test is the template's own and
`eject` removes it. Then:

```bash
vpr dev
```

`/dashboard/payments` renders a paginated, MSW-backed **data grid** (search,
sort, status filter, server pagination); the sidebar shows the entry under its
group; the record and form pages work. Replace the placeholder columns in
`components/PaymentsScreen.vue` when you replace the placeholder fields in
`types.ts`. The list route only binds its QueryWeave model and renders that screen.

The form page is a complete submit lifecycle, not a stub: it validates against
the draft schema in the user's language, keeps its button pending for the whole
save, shows a refused save under the field it is about, and asks before unsaved
changes are discarded. When you replace the fields, change three places: the
draft schema in `types.ts`, the initial values in `composables/usePaymentForm.ts`
and the fields in `pages/form.vue`. See
[Submit a form to your API](/docs/recipes/submit-a-form-to-your-api).

## When you should not use it

The generator produces a **collection** domain — a list of records with CRUD.
That is what `createCollectionApi` and `createCollectionMock` are for. If your
module is a dashboard (`analytics`), a settings surface (`settings`), or a
presentational demo (`showcase`), start from one of those instead — they are
deliberately not collection-shaped, and forcing them through this template
produces a module you have to gut.

## Doing it by hand

Nothing here is magic; see
[Creating a module](/docs/modules/creating-a-module) for the same steps written
out. The one that gets forgotten is registering in `setup.ts` — a module that is
never registered produces no error at all, which is why
`test/unit/architecture/registry-drift.test.ts` fails on it.
