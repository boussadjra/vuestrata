# Submit a Form to Your API

`vpr gen:module <name>` writes all of this for a new module. This recipe is the
same thing by hand, for a form in a module you already have. The reference is
`src/modules/customers/`: `types.ts`, `composables/useCustomerForm.ts` and
`pages/form.vue`.

## 1. Put the rules in the draft schema

```ts
// types.ts, in your module
export const invoiceDraftSchema = invoiceSchema.pick({ status: true }).extend({
  number: z.string().trim().min(1).max(40),
  customerEmail: z.string().trim().min(1).pipe(z.email()),
  notes: z.string().max(2000),
})
```

Keep the record schema (`invoiceSchema`) lenient: it describes what the server
sends, and a record written before a rule existed must still load. The draft is
what a person is typing now.

Write no messages. Each check is worded from the `validation.*` catalog in the
language the user is reading. Add a message of your own only where the generic
one would not say enough.

## 2. Put the save in a module composable

```ts
// composables/useInvoiceForm.ts, in your module
export function useInvoiceForm(id: Ref<string | undefined>) {
  const createMutation = useCreateInvoiceMutation()
  const updateMutation = useUpdateInvoiceMutation()

  async function save(values: Record<string, unknown>): Promise<Invoice> {
    const draft = invoiceDraftSchema.parse(values)
    return id.value
      ? updateMutation.mutateAsync({ id: id.value, patch: draft })
      : createMutation.mutateAsync(draft)
  }

  return { schema: invoiceDraftSchema, save }
}
```

`save` does not catch. A failure has to reach the form for the form to show it.

The page may not hold the mutation: a route page is a thin adapter, and the
`no-restricted-imports` lint rule keeps `@tanstack/vue-query` out of `pages/`.

## 3. Hand both to `UiForm`

```html
<UiForm
  :schema="schema"
  :initial-values="initialValues"
  :action="save"
  show-errors="touched"
  confirm-leave
  @success="onSaved"
>
  <template #default="{ formErrors, isSubmitting }">
    <UiAlert v-if="formErrors.length > 0" variant="error" :title="t('common_error_title')">
      <p v-for="message in formErrors" :key="message">{{ message }}</p>
    </UiAlert>

    <UiTextField name="number" :label="t('invoices_number')" required />
    <UiTextField name="customerEmail" type="email" :label="t('common_email')" required />
    <UiTextarea name="notes" :label="t('common_notes')" />

    <UiButton type="submit" variant="primary" :loading="isSubmitting">
      {{ t('common_save') }}
    </UiButton>
  </template>
</UiForm>
```

That is the whole lifecycle:

- `action` is awaited, so the button is pending until the save has finished and
  a double click saves once. The button is `loading`, not `disabled`: it keeps
  focus while the save is in flight.
- A refused save puts each message under the field it is about, and moves
  focus to the first of those fields. What belongs to no field is in
  `formErrors`, already in the user's language.
- `confirm-leave` asks before a navigation discards what was typed, and stops
  asking once the save has succeeded. It never holds the redirect of a session
  that ended, and a sign-out asks before it signs out.
- `@success` receives what `save` resolved with. Navigate from there.

Bind fields by `name`, not `v-model`. The name is how the form knows which field
a server message belongs to, and a named field with no value of its own opens
on the form's: an edit form is `:initial-values="record"` and nothing more. A
select, a switch or a checkbox opens on the record like a text field does; a
`null` in the record becomes the field's empty value where it has one, and
stays `null` under a text field, so give a nullable text column
`z.string().nullable()` or map it to `''` first. The rule is in
[Forms](/docs/components/forms#which-value-a-field-opens-on).

## 4. Check what your backend sends

For a field message to land, a refused save must arrive as an `AppError` whose
`details` are keyed by field. Out of the box the API client reads:

```json
{ "message": "The invoice could not be saved.", "details": { "customerEmail": ["Already used."] } }
```

with a `4xx` status. If your backend speaks another dialect (Laravel's `errors`,
DRF's bare field map, ASP.NET's `ProblemDetails`), choose its preset in
`src/modules/app/config/api.overrides.ts`. See
[Connect Your Backend API](/docs/recipes/connect-your-backend-api).

The keys may stay in the backend's spelling. `contact_name`, `ContactName` and
`Items[0].Quantity` find `contactName` and `items.0.quantity` by themselves.
Only a name that differs in more than spelling needs telling:

```html
<UiForm :action="save" :field-map="{ 'Address.City': 'city' }" />
```

A key that matches no field is shown in `formErrors` with the key in front of
it, so a missing mapping is visible the first time it happens rather than
silently dropped.

## Verify

```bash
vp check
vpr test --run
```

Then, by hand, against your backend:

1. Submit the empty form. Every required field says so, in the active language.
2. Submit something the backend refuses (a duplicate, a business rule). The
   message is under the right field, and it clears when you edit that field.
3. Stop the backend and submit. The form shows the network message and is ready
   to be submitted again.
4. Type something and click a sidebar link. The dialog asks; "Keep editing"
   leaves what you typed in place.

Reference: [Forms](/docs/components/forms), sections "The submit lifecycle" and
"Server errors on fields".
