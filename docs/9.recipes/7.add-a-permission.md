# Add a Permission or a Role

Everything on this page is written in one file that is yours,
`src/modules/app/config/rbac.overrides.ts` (and, for identity-provider claims,
`auth.config.ts` beside it). Nothing under `src/modules/core/lib/rbac/` needs
editing, and editing it would stop that folder receiving updates.

- A permission: steps 1 to 4 below.
- [A role](#add-a-role): a name beside the built-in six, with what it inherits.
- [Several roles per user](#a-user-with-several-roles).
- [Roles from an identity provider](#roles-from-an-identity-provider): Keycloak,
  Auth0, Microsoft Entra ID.

For a permission, two separate acts, and conflating them is the usual bug:

1. **Declaring** a permission makes the string legal.
2. **Granting** it to a role makes someone able to use it.

`vpr gen:module` does the first for you and deliberately not the second.

## 1. Declare

Add the string to `AppPermissions`, in the `app:permissions` region:

```ts
declare module '~/lib/rbac/types' {
  interface AppPermissions {
    // app:permissions-start
    'payments:read': true
    'payments:manage': true
    // app:permissions-end
  }
}
```

That is declaration merging. `Permission` is the built-in union plus the keys of
`AppPermissions`, so `can('payments:read')` type-checks and `can('payment:read')`
— note the missing plural — still does not. The value type is never read;
`true` is convention.

Convention is `<resource>:<action>`, with `read` / `manage` covering most cases.
Add finer actions (`payments:refund`) only when a role genuinely holds one and
not the other — a permission nobody is granted separately is just a longer name
for the one beside it.

Also list it on the owning module's `config.permissions`, which is what
registers it with the RBAC registry at boot.

## 2. Grant

In the same file, the `grants` object maps a role to the permissions it gains:

```ts
export default defineRbacOverrides({
  grants: {
    viewer: ['payments:read'],
    manager: ['payments:manage'],
    // app:grants-start
    // app:grants-end
  },
})
```

Grants accumulate up the hierarchy exactly like the built-in deltas: a
permission granted to `viewer` is held by `member`, `manager`, `admin` and
`super_admin` too, and by every role of your own that inherits from `viewer`.
So grant it to the **lowest** role that should have it.

Until a role holds it, a route guarded by it is unreachable **for everyone**,
including `super_admin`. This is the step people miss and then debug as "the page
404s". It does not 404 — the guard denies access and redirects to `/403`.

`validateBuiltinRolePermissions()` runs at boot and warns about permissions
referenced by roles but never registered — the reverse direction.

## Taking one away

`withdrawn` removes built-in permissions from every role and from the registry.
It is how `vuestrata eject` retires the permissions of the modules it removes,
and it works the same for you:

```ts
withdrawn: [
  'billing:manage',
  // app:withdrawn-start
  // app:withdrawn-end
],
```

The permission is still a legal string — the union is Vuestrata's and stays
closed — but no role holds it. A withdrawal wins over a grant.

## 3. Guard

**Routes** — in the module's `routes` array:

```ts
meta: {
  requiresAuth: true,
  requiredPermission: 'payments:manage',
  // or several:
  requiredPermissions: ['payments:read', 'billing:read'],
  permissionMode: 'all',   // 'all' (default) = AND, 'any' = OR
}
```

`module-contract.test.ts` fails if a route requires a permission that is neither
declared on its module nor a builtin — i.e. a page nobody could ever open.

**UI** — hide the control, do not just let the click fail:

```ts
const { can } = useRbac()
```

```vue
<UiButton v-if="can('payments:manage')" @click="…">Refund</UiButton>
```

Server-side authorisation is still the real boundary. Hiding a control is a
usability decision, not a security one.

## 4. Label

Keys go in `src/modules/app/locales/{en,fr,ar}.overrides.json` (all three, or
`i18n-parity` fails). Those files are yours and are merged on top of the
catalogs beside them; `en.json`, `fr.json` and `ar.json` are Vuestrata's, and a
key added there stops the file receiving updates:

- `perm_<resource>_<action>` — the full phrase (`View Payments`)
- `perm_ns_<resource>` — the resource name on the account grants list
- `perm_action_<action>` — the verb only (`View`). Shared across resources;
  add it only when the action itself is new. `read`, `create`, `update`,
  `delete`, `manage`, `assign`, and `export` already exist.

The account page lists grants as a searchable data grid (resource, grant, token). Without `perm_ns_*` the
resource column falls back to the raw namespace; `perm_action_*` is used wherever a verb-only label is needed.

## Add a role

The built-in roles are `super_admin`, `admin`, `manager`, `member`, `viewer`
and `guest`, each holding everything the next one holds. A role of your own is
added beside them, in the same file, in two places that go together.

**Declare the name**, in the `app:roles` region. This is what makes `'auditor'`
a `Role`: `isAtLeast('auditor')` type-checks and `isAtLeast('auditer')` does
not.

```ts
declare module '~/lib/rbac/types' {
  interface AppRoles {
    // app:roles-start
    auditor: true
    // app:roles-end
  }
}
```

**Define it**, in the `app:role-definitions` region, and grant it what it holds
beyond what it inherits:

```ts
export default defineRbacOverrides({
  roles: {
    // app:role-definitions-start
    auditor: { inherits: ['viewer'], label: 'Auditor' },
    // app:role-definitions-end
  },
  grants: {
    // app:grants-start
    auditor: ['audit:read'],
    // app:grants-end
  },
})
```

A declared role that is not defined does not compile, and neither does a
definition for a name you did not declare, so the two cannot drift apart.

| Field         | Meaning                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------ |
| `inherits`    | The roles whose permissions it also holds, built-in or your own. `[]` for a role that holds only its grants. |
| `label`       | Its name in plain text, shown when no translation exists.                                                    |
| `labelKey`    | The i18n key of its name. Defaults to `role_<name>`.                                                         |
| `description` | One line for a legend or a tooltip.                                                                          |
| `assignable`  | `false` keeps it out of role pickers (a role only an integration holds). Defaults to `true`.                 |

### What inheriting means

`auditor` above holds what `viewer` holds (and so what `guest` holds), plus
`audit:read`. A grant made to `viewer` later reaches it too.

**Nothing inherits from your role unless you say so.** No built-in role does:
`admin` does not become an auditor, and `audit:read` granted to `auditor`
alone is not held by `manager`. One of your roles can inherit from another,
and from several at once:

```ts
roles: {
  auditor: { inherits: ['viewer'] },
  billing_admin: { inherits: ['member', 'auditor'] },
},
```

"Is this user at least a manager?" (`isAtLeast('manager')`, a route's
`requiredRole`) is answered by ancestry, not by a position in a list: a role is
at least the roles it inherits from, directly or not, and no other. So
`auditor` is at least a `viewer` and a `guest`, and is not a `member`.

**The built-in hierarchy cannot be rearranged in this version.** Listing a
built-in role under `roles` is a compile error. What a built-in role _holds_ is
yours to change, with `grants` and `withdrawn`.

A definition that cannot be meant — a parent that is not a role, a role that
inherits from itself through any chain — stops the app at boot with a message
that names `rbac.overrides.ts` and the role. Until it is fixed that role, and
every role that inherits from it, holds nothing.

### Label it

Add the key to `src/modules/app/locales/{en,fr,ar}.overrides.json`:

```json
{ "role_auditor": "Auditor" }
```

`role_<name>` is the key the built-in roles use, so every place that already
shows a role shows yours. Where no locale has the key, `roleLabel()` falls back
to `label`, and to the name made readable (`billing_admin` → "Billing admin")
when there is none:

```ts
import { roleLabel } from '~/lib/rbac'

const { t, te } = useI18n()
roleLabel(user.role, { t, te })
```

### Assign it in the users page

Nothing to do in a new project: the users module reads its role lists from the
role definitions, so the role is in the invite dialog, the inline role picker,
the filter, the legend and the permission matrix as soon as it is defined.

```ts
import { getAssignableRoles, getRoleDefinitions } from '~/lib/rbac'

getRoleDefinitions() // every role: built-in first, then yours in the order defined
getAssignableRoles() // the ones a picker offers
```

`ROLE_DEFINITIONS` is still exported and still holds the built-in six. It is
built before your file is read, so a role of yours is never in it. **A project
upgraded from 1.0 keeps its own users module**, which lists roles from
`ROLE_DEFINITIONS`: replace `Object.values(ROLE_DEFINITIONS)` with
`getRoleDefinitions()` (or `getAssignableRoles()` for a picker), and the
`t('role_' + name)` that labels a role with `roleLabel(name, { t, te })`. Once
you declare a role the compiler points at the rest: `ROLE_DEFINITIONS[role]`
and a `Record<Role, …>` written for six roles no longer type-check.

Your backend decides which roles a user actually has. The picker only offers
names; `PATCH /users/{id}/role` must refuse one the caller may not hand out.

## A user with several roles

A user may carry `roles`, a list of role names, beside `role` or instead of it:

```json
{ "id": "7", "email": "ada@example.test", "role": "viewer", "roles": ["viewer", "auditor"] }
```

| The user has                       | They hold                                                         |
| ---------------------------------- | ----------------------------------------------------------------- |
| `permissions: [...]`               | Exactly that list, whatever their roles. Minus what you withdrew. |
| several roles and no `permissions` | The union of what each role holds.                                |
| one role                           | What that role holds, as always.                                  |
| no role the app declares           | Nothing.                                                          |

`role` stays the **primary** role: what the header and the users table show,
and what code written for one role reads. It is the backend's `role` when the
app has that role. When only `roles` came (or `role` is a name the app does
not have), it is the first of `roles`, in the order sent, that no other of the
user's roles inherits from: for `["viewer", "admin"]` that is `admin`, because
an admin is a viewer already.

Authorization never asks the primary role alone:

```ts
const { roles, hasRole, isAtLeast, can } = useRbac()

isAtLeast('manager') // true when ANY of the user's roles is a manager or inherits from it
hasRole('auditor') // true when the user was given exactly this role
can('audit:read') // the union of every role, or the explicit list
```

and a route's `requiredRole` is met by any of the user's roles.
`useAuthStore().userRoles` is the list; `userRole` is the primary one.

**A role name the app does not declare is dropped.** A role created at the
identity provider last week, a typo from the backend: it is never a role with
permissions. A user left with no role is treated as a user with no role always
was — `guest` for role checks, holding nothing. In development each dropped
name is logged once, by name, with nothing about the user.

A permission string the app does not declare, in a user's explicit
`permissions`, is left in the list as sent and grants nothing: nothing asks
for it.

## Roles from an identity provider

An identity provider does not send `role: 'manager'`. It sends its own claims,
and `mapUser` in `src/modules/app/config/auth.config.ts` is where they are read
into the roles and permissions above. The identity mappers do the reading:

```ts
import { defineAuthConfig } from '~/lib/auth'
import { applyIdentity, identityMappers } from '~/lib/rbac/identity-mappers'

const identity = identityMappers.keycloak({
  clientId: 'my-app',
  roleMap: { 'team-lead': 'manager' },
})

export default defineAuthConfig({
  mapUser: (raw) => {
    const claims = raw as { sub: string; email: string; name?: string }
    return applyIdentity({ id: claims.sub, email: claims.email, name: claims.name }, identity(raw))
  },
})
```

`identity(raw)` returns `{ roles, permissions, hasPermissions }` in **your**
names, and `applyIdentity` writes `role`, `roles` and `permissions` on the user
from that result alone. Whatever the payload itself said about roles is not
kept.

| Mapper                     | Reads                                                                                  |
| -------------------------- | -------------------------------------------------------------------------------------- |
| `identityMappers.keycloak` | `realm_access.roles`, and `resource_access[clientId].roles` when you give a `clientId` |
| `identityMappers.auth0`    | `permissions`, and roles from `<namespace>/roles` when you give a `namespace`          |
| `identityMappers.entra`    | `roles` (app roles), and `groups` through a `groupMap` of group object ids             |
| `identityMappers.claims`   | Whatever you point it at: `{ roles: (claims) => claims['cognito:groups'] }`            |

```ts
// Auth0: permissions written "read:users" at the provider, "users:read" here.
identityMappers.auth0({
  namespace: 'https://my-app.example.com',
  roleMap: { Manager: 'manager' },
  permissionMap: { 'read:users': 'users:read' },
})

// Microsoft Entra ID: app role values, and one security group.
identityMappers.entra({
  roleMap: { 'Task.Manager': 'manager' },
  groupMap: { '0a1b2c3d-0000-4000-8000-123456789abc': 'auditor' },
})
```

The rules are the same for all four:

- **`roleMap` is provider name → your role** (or several). A provider role that
  is not in the map counts only if it already is the name of one of your roles;
  anything else is dropped. Nothing a provider can send becomes a role you did
  not declare.
- **Permissions** go through `permissionMap` the same way and are kept only if
  the app knows them: granted to some role, or listed in a module's
  `permissions`. When the claims carry a permission list at all, even an empty
  one, it is the user's whole set and their roles add nothing to it
  (`hasPermissions`). When they carry none, the roles decide.
- **Claims are read as hostile input.** A missing object, a string where an
  array belongs, a key named `__proto__`, a list of a million entries: none of
  it throws, and what cannot be read grants nothing.
- Keycloak lists the roles of every client the user has any in. Only the
  client you name is read. Entra leaves `groups` out of a token for a user in
  more than 200 groups; `groupMap` then grants nothing and says so in
  development. Prefer app roles, or resolve groups on your backend.

### This shapes the interface. It protects nothing

The claims are read in the browser, by code the user can change, and nothing
here verifies a token's signature. A user who edits their roles in memory sees
more buttons and gets a `403` from every one of them, **provided your backend
checks**. Every role and permission on this page must be enforced again by the
backend, from a token it validated itself. The frontend's checks decide what
is shown.

## Verify

```bash
vp check && vpr typecheck && vpr test --run
vpr dev    # sign in as the demo account and confirm the nav entry and page
```

The demo super-admin holds the role hierarchy's full set — grants included —
**plus** everything modules registered at runtime, reconciled on every boot of a
demo build. A module you just generated is therefore reachable in `vpr dev`
before you grant anything, without the visitor clearing site data first. A real
backend's users are different: they hold what their role's grants give them, so
the grant in step 2 is what makes the page work outside the demo.

`test/unit/architecture/demo-access.test.ts` asserts the demo half of it: the
demo account holds every permission any module declares, may open every route
any module registers, and sees every nav item.

## If you edited `core/lib/rbac/` before

Earlier releases told you to add the literal to the `BuiltinPermission` union in
`rbac/types.ts` and the delta to `inheritance.ts`. Entries in the union's
`app:permissions` region still work, and an upgrade keeps them. A change to
`inheritance.ts` is an edit to a file Vuestrata owns, and an upgrade leaves such a
file alone: move the change into `grants`, restore the file from the release
you are on, and it updates again. `vuestrata doctor` says which files differ.

The same goes for a role you added there (to the `Role` union, to
`ROLE_HIERARCHY` and to `ROLE_DELTA_DEFINITIONS`): declare it in `AppRoles`,
define it under `roles` with `inherits` naming the role that came right after
it in the hierarchy, and move its delta to `grants`. One thing changes. A role
you had placed in the middle of `ROLE_HIERARCHY` was inherited by every role
above it; a project role is inherited by nobody unless another of your roles
names it. Grant what the roles above it should keep to the built-in role they
should keep it through. While a kept copy of `inheritance.ts` is in place your
own roles hold nothing: it is the file that resolves them.
