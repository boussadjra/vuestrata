# Accessibility Testing

## What runs automatically

| Suite                           | Covers                                                                                 |
| ------------------------------- | -------------------------------------------------------------------------------------- |
| `e2e/accessibility.spec.ts`     | axe-core audit of public + authenticated pages, a theme/colour-mode matrix, and RTL.   |
| `e2e/rtl-and-keyboard.spec.ts`  | Skip link, focus indicator, drawer focus trap, `inert` when closed, RTL layout mirror. |
| `test/component/**`             | Component-level ARIA wiring.                                                           |
| `scripts/lint/…/no-raw-palette` | Blocks raw palette utilities that bypass the accessible semantic tokens.               |

Run them:

```bash
E2E_TARGET=preview vp run test:e2e -- e2e/accessibility.spec.ts e2e/rtl-and-keyboard.spec.ts
```

CI runs these against the **built preview**, not the dev server.

### Two decisions worth knowing

**`serious` fails the build, not just `critical`.** Most real barriers —
insufficient contrast, a missing form label, an unlabelled control — are
classified `serious` by axe. Asserting only on `critical`, as this suite
originally did, lets all of them through.

**Every audit waits for the app to render.** `page.goto()` resolves on document
load, not on Vue mounting. Auditing immediately races the first paint, and a
suite that audits an empty page passes every time while testing nothing. Use
`gotoAndSettle()` — never `goto` + `analyze` directly.

## What automation cannot tell you

Axe checks roughly a third of WCAG success criteria, and only the mechanical
ones. It cannot judge whether:

- focus order follows the visual order, or jumps around;
- an announcement is _meaningful_ — `aria-label="button"` passes every rule and
  helps nobody;
- alternative text conveys what the image conveys;
- a chart is comprehensible without seeing it;
- an error message explains how to fix the problem;
- a colour difference is the _only_ thing distinguishing two states;
- a live region fires at a useful moment rather than constantly.

Everything below is manual, and none of it is optional.

## Manual checklist

Run before any release, and whenever you touch layout, forms, or navigation.

### Keyboard only

Unplug the mouse. Not "avoid using it" — unplug it.

- [ ] Every interactive control is reachable with Tab, and reachable in the order it appears.
- [ ] The focus indicator is visible on every control, on every theme, in both colour modes. This is the one thing you cannot work around.
- [ ] Nothing traps focus except a modal, and every modal releases it on Esc.
- [ ] The skip link is the first Tab stop and actually moves focus.
- [ ] Dropdowns, comboboxes and menus respond to Arrow keys, Home/End, Esc and Enter.
- [ ] Data tables are navigable, and sorting can be triggered from the keyboard.
- [ ] Nothing is reachable that is not visible (the classic off-canvas-menu bug).

### Screen reader

Test with at least one of NVDA + Firefox (Windows), VoiceOver + Safari (macOS),
or TalkBack + Chrome (Android). Behaviour differs enough between them that one
is not a proxy for another.

- [ ] Page title changes on navigation and is announced.
- [ ] Headings form a sensible outline — one `h1`, no skipped levels.
- [ ] Landmarks (`banner`, `navigation`, `main`, `contentinfo`) are present and distinct.
- [ ] Form fields announce their label, current value, required state, and error.
- [ ] Errors are announced when they appear, not only when focused.
- [ ] Toasts and status changes are announced without interrupting mid-sentence.
- [ ] Icon-only buttons have names that describe the _action_, not the icon.
- [ ] Tables announce their caption and header associations.

### Charts

Charts render to a canvas: a single opaque node with no internal structure.
`BaseChart` gives them a `role="img"`, an accessible name, and a
visually-hidden data table — but only if you pass the data.

- [ ] Every chart passes `summary` describing the **trend**, not the title. "Revenue rose 24% over seven days, peaking Saturday" is useful; "Revenue chart" is not.
- [ ] Every chart passes `dataColumns` and `dataRows` so the numbers exist for someone not looking at the canvas.
- [ ] Series are distinguishable without colour. Check in greyscale. Colour must never be the only carrier of meaning (WCAG 1.4.1).
- [ ] Tooltip content is available some other way — hover is not a keyboard interaction.

### Colour and contrast

The semantic tokens are designed to clear WCAG AA, but a theme override or a
one-off utility can still break it.

- [ ] Body text ≥ 4.5:1; large text (18.66px bold / 24px) ≥ 3:1.
- [ ] UI component boundaries and state indicators ≥ 3:1 (WCAG 1.4.11).
- [ ] Focus indicators ≥ 3:1 against **both** the component and the adjacent background.
- [ ] Placeholder text is legible — it is the most common contrast failure, because it is styled as "less important" and then used to carry the label.
- [ ] Disabled controls are visibly disabled without relying on contrast alone.
- [ ] Check the themes with the least headroom: `terminal` and `brutalist` in dark, `ghibli` in light.

### Motion

- [ ] With `prefers-reduced-motion: reduce` set at the OS level, no animation plays. `styles/motion.css` covers CSS; `BaseChart` covers ECharts canvas tweening. Verify nothing else re-introduces motion via inline styles or JS.
- [ ] Nothing flashes more than three times per second (WCAG 2.3.1).
- [ ] Auto-playing motion can be paused.

### RTL

Switch the locale to Arabic.

- [ ] Layout mirrors: sidebar, icons, chevrons, progress direction.
- [ ] No horizontal scrollbar appears.
- [ ] Numbers, dates and currency use the locale's formatting.
- [ ] Mixed LTR content (code blocks, URLs) stays LTR — see the explicit `dir="ltr"` escape hatches.
- [ ] Charts read in the correct direction.

### Zoom and reflow

- [ ] 200% browser zoom: no loss of content or function (WCAG 1.4.4).
- [ ] 400% zoom at 1280px wide: content reflows to a single column with no horizontal scrolling (WCAG 1.4.10).
- [ ] Text spacing overrides do not clip content (WCAG 1.4.12).

### Windows High Contrast Mode

Forced-colors mode discards author colours entirely.

- [ ] Borders and focus indicators remain visible — anything conveyed only by `background-color` disappears.
- [ ] Icons drawn with `background-image` are still perceivable.

## Adding a theme

A new theme inherits every semantic token automatically, but its ramps are
yours. Before shipping it:

1. Verify `--color-muted-foreground` against `--color-background` in both modes — the tightest ratio in the system.
2. Verify `--color-ring` against both `--color-background` and `--color-card`.
3. Verify each `--color-chart-N` against `--color-card`, and against its neighbours.
4. Add it to the matrix in `e2e/accessibility.spec.ts` if its ramps sit close to its surfaces.

See `docs/4.theming/` for the token contract.
