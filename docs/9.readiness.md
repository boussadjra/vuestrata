# Readiness

"Is it production ready?" is three questions wearing one coat, and they have
different answers. This page keeps them apart.

|                                              | Status                      |
| -------------------------------------------- | --------------------------- |
| **1. Public demo** — deploy the showcase     | **Ready**                   |
| **2. Template** — start a project from it    | **Ready**                   |
| **3. Your application** — ship to real users | **Depends on your backend** |

A fourth thing people sometimes mean by "ready" is _stable_, and that one has
its own answer: Vuestrata is on an alpha release train. Ready here means usable
and verified, not frozen — conventions, generated file shapes and the public
surface may still change between alpha releases. `RELEASE.md` has the channels.

---

## 1. Public demo readiness

**Ready.** Deploy it — <https://vuestrata.vercel.app/> is this build.

- [x] Builds with no backend, no database, no secrets
- [x] MSW starts from validated runtime config, not `import.meta.env.DEV` — the
      defect that made a hosted demo impossible
- [x] Service worker published at root scope with `no-cache`, so a deploy cannot
      leave stale handlers serving forever
- [x] SPA fallback excludes `/api/*`, so a missing route 404s instead of
      returning HTML with a 200
- [x] Security headers on every response; one CSP definition behind Vercel,
      `_headers` and the Docker image
- [x] `verify-bundle --mode=demo` asserts the artifact in CI
- [x] Deterministic fixtures — same data on every reload, so screenshots and e2e
      assertions stay valid
- [x] Eight domains with working CRUD, all reachable from the sidebar

**Known limitations** (by design, documented in
[Vercel demo](8.deployment/1.vercel-demo)): data is per-browser and resets;
authentication is simulated and trivially bypassable; a service worker is
required.

## 2. Template readiness

**Ready.** Fork it and start deleting.

- [x] One switch (`VUESTRATA_RUNTIME_MODE`) produces both artifacts
- [x] Demo code is _compiled out_ of production, not merely unused — verified
      mechanically, not by inspection
- [x] Env config validated by one zod schema, strictly at build time and
      leniently in the browser
- [x] Auth is one explicit contract with capability flags, covering mock, JWT
      and OAuth; transport (bearer vs cookie) is explicit and never mixed
- [x] Semantic design tokens across all 12 themes in both colour modes
- [x] Accessibility enforced in CI: axe on `critical` **and** `serious`, across
      themes, colour modes and RTL, on every page pattern
- [x] Collection contract shared by mocks and queries, with 19 integration tests
- [x] Worked example per pattern: server table, record page, multi-step form,
      card grid, kanban, calendar, master/detail, feed, directory, restricted page
- [x] Strict TypeScript throughout; no `any` used to bypass a design problem
- [x] Custom lint rules with a shrinking ratchet for raw palette values
- [x] Sessions survive a reload on every real adapter, given the backend each
      one expects. `oauth` and `session` (cookie transport) resume from the
      session cookie through `GET /auth/me`, or the `me` endpoint configured. `jwt` presents the credential
      `VUESTRATA_SESSION_PERSISTENCE` selects to `POST /auth/refresh`, then
      loads the user from `GET /auth/me` when the refresh response has none.
      Under the production default, `refresh-cookie`, that needs a backend that
      sets an HttpOnly refresh cookie on login and reads it on `/auth/refresh`
      — see [what `refresh-cookie` needs from the backend](6.configuration/1.environment#what-refresh-cookie-needs-from-the-backend).
      Under `none` a reload ends the session, by design
- [x] A session refreshes before its access token expires and on a `401`, with
      the same credential, and the request that hit the `401` is replayed. A
      session that cannot be refreshed lands on the sign-in page with its
      destination and a notice that it expired, once; a sign-out is not taken
      for an expiry; a refresh that answers after its session ended is dropped;
      and the previous user's cached data is dropped
- [x] The route guard, `useRbac` and the sidebar give one answer for what a
      user holds, with a test holding them to it. A project declares, grants
      and withdraws permissions in `config/rbac.overrides.ts`, which is its own
- [x] Every failure has something on screen. A boot that fails shows a static
      screen in place of the spinner; a page that fails to set up, or a
      navigation that fails, shows an error state with Retry; a chart whose
      engine cannot be loaded says so in its own place. Each is reported once —
      see [When something fails](2.architecture/1.overview#when-something-fails)
- [x] Security headers generated from one definition into all four targets,
      with CI failing on drift
- [x] Node, pnpm and Vite+ pinned from one source each, with CI failing on drift
- [x] A CI workflow for a project, written by `vuestrata add ci` and by
      `vuestrata eject`: check, tests, a verified production build, the
      end-to-end suite, the image. No maintainer step and no deploy; see
      [CI for your project](8.deployment/3.ci-for-your-project). Its commands
      are held to the template's own workflow by a test, but the workflow itself
      has not yet run on GitHub in a project
- [x] The production Docker image is built AND opened in a browser in CI. It
      compresses (gzip, with the text assets compressed once at build time),
      answers `/healthz`, returns a JSON `502` for an `/api` path nothing
      routes, and caches by path class, with `immutable` on hashed assets only.
      `linux/arm64` is supported, and verified in CI only, by a build under
      emulation: an arm64 image has never been started
- [x] Coverage thresholds enforced, not merely collected
- [x] Bundle size budgets on the initial payload (560 KB gzipped), the largest
      eager chunk (400 KB), the largest eager stylesheet (700 KB) and total JS
      (7 MiB), and a check by name that nothing a page fetches on demand (the
      charting engine, the markdown and docs engines, the mock backend) is
      loaded with the page. The checks fail, instead of passing on nothing, when
      `index.html` names no script of the build. A project sets its own numbers
      and its own on-demand chunks under `bundle` in
      `src/modules/app/config/deploy.config.ts`, and each run prints them
      beside the defaults
- [x] A stale route chunk after a deploy reloads once instead of dead-ending,
      only when the attempt can be recorded, and a second failure reaches the
      error state
- [x] The gates a project inherits hold in a project. `vpr lint` and
      `vpr test --run` pass after a version bump, an edited managed file and
      the first `add module`. What describes a _release_ of the template (the
      shipped lockfile, the CLI payload, the files a migration installs, the
      public-surface snapshots) runs for maintainers only, as
      `vpr lint:maintainer`; a project's own check is `vuestrata doctor`
- [x] An existing project takes a release with `vuestrata upgrade`. Files
      nobody edited are replaced, and that now includes the plumbing most fixes
      land in (the auth store and adapters, the boot sequence, the route guard,
      the build and header scripts). An edited file is kept, with the release's
      version beside it and a note. `UPGRADING.md` has the 1.1.0 steps

**Known gaps:**

- 47 raw-palette occurrences remain across four files (the showcase tables
  page, and three in `users/`). The lint ratchet prevents new ones and refuses
  a stale baseline; migrating these is mechanical.
- `comark` is vendored as a committed tarball
  (`vendor/comark-1.0.0-05679bb.tgz`) because the version this app uses is not
  on the registry — 0.6.2 has no `comark/vue` or `comark/ast` export. It was
  previously fetched from `pkg.pr.new`, whose preview builds are not retained,
  so the build had an off-site single point of failure. See `vendor/README.md`
  for the upgrade path.
- The demo salt in `demo-storage.ts` is a public constant, not a secret. It
  makes tampering visible, not impossible — which is all a client-side value
  can do.
- **The initial payload is ~511 KB gzipped** in a production build (~516 KB in
  the demo build) against a 560 KB budget. index.html loads the stylesheet
  (85 KB gzipped and 639 KB raw, every theme in one file, against a raw budget
  of 700 KB), the Reka primitives (`ui-vendor`, 90 KB), the framework
  (`vue-vendor`, 77 KB), the data layer (`data-vendor`, 48 KB) and the shell.
  The charting engine is no longer among them: `charts-vendor` (668 KB raw) is
  fetched by the first chart a page renders, and the markdown and docs engines
  by the docs. It used to be preloaded on every page, the login screen
  included, because the vendor chunk groups in `vite.config.ts` had no order
  and the chart group took the Vue runtime with it; the payload was ~728 KB.
  The chart group also leaves out what the library depends on (`tslib`, which
  gets a chunk of its own), so an eager import of that package elsewhere does
  not bring the engine back. `verify-bundle` now fails a build that loads one
  of those chunks with the page, by name, and pins the sizes.
  What still loads with every page and need not: all three locale catalogs,
  and each module's messages and query composables, because the module
  registry imports every module's barrel. The payload grows with each module
  and each locale a project adds.

## 3. Your application's production readiness

**This is on you and your backend.** The frontend is ready to be pointed at one.

### Blocked on things this repository cannot contain

| Blocker                                                                         | Why it cannot live here                                    |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| A real API implementing the [endpoint contract](8.deployment/2.real-production) | It is your backend                                         |
| OAuth client IDs and redirect URIs                                              | Per-deployment, and the secret half never touches a client |
| A deploy job, and the credentials of the host it deploys to                     | Where your app ships is your decision                      |
| An error-reporting DSN + `createReporter()` implementation                      | Optional by design; no SDK ships                           |
| A performance reporter (`createPerformanceReporter()`) for web vitals           | Same integration point, same reason                        |
| TLS, WAF, rate limiting, backups                                                | Infrastructure                                             |

The workflow `vuestrata add ci` writes stops at a verified artifact;
[CI for your project](8.deployment/3.ci-for-your-project) shows where a deploy
job goes. A `VERCEL_TOKEN` is not among the credentials you need: the one
workflow here that reads it, `deploy-demo.yml`, deploys the template's **demo**,
and since 1.1.0 it runs only in the template's own repository.

Partly mitigated in-repo: unit tests pin each real adapter's request paths and
bodies against a stubbed `apiFetch` (`test/unit/auth/`). The `msw/node` suites
exercise the demo's mock handlers, not those adapters, so nothing here stands in
for running against your backend.

### Security checklist

The first item is not a formality.

- [ ] **Every endpoint authorises independently.** Frontend RBAC decides what
      renders. It cannot decide what is allowed. If a hidden button is the only
      thing protecting an operation, it is unprotected.
- [ ] Server-side validation of every payload. The zod schemas run in a browser
      the user controls.
- [ ] Prices, totals and any derived money recomputed server-side; client
      figures ignored.
- [ ] `AUTH_ADAPTER` and transport chosen deliberately; cookies preferred for
      first-party apps, and **never** both cookie and bearer.
- [ ] CSRF tokens enforced server-side on every mutating request when using
      cookie transport.
- [x] CSP `connect-src` widened to your API origin. Handled in the Docker
      image: its entrypoint derives the **origin** (never a path — one invalid
      source voids the whole directive) from the `VUESTRATA_API_URL` the
      container is started with, the same value the app fetches with. A static
      host renders its headers with `sync-headers.mjs --from-env` at deploy
      time; confirm it there.
- [ ] Every other origin the app connects to (an identity provider, an error
      tracker, a realtime endpoint) is declared under `headers` in
      `src/modules/app/config/deploy.config.ts`, and `vpr security:headers` was
      run after the change.
- [ ] `VUESTRATA_SESSION_PERSISTENCE` chosen deliberately. `refresh-cookie`
      (the production default) needs a backend that sets an HttpOnly refresh
      cookie on login, reads it on `/auth/refresh` and `/auth/logout`, and — when
      the API is on another origin — allows credentialed CORS on `/auth/*` with
      a `SameSite` the browser will accept; `session`/`local` put a refresh
      token where an XSS can read it; `none` means a reload ends the session.
- [ ] No secret in any `VUESTRATA_*` variable. Each one reaches the browser,
      inlined into the bundle or served in `/runtime-config.js`, and is public.
- [ ] Sourcemaps uploaded to your error provider from CI, then deleted before
      the artifact is published.
- [ ] Refresh-token rotation and reuse detection implemented server-side.
- [ ] Rate limiting on `/auth/login` — the client-side lockout is a courtesy,
      not a control.

### Production checklist

- [ ] `vp check` clean
- [ ] `vpr lint` clean — includes the toolchain-pin and security-header drift checks
- [ ] `vuestrata doctor` passes, and every file it lists as edited or waiting
      for `vuestrata adopt` is one you meant to keep as yours
- [ ] `vpr test --run` green (coverage thresholds are enforced)
- [ ] `E2E_TARGET=preview vpr test:e2e` green against the built artifact
- [ ] `verify-bundle --mode=production` passes
- [ ] `node scripts/docs/check-links.mjs` passes
- [ ] `docker build` succeeds and the image serves — CI does this, and runs
      `e2e/production-artifact.spec.ts` against the running container
- [ ] `/version.json` reports the release you expect
- [ ] `VUESTRATA_API_URL` points at your real origin
- [ ] `VUESTRATA_RELEASE` set to the git SHA
- [ ] Error reporting configured, or consciously declined
- [ ] Demo account confirmed absent from the bundle — checked by default by
      `verify-bundle --mode=production`, in the in-app docs pages too;
      `--strict-demo=false` turns that off, for local triage only
- [ ] A backend health check exists and is monitored
- [ ] Rollback plan: the previous artifact is still deployable

### Accessibility checklist

Automated coverage catches perhaps half of what matters. The rest is in
[Accessibility testing](7.testing/2.accessibility) and needs a person:

- [ ] Keyboard-only pass over your new pages
- [ ] Screen-reader pass on at least one primary flow
- [ ] Every chart's non-visual representation actually says something useful
- [ ] Your brand theme re-checked for contrast in **both** colour modes

## Environment variables, exactly

### Demo

```
VUESTRATA_RUNTIME_MODE=demo
VUESTRATA_USE_MOCKS=true
VUESTRATA_AUTH_ADAPTER=mock
```

### Production

```
VUESTRATA_RUNTIME_MODE=production
VUESTRATA_USE_MOCKS=false
VUESTRATA_AUTH_ADAPTER=jwt
VUESTRATA_API_URL=https://api.yourcompany.com
VUESTRATA_APP_TITLE=Acme Console
VUESTRATA_RELEASE=$GIT_SHA
```

Full reference: [Environment](6.configuration/1.environment).
