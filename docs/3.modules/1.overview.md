# Module System

Vuestrata uses a lightweight module system where each module is a self-contained package under `src/modules/<name>/`.

Current built-in modules:

- `auth` (login / register / OAuth callback pages, `useAuth` composable, mock handlers — required, cannot be disabled)
- `analytics` (dashboard home, audit logs, charts — server state via TanStack Query)
- `billing` (server state via TanStack Query)
- `users` (server state via TanStack Query)
- `showcase` (forms and tables demos)
- `settings` (client state via Pinia + persisted local storage)

## Module Definition

Each module exports a `ModuleDefinition` from its `index.ts` file.

```ts
import type { ModuleDefinition } from '~/modules/types'

const myModule: ModuleDefinition = {
  config: {
    id: 'my-module',
    name: 'My Module',
    description: 'Module description',
    version: '1.0.0',
    category: 'system',
    enabledByDefault: true,
    // Optional: mark `required: true` to prevent the module from being
    // disabled at runtime (used by core modules like `auth`).
  },
  navItems: [
    {
      label: 'my_module_nav',
      icon: 'widget',
      to: '/dashboard/my-module',
      order: 50,
    },
  ],
  i18n: {
    en: { my_module_nav: 'My Module' },
  },
}

export default myModule
```

## Registration

Modules are imported in `src/modules/setup.ts` and passed to `setupModules(...)` from `src/main.ts`.

The setup layer is responsible for:

- Registering module routes and nav metadata
- Loading module-local i18n messages
- Keeping enabled module state persistent

Enablement is persisted per browser in `vuestrata-enabled-modules`, alongside a
`vuestrata-known-modules` list of every module id that browser has already seen.
A module marked `enabledByDefault` is enabled the first time it appears in that
diff, and its persisted state is honoured from then on — which is what lets a
module added long after someone's first visit still show up for them, without
re-enabling one that was deliberately turned off.

## Boundaries

Use this ownership rule for every module:

- **Server state** (`GET/POST/PATCH` data): TanStack Query composables
- **Client state** (preferences/UI toggles): Pinia stores
- **Cross-module notifications**: typed app event bus (`src/modules/core/lib/events.ts`)

Avoid mixing server and client ownership for the same entity.

## Public API

Each module must expose its public API through `src/modules/<name>/index.ts` only.

Do not deep-import internals across modules.

Good:

```ts
import { useUsers } from '~/modules/users'
```

Avoid:

```ts
import { useUsers } from '~/modules/users/composables/useUsers'
```
