# Navigation

Navigation is assembled from what the enabled modules contribute. No file lists
the sidebar's contents — add a module and its entries appear; disable it and
they vanish.

## The pipeline

```
module.navItems  →  moduleStore.navGroups  →  useModuleNav  →  AppSidebar
                    (bucketed by group)      (permission-filtered,
                                              active state resolved)
```

`useModuleNav` decides the two hard questions — "may this user see it" and "is
this the current page" — once, so no template re-derives them.

## Groups

Sections are declared in `src/modules/nav-groups.ts`:

```ts
export const NAV_GROUPS = [
  { id: 'overview', label: 'nav_group_overview', order: 10 },
  { id: 'commerce', label: 'nav_group_commerce', order: 20 },
  { id: 'work', label: 'nav_group_work', order: 30 },
  { id: 'organization', label: 'nav_group_organization', order: 40 },
  { id: 'account', label: 'nav_group_account', order: 50 },
  { id: 'reference', label: 'nav_group_reference', order: 60 },
] as const
```

A module references a group by id and cannot define one. If modules could
define groups, two modules contributing to "Commerce" would each carry a copy of
the heading and could disagree about its order — and the sidebar would sprout a
new section every time someone typed a slightly different string.

An unknown group id falls back to the default rather than dropping the item:
hiding a navigation entry because of a typo is a much worse failure than showing
it under the wrong heading.

Empty groups are not rendered. Permission filtering can legitimately empty a
whole section, and a heading with nothing under it is a promise the UI cannot
keep.

## Active state

```ts
matchesRoute(currentPath, to, exact)
```

Prefix matching by default, so a section stays active on its own detail pages
(`/dashboard/orders` on `/dashboard/orders/42`). The boundary is a path
separator, so `/dashboard/order` does not match `/dashboard/orders`.

**`exact: true`** opts an index entry out. `/dashboard` prefixes every path in
the app, so without it the Overview entry is highlighted everywhere — and the
visual state and the announced `aria-current` disagree.

## Nested sections

```ts
{
  label: 'orders_nav',
  icon: 'shopping-cart',
  to: '/dashboard/orders',
  group: 'commerce',
  exact: true,
  children: [
    { label: 'orders_nav_all', to: '/dashboard/orders', exact: true },
    { label: 'orders_nav_new', to: '/dashboard/orders/new', permission: 'orders:manage' },
  ],
}
```

A parent may have both `to` and `children`. Clicking the label still goes
somewhere useful — a disclosure that only expands makes the most-wanted
destination the one that takes two clicks.

Three behaviours worth knowing:

- **Open state is seeded from the route, not bound to it.** Navigate into a
  section and it is already open; collapse it and it stays collapsed. Binding
  would fight the user — closing a section you are inside would spring straight
  back open.
- **A parent whose children are all permission-filtered away, and which has no
  route of its own, is dropped.** Otherwise the sidebar grows disclosures that
  open onto nothing.
- **In the collapsed rail, children render as a flyout.** Hiding them would make
  those routes unreachable from the sidebar entirely.

## Permissions

```ts
{ label: 'reports_nav', to: '/dashboard/reports', permission: 'reports:read' }
```

Filtering is recursive, and it removes entries from the DOM rather than hiding
them with `v-show` — a route the user cannot reach should not be discoverable in
the accessibility tree either.

::alert{type="warning"}
This is a UI affordance. It decides what renders, not what is allowed. The
route guard is a second layer, and your backend is the only real one.
::

## Breadcrumbs

Routes are registered flat — `/dashboard/orders/:id` is not a child record of
`/dashboard/orders` — so `route.matched` contains the layout and the leaf and
nothing between. It cannot produce a trail.

`useBreadcrumbs` walks the URL instead: each `/`-delimited prefix is resolved
against the router, and prefixes that correspond to a real route become links.
Labels resolve in order: `meta.title` → the matching sidebar label → a humanized
segment.

A detail page replaces the trailing crumb with the entity it loaded:

```ts
useBreadcrumbLabel(() => customer.value?.company)
```

so the trail reads `Customers → Northwind Logistics` rather than
`Customers → CUS-1004`. It clears on unmount, so a stale entity name never leaks
onto the next page.

## Command palette

⌘K / Ctrl+K opens a palette fed the same permission-filtered tree the sidebar
renders, so it can never offer a route the user would be bounced out of. The
group name rides along as a hint — it is what makes two identically named leaves
distinguishable in a flat list.

There is also a visible trigger. The shortcut is a convenience, not the only way
in: touch users and anyone who never learns the chord still need a control they
can activate.

## Testing

`e2e/sidebar.spec.ts` asserts the mechanism rather than any module's links:
groups render, sections disclose, active state follows the route, the breadcrumb
resolves — and, the rule the whole design exists to keep, **every advertised
destination resolves to a real page**.

Nothing in it depends on position, so reordering the sidebar does not break the
suite.
