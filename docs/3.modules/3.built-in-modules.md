# Built-in Modules

This page documents the active module set shipped with Vuestrata.

## Auth

| Property      | Value                                           |
| ------------- | ----------------------------------------------- |
| ID            | `auth`                                          |
| Category      | `core`                                          |
| Default       | Enabled                                         |
| Required      | Yes (cannot be disabled)                        |
| State pattern | Pinia (auth store, infrastructure) + composable |

Auth owns the public authentication surface: `/auth/login`, `/auth/register`,
`/auth/callback` pages, the `useAuth` composable, PKCE helpers, and the MSW
mock handlers used by the `mock` adapter. The auth Pinia store, API
auth-interceptor, router guard, and RBAC engine remain in
`src/modules/app/` and `src/modules/core/` because they boot before the
module system.

The module is registered first in `setup.ts` and its `mockHandlers()` hook
contributes the auth handlers that MSW starts after `setupModules` runs.

Public API:

- `useAuth`
- `createAuthAdapter`, `resolveAuthAdapterName`
- `exchangeOAuthCode`, `OAuthRedirectError`
- `generateCodeVerifier`, `generateCodeChallenge`, `generateState`
- `AuthAdapter` (type)

## Users

| Property      | Value          |
| ------------- | -------------- |
| ID            | `users`        |
| Category      | `users`        |
| Default       | Enabled        |
| State pattern | TanStack Query |

Users manages team members, role assignments, and per-user permission overrides.

- **Invite users** — `useInviteUserMutation` posts to `POST /users`; the MSW handler validates required fields, rejects duplicate emails, and persists the new user to IndexedDB in demo mode.
- **Role assignment** — `useUpdateRoleMutation` patches `PATCH /users/:id/role`.
- **Per-user permissions** — `useUpdatePermissionsMutation` patches `PATCH /users/:id/permissions`; in demo mode the MSW handler refreshes the current session if the edited user is self.

Public API:

- `useUsers`
- `useUsersQuery`
- `useUpdateRoleMutation`
- `useInviteUserMutation`
- `useUpdatePermissionsMutation`
- `usersModuleKeys`
- `UserFilters`, `UserInvitePayload`, `UserRoleUpdatePayload`

## Domain modules

Eight modules built on the same foundation: a zod contract, a seeded mock
backend from `createCollectionMock`, queries from `createCollectionApi`, and
functional pages. Each exists to demonstrate a **different** interaction pattern
rather than to repeat one — they are the worked examples for
[Creating a module](./2.creating-a-module).

| Module    | ID          | Group        | Permissions                          | Pattern it demonstrates                                    |
| --------- | ----------- | ------------ | ------------------------------------ | ---------------------------------------------------------- |
| Customers | `customers` | Commerce     | `customers:read`, `customers:manage` | Server-backed table, record page, create/edit form         |
| Orders    | `orders`    | Commerce     | `orders:read`, `orders:manage`       | Multi-step form; server-side pricing                       |
| Products  | `catalog`   | Commerce     | `catalog:read`, `catalog:manage`     | Card grid; inline editing on the record page               |
| Projects  | `projects`  | Work         | `projects:read`, `projects:manage`   | Kanban board, keyboard-first                               |
| Calendar  | `calendar`  | Work         | `calendar:read`, `calendar:manage`   | Month grid with roving tabindex; date-range query          |
| Messages  | `messages`  | Work         | `messages:read`                      | Master/detail with URL-held selection; notification centre |
| Team      | `team`      | Organization | `team:read`                          | Grouped directory, profile page (read-only)                |
| Reports   | `reports`   | Organization | `reports:read`, `reports:export`     | Permission-restricted page with a second-tier action       |

Three design decisions run through all of them:

- **The schema is the contract.** The mock handler builds responses through it
  and the query validates on arrival, so the two cannot drift.
- **Money is minor units plus a currency code**, never a formatted string, and
  totals are recomputed server-side. The order pricing helper lives in
  `src/modules/orders/pricing.ts`, not under `mocks/`, because a page imports it
  — anything a page imports is in the production bundle.
- **`team` is deliberately separate from `users`.** `users` is access
  administration — who may do what. `team` is the people directory — who someone
  is and when they are awake. Merging them puts a permission matrix on a profile
  page and a phone number in an access review.
