# Ui Wrapper Architecture

Vuestrata keeps a single public component layer under `src/modules/app/components/ui/`. App code
imports `Ui*` wrappers; those wrappers hold markup and styling only, and delegate field behaviour
to a matching composable under `src/modules/app/composables/forms/`.

## Structure

```
src/modules/app/
├── components/ui/
│   ├── UiButton.vue
│   ├── UiDialog.vue
│   ├── UiTextField.vue
│   └── …                      # 69 wrappers, all flat — no nested folders
└── composables/forms/
    ├── index.ts               # barrel; wrappers import from here
    ├── useUiTextField.ts
    ├── useUiSelect.ts
    └── …                      # one per field-like component
```

There is no `components/ui/base/` folder. Shared behaviour lives in the `forms/` composables, not
in intermediate `Base*.vue` components — a `Ui*` wrapper is the only component in the chain.

## Responsibilities

- **`Ui*` wrappers** — stable public imports for pages, layouts, and feature modules. They own the
  template, the `data-ui` / `data-variant` attributes that themes style against, and nothing else.
- **`composables/forms/useUi*.ts`** — Formwerk bindings, labels, hints, error output, and repeated
  interaction logic. Each exports its hook plus the props interface the wrapper spreads.
- **`core/lib/*`** — framework-agnostic utilities beneath the component layer.

## The Provider Indirection

Most wrappers accept a `provider` prop defaulting to `'reka'`, and render it back out as
`data-provider`:

```vue
<script setup lang="ts">
import { useUiTextField, type TextFieldProps } from '@/composables/forms'

const props = withDefaults(defineProps<TextFieldProps & { provider?: 'reka' }>(), {
  provider: 'reka',
})
const { inputProps, labelProps, errorMessage } = useUiTextField(props)
</script>
```

The prop exists so a second headless library can be introduced behind the same public API without
touching call sites. Today `'reka'` is the only implementation.

## Why Keep The Split

It lets the repo keep one import contract without duplicating field logic across dozens of
components. When a field needs labels, validation messages, or keyboard handling, the composable
owns it and the wrapper stays thin — and the logic stays unit-testable without mounting anything.

## Adding A New Ui Component

Run the generator rather than hand-wiring the four touch points:

```bash
vp run gen:component <Name>
```

It writes `components/ui/Ui<Name>.vue` and `composables/forms/useUi<Name>.ts`, and registers both
in their barrels. What you still decide yourself:

1. The props interface and any `variant` / `size` unions.
2. The `data-ui` value the theme layer styles against — reuse an existing one where the component is
   a variation of something that already exists.
3. Semantic tokens only for colour. Raw Tailwind palette utilities (`bg-red-500`) are rejected by
   the `no-raw-palette` lint rule; see [Semantic tokens](/docs/theming/semantic-tokens).
4. Tests under `test/component/ui/`.
